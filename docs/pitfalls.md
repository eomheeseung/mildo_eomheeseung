# A. 프록시와 지연 로딩

## A-1. N+1 — 목록을 뽑았는데 쿼리가 목록 크기만큼 더 나간다

```java
List<ActivityLog> logs = repository.findAll();       // 쿼리 1번
for (ActivityLog log : logs) {
    log.getUser().getNickname();                     // 로그 수만큼 쿼리
}
```

`@ManyToOne(fetch = LAZY)`라 `user`는 **프록시**입니다. 실제로 값을 건드리는 순간
그때야 조회가 나갑니다. 목록이 20건이면 **1 + 20 = 21번**입니다.

무서운 점은 **개발 중에는 안 보인다**는 것입니다. 로컬 데이터가 3건이면 4번이라
눈에 안 띄고, 운영에서 수백 건이 되면 그때 터집니다.

### 해결 세 가지 — 언제 무엇을 쓰는가

| | 방식 | 쓰는 자리 | 안 되는 자리 |
|---|---|---|---|
| 페치 조인 | 조인해서 **한 번에** 가져옴 | ToOne, 또는 ToMany 하나 | ToMany 여럿 · ToMany + 페이징 |
| 배치 사이즈 | 지연 로딩을 **IN 절로 묶어** 가져옴 | ToMany 여럿 · 페이징과 함께 | 완전한 1회 조회가 필요할 때 |
| DTO 직접 조회 | 엔티티 없이 **필요한 컬럼만** | 화면 전용 조회 | 그 객체로 수정할 때 |

---

**① 페치 조인 — 기본 선택지**

```java
@Query("SELECT a FROM ActivityLog a JOIN FETCH a.user u WHERE ...")
```

`JOIN FETCH`는 SQL 에 없는 JPQL 전용 문법입니다. "조인한 것을 **엔티티에 채워 넣어라**"는 뜻이라
ORM 에만 있는 개념입니다.

**ToOne(ManyToOne·OneToOne)이면 페이징과 같이 써도 안전합니다.** 결과 행 수가 안 늘어나므로
DB 가 `LIMIT`으로 자릅니다.

**ToMany(OneToMany)는 다릅니다.** 조인하면 행이 곱해집니다 — 게시글 10개에 댓글이 각 5개면
50행이 나옵니다. 여기에 `LIMIT 10`을 걸면 게시글 2개어치만 나옵니다.
하이버네이트는 이걸 알아서 **전부 읽어 메모리에서 자릅니다.** 경고만 남기고 조용히 동작합니다.

```
HHH000104: firstResult/maxResults specified with collection fetch; applying in memory
```

데이터가 적을 땐 통과하고, 늘면 OOM 입니다.
**ToMany 를 둘 이상 페치 조인하면** 아예 `MultipleBagFetchException`으로 뜹니다.

이 프로젝트에서 `JOIN FETCH`를 쓰는 16곳은 전부 ToOne 입니다.
`ActivityLogRepository.searchAll`이 대표적인데, 거기서 하나 더 짚을 게 있습니다.

```java
value      = "... JOIN FETCH a.user u ..."   // 목록용
countQuery = "... JOIN a.user u ..."          // 개수용 — FETCH 없음
```

`Page`를 쓰면 개수 쿼리가 따로 나가는데, **개수를 세는 데 유저 컬럼을 끌어올 이유가 없고**
`COUNT`에 `JOIN FETCH`를 쓰면 하이버네이트가 거부합니다. `countQuery`를 안 주면 자동 생성이
실패하므로 손으로 써 준 것입니다.

---

**② 배치 사이즈 — ToMany 와 페이징을 같이 써야 할 때**

```yaml
spring.jpa.properties.hibernate.default_batch_fetch_size: 100
```

지연 로딩을 **하나씩 하지 않고 모아서** 합니다.

```sql
-- 켜기 전: 20번
SELECT * FROM users WHERE id = 1;
SELECT * FROM users WHERE id = 2;   ...

-- 켠 뒤: 1번
SELECT * FROM users WHERE id IN (1, 2, 3, ... 20);
```

쿼리 수가 `1 + N`에서 **`1 + (N / 배치크기)`**로 떨어집니다.
페치 조인과 달리 **행이 곱해지지 않아 페이징과 아무 충돌이 없습니다.**

`@BatchSize`로 엔티티·필드별로 걸 수도 있지만, **전역 설정을 켜 두는 편이 낫습니다.**
개별로 걸면 안 걸린 곳이 조용히 N+1 로 남습니다.

> **이 프로젝트에는 아직 안 켜져 있습니다.** 지금은 페치 조인과 DTO 조회로 막고 있는데,
> 전역 배치는 **놓친 자리를 덮어주는 안전망**이라 켜 둘 값어치가 있습니다.
> 켜서 손해 볼 일이 거의 없는 몇 안 되는 설정입니다.

---

**③ DTO 직접 조회 — 엔티티가 필요 없을 때**

```java
@Query("SELECT new tideflo...SomeDto(a.id, u.nickname, a.createdAt) FROM ActivityLog a JOIN a.user u")
```

엔티티를 안 만들고 **필요한 컬럼만** 뽑습니다. 지연 로딩이라는 개념 자체가 없으니 N+1 이 날 수 없습니다.
전송량도 가장 적습니다.

대신 **그 객체로는 수정을 못 합니다.** 영속 상태가 아니라 더티 체킹이 안 됩니다.
화면 하나를 위한 조회라 재사용도 잘 안 됩니다.

> 이 프로젝트에 `SELECT new`가 **45곳**입니다. 관리자 통계·목록처럼 읽기만 하는 화면이
> 대부분 이쪽입니다. 페치 조인(16곳)보다 훨씬 많습니다.

---

### 판단 순서

```
그 화면이 엔티티를 수정하는가?
  아니오 → DTO 직접 조회
  예 ↓
연관이 ToOne 인가?
  예   → 페치 조인
  아니오 ↓
페이징이 필요한가?
  예   → 배치 사이즈
  아니오 → 페치 조인(단, ToMany 는 하나만)
```

## A-2. 프록시로 충분한 자리에 조회를 하지 않는다

활동 로그를 저장할 때 필요한 것은 `user_id` 값 하나뿐입니다.

```java
User userRef = userRepository.getReferenceById(userId);   // DB 에 안 감
activityLogRepository.save(ActivityLog.builder().user(userRef)...build());
```

`getReferenceById`는 **프록시만 만듭니다.** 프록시도 id 는 알고 있으므로 INSERT 에 필요한 것은
다 있습니다. `findById`였다면 로그 한 건마다 **SELECT + INSERT 두 방**이 나갔을 것입니다.

대가는 있습니다 — 그 id 의 회원이 없어도 그 자리에서 안 터지고 **INSERT 시점에 FK 위반**으로
터집니다. 로그 저장은 실패해도 본 흐름을 막지 않아야 하므로 받아들일 만한 거래였습니다.

**프록시를 트랜잭션 밖으로 들고 나가면** 초기화가 안 돼 `LazyInitializationException` 입니다.
그래서 컨트롤러까지 엔티티를 들고 가지 않고 DTO 로 변환해 넘깁니다.

## A-3. 양방향으로 만들지 않은 이유

`ActivityLog`는 `@ManyToOne User`를 갖지만, `User`에는 **컬렉션이 하나도 없습니다.**

```java
log.getUser()               // 된다
user.getActivityLogs()      // 그런 메서드가 없다
```

**"조회가 안 된다"가 아니라 "공짜로 딸려오지 않는다"입니다.**
필요하면 리포지토리로 가되, 그때 **페이징을 강제할 수 있습니다.**

```java
Page<ActivityLog> findByUserId(Long userId, Pageable pageable);
// List<ActivityLog> findAllByUserId(Long userId);   ← 주석 처리해 막아둠
```

`User`에 `@OneToMany`를 달았으면 **유저 한 명 조회에 로그 293건(현재 최다)이 딸려올 수** 있습니다.
로그는 상한 없이 늘어나므로 컬렉션으로 매면 안 되는 쪽입니다.

**부수 효과로 직렬화 사고도 막힙니다.** 엔티티를 그대로 JSON 으로 내보내도 딸려 나갈 컬렉션이 없고,
순환 참조로 무한 직렬화될 일도 없습니다.

# B. 쓰기 시점과 영속성 컨텍스트

## B-1. `save()`는 커밋할 때 쓴다 — try/catch가 못 잡는 자리가 있다

구글폼 응답 수신 API 를 만들고 **같은 응답 5건을 동시에** 넣어봤습니다.
데이터는 완벽했는데(1행·원장 1건·잔액 정확) **3건이 500** 을 받았습니다.

```java
@Transactional
public SurveyResponse receive(SurveyWebhookRequest request) {
    try {
        return repository.save(...);              // 여기서 안 터짐
    } catch (DataIntegrityViolationException e) {  // 그래서 여기 안 걸림
        return repository.findByResponseId(...).orElseThrow();
    }
}                                                  // ← 커밋 시점에 터짐
```

`save()`는 곧바로 DB 에 쓰지 않고 **커밋할 때 몰아 씁니다.** 유니크 제약 위반은 그 시점에 나는데,
이미 try/catch 를 빠져나온 뒤라 잡을 자리가 없습니다.

**왜 그냥 두면 안 되는가** — 이 API 를 부르는 것은 Google Apps Script 이고, 200 이 아니면 **다시 쏩니다.**
500 을 주면 영원히 재시도합니다. 데이터가 멀쩡해도 고쳐야 하는 이유가 그것입니다.

**해결** — 트랜잭션을 걷어내고 `saveAndFlush`로 바꿔 예외가 그 자리에서 나게 했습니다.
그러면 catch 가 잡아 기존 행을 그대로 돌려줍니다. 수정 후 동시 10건이 전부 200.

> 같은 뿌리: `troubleshooting.md` §7 — try/catch 로는 트랜잭션 격리가 안 된다

## B-2. 벌크 연산은 영속성 컨텍스트를 우회한다 — 그런데 `clearAutomatically`도 위험하다

`@Modifying` 쿼리는 DB 만 바꿉니다. 1차 캐시의 엔티티는 옛날 값 그대로입니다.

교과서적 해법은 `clearAutomatically = true`인데, 밀도 TALK 입장 표시를 만들며 **도로 뺐습니다.**

```java
User me = findUser(email);          // 영속 상태
TalkRoom room = ...;                // 영속 상태

touchEnteredIfStale(...)            // ← 여기서 컨텍스트를 비우면
room.getTitle()                     //   호출부가 들고 있던 것들이 떨어져 나감
```

**컨텍스트를 비우면 그 트랜잭션의 다른 엔티티까지 전부 떨어집니다.**
지금 필요한 것은 "이 행 하나 갱신"뿐이라 대가가 맞지 않았습니다.

대신 순서로 풀었습니다. 같은 메서드에서 쓰고 읽지만 **마지막 읽기가 `COUNT`** 라 문제가 없습니다.

| 조회 종류 | 벌크 쓰기 직후 |
|---|---|
| 엔티티 조회 (`findById`) | 1차 캐시의 옛날 값 |
| 집계·스칼라 (`COUNT`, `MAX`) | **캐시를 안 거침. 최신값** |

원래 코드의 주석이 이미 그 고려를 담고 있었습니다 —
"조회보다 먼저 해야 「내가 첫 방문자」일 때 1이 보인다".

**규칙** — 벌크 연산은 트랜잭션 끝쪽에 몰아 둡니다. 쓰고 나서 같은 트랜잭션에서 그 엔티티를
다시 안 읽으면 고민할 일이 없습니다.

## B-3. 1차 캐시는 `findById`만 막는다

흔한 오해가 "같은 트랜잭션 안에서는 조회가 캐시된다"입니다. 절반만 맞습니다.

```java
em.find(User.class, 1L)       // 두 번째 호출 → DB 안 감
repo.findByEmail("a@b.com")   // 두 번째 호출 → DB 또 감
```

`findById`만 `EntityManager.find()`로 넘어가 1차 캐시를 봅니다.
`findByXxx`는 이름을 파싱해 **JPQL 을 실행**하므로 매번 DB 에 나갑니다.
캐시는 id 로만 색인돼 있어서 "email 이 이거인 애가 캐시에 있나"를 찾을 수 없습니다.

JPQL 에서 1차 캐시가 하는 일은 **결과를 매핑할 때** 개입하는 것입니다.
DB 에서 행을 받아온 뒤 그 id 가 이미 캐시에 있으면 **읽어온 값을 버리고 캐시의 객체를 줍니다.**

```
쿼리는 두 번, 객체는 하나
```

이것이 없으면 같은 행이 두 객체로 존재하게 되고 어느 쪽을 저장할지 알 수 없어집니다.
**1차 캐시의 진짜 값어치는 조회 절감이 아니라 동일성 보장입니다.**

조회 횟수를 줄이려면 캐시를 믿을 게 아니라 **호출을 안 해야 합니다.**
이 프로젝트의 서비스들이 유저를 메서드 첫 줄에서 한 번 조회해 변수로 들고 다니는 이유입니다.

같은 이유로 **벌크 UPDATE 후 JPQL 재조회도 옛날 값**이 나옵니다(B-2).
DB 는 다녀왔는데 결과를 버리기 때문입니다.

한 가지 더 — **스냅샷은 1차 캐시가 아닙니다.** 스냅샷은 엔티티를 읽을 때 떠 두는 원본 복사본이고,
flush 시점에 현재 값과 비교해 바뀐 필드를 찾는 **더티 체킹용**입니다. 조회와 무관합니다.

# C. 트랜잭션 경계

## C-1. `@Async`는 자기호출이면 아무 일도 하지 않는다

`ActivityLogService.log()`에 `@Async`와 `@Transactional`이 둘 다 붙어 있습니다.
의도는 "활동 로그가 본 흐름과 무관하게 별도 스레드·별도 트랜잭션에서 저장된다"였습니다.

```java
@Async
@Transactional
public void log(Long userId, String activityType, ...) { ... }

public void logLogin(Long userId, ...) {
    log(userId, "로그인", ...);      // ← 같은 클래스에서 직접 호출
}
```

외부 빈이 부르는 것은 `logLogin`·`logProfileUpdate` 같은 래퍼고, **그 래퍼들이 같은 클래스의
`log()`를 직접 부릅니다.** 자기호출은 프록시를 거치지 않으므로 두 어노테이션 모두 무효입니다.

| | 의도 | 실제 |
|---|---|---|
| 스레드 | 별도 | 호출자 스레드 |
| 트랜잭션 | 별도 | 호출자 트랜잭션 |
| 호출자 롤백 시 | 로그는 남음 | **로그도 사라짐** |
| 로그 저장 실패 시 | 호출자 무관 | 호출자가 rollback-only 로 마킹될 수 있음 |

"탈퇴 시도했다가 실패"를 남기려 해도 안 남습니다. 운영에 4,106건이 쌓여 있지만
전부 호출자 트랜잭션에 묶여 저장된 것들입니다.

**같은 함정을 피한 사례** — `AuthService`는 경계가 필요한데 자기호출이라 `@Transactional`을
못 쓰는 상황이라, `TransactionTemplate`으로 경계를 프로그래밍 방식으로 잡습니다.
프록시를 거치지 않으므로 자기호출 함정이 없습니다. 설문 보상 지급도 같은 방식입니다.

---

## C-2. ThreadLocal 은 스레드를 넘지 않는다

트랜잭션·SecurityContext·HttpServletRequest 가 전부 ThreadLocal 에 있습니다.
`@Async`로 스레드가 바뀌는 순간 **아무것도 따라가지 않습니다.**

- 트랜잭션이 없으니 `@Transactional`이 **새 트랜잭션을 엽니다.** `REQUIRED`여도 참여할 부모가 없습니다
- 요청 정보가 없으니 `RequestUtils.getCurrentIp()`가 **null** 을 반환합니다

그래서 활동 로그는 IP·디바이스를 **호출자가 미리 뽑아 파라미터로 넘깁니다.**

```java
activityLogService.logLogin(user.getId(), ipAddress, deviceInfo);
                                          // ← 호출자가 뽑아서 넘김
```

**가장 많이 데는 함정은 순서입니다.** 호출자가 아직 커밋하지 않았는데 비동기 쪽이 먼저 DB 를 읽으면
호출자가 쓴 것을 못 봅니다. 다른 트랜잭션이기 때문입니다.
그래서 "커밋 뒤에 뭘 해야 하는 것"은 비동기가 아니라 `afterCommit`으로 잇습니다(C-3).

`void` 반환이면 예외도 삼켜집니다. `AsyncUncaughtExceptionHandler`가 받는데,
이 프로젝트는 `@EnableAsync`만 있고 핸들러 설정이 없어 **기본 동작(로그만)**입니다.

## C-3. 트랜잭션 안에서 소켓·푸시를 쏘면, 일어나지 않은 일이 남의 화면에 남는다

밀도 TALK 입장 표시를 만들 때입니다. 방 부트스트랩은 방문 기록을 남기는 **쓰기 트랜잭션**입니다.
그 안에서 "○○님이 들어왔어요"를 브로드캐스트하면, 뒤에서 트랜잭션이 깨졌을 때
**입장하지 않은 사람의 입장 알림이 이미 다른 사람 화면에 떠 있습니다.**

```java
TransactionSynchronizationManager.registerSynchronization(new TransactionSynchronization() {
    @Override public void afterCommit() {
        messagingTemplate.convertAndSend(destination, event);
    }
});
```

커밋이 끝난 뒤에 쏩니다. 소켓 전송이 실패해도 방 화면은 정상적으로 열립니다 —
소켓이 죽었다고 화면이 안 뜨면 그게 더 큰 문제입니다.

**되돌릴 수 없는 것은, 되돌릴 수 있는 것이 확정된 뒤에 보냅니다.**

> 관련: `engineering-decisions.md` §16 — 트랜잭션 경계에서 외부 호출을 걷어낸다
> 실제 사고: `troubleshooting.md` §18 — AI 응답 40초 동안 커넥션을 붙잡고 있던 것

# D. 동시성

## D-1. 락 없이 읽고 쓰면 값이 조용히 사라진다

로컬에서 재현한 것입니다. 두 트랜잭션이 잔액 100 을 읽고 각자 +10 을 합니다.

```
tx1  SELECT balance → 100    tx2  SELECT balance → 100
tx1  UPDATE 110              tx2  UPDATE 110
결과: 110    (120이어야 함)
```

**에러가 나지 않습니다.** 10 이 조용히 사라집니다.

`FOR UPDATE`로 읽으면 tx2 의 SELECT 가 tx1 커밋까지 멈췄다가 **최신값 110 을 읽습니다.**
여기서 자주 놓치는 것은 `FOR UPDATE`가 하는 일이 하나가 아니라는 점입니다.

| | 읽는 대상 |
|---|---|
| 일반 SELECT | 트랜잭션 시작 시점 스냅샷. 남이 커밋해도 안 보임 |
| SELECT FOR UPDATE | 스냅샷 무시. **항상 최신 커밋본** |

"락을 건다"만이 아니라 **"기다렸다가 최신값을 읽는다"**가 같이 딸려옵니다. 후자가 실은 더 중요합니다.

### 언제 무엇을 쓰는가

```
읽고 끝                        그냥 SELECT
읽고 나서 그 값으로 쓴다         FOR UPDATE
정말 읽기만 하는데 최신 필수      FOR SHARE  (드묾. 데드락 위험)
```

`FOR SHARE`로 읽고 나서 쓰면 둘 다 공유 락을 쥔 채 서로 배타 락을 기다려 **데드락**입니다.
이 프로젝트에 `FOR SHARE`가 한 곳도 없는 이유입니다.

### 락은 트랜잭션 진입 시점에 잡히지 않는다

```
트랜잭션 시작    락 없음
그 행을 건드림   ← 여기서 잡힘
커밋/롤백        ← 여기서 놓음
```

**커밋까지 안 놓습니다.** 그래서 트랜잭션이 길수록 락을 오래 쥡니다.
트랜잭션 안에 외부 호출이 들어가면 그동안 남이 못 들어옵니다(C-3).

### 데드락은 순서 문제다

```
tx A:  users → token_account 순으로 잠금
tx B:  token_account → users 순으로 잠금
       서로 기다림 → DB 가 한쪽을 죽임 → 롤백
```

**여러 행을 건드릴 땐 항상 같은 순서로** 잠급니다.
이 프로젝트는 잔액을 건드리는 모든 경로가 `findByUserIdForUpdate` 하나로 통일돼 있습니다.

> 설계 근거: `engineering-decisions.md` §5 — 왜 비관적 락인가
> 실제 사고: `troubleshooting.md` §9 — 동시 지급 하나가 조용히 사라지던 문제

## D-2. 멱등은 코드가 아니라 제약으로 걸어야 한다

"조회해서 없으면 저장"은 순차 실행에서만 맞습니다. 동시에 들어오면 둘 다 "없음"으로 읽습니다.
검사(check)와 행동(act) 사이의 틈은 **애플리케이션 레벨에서 없앨 수 없습니다.**

설문 응답 수신은 세 겹으로 막았습니다.

| | 역할 |
|---|---|
| 저장 전 조회 | 흔한 재전송을 DB 예외 없이 조용히 넘김 |
| `response_id` UNIQUE | **최종 방어.** 동시에 들어와도 DB 가 하나만 통과시킴 |
| 원장 멱등키 | 지급 자체가 `(ONBOARDING_SURVEY, 응답id)` 로 1회 |

동시 10건 실측에서 행 1개·원장 1건·잔액 정확히 +10 이 나왔습니다.
`id` 번호가 중간에 건너뛰는데(4 → 9 → 16), **auto_increment 를 가져갔다가 제약에 막혀 롤백된
자국**입니다. 번호만 소모되고 행은 생기지 않습니다.

세 번째 겹이 특히 중요합니다 — 나중에 백오피스에서 수동 지급을 눌러도 원장이 막습니다.

> 설계 근거: `engineering-decisions.md` §4 — 멱등성을 데이터 레벨에서 강제
> 관련 사고: `troubleshooting.md` §2 (CI 도난 TOCTOU) · §9 (동시 지급)

# E. 스키마

## E-1. `ddl-auto: update`는 기존 컬럼을 절대 건드리지 않는다

`update`가 하는 일은 "없는 것을 추가"뿐입니다. 없는 테이블·컬럼·인덱스·FK 를 만듭니다.
**기존 컬럼의 타입 변경, 길이 변경, ENUM 값 목록 변경, 컬럼 삭제는 하지 않습니다.**
데이터 손실 위험을 판단할 수 없기 때문입니다.

```sql
source enum('ADMIN','ATTENDANCE','BONUS','EVENT','PHOTO','REFERRAL')
-- 자바에 SURVEY 를 추가해도 여기엔 안 생긴다 → INSERT 하는 순간 터진다
```

**설문 보상을 만들 때 피한 방법** — 새 ENUM 값을 만들지 않고 기존 값(`EVENT`, `EARN_BONUS`)을
쓰되, `ref_type`(varchar)에 `ONBOARDING_SURVEY`를 넣어 원장에서 구분했습니다. **DDL 없이 추적됩니다.**

ENUM 값을 정말 늘려야 한다면 ALTER 를 직접 치되 **기존 목록을 그대로 두고 뒤에만 붙여야 합니다.**
MySQL ENUM 은 내부적으로 순번으로 저장하므로, 순서를 바꾸면 기존 행의 값이 통째로 밀립니다.

같은 이유로 **엔티티에서 필드를 지워도 DB 컬럼은 남습니다.** 코드와 스키마가 조용히 갈라집니다.

> 실제 사고: `troubleshooting.md` §11

**참고 — 모든 문자열 컬럼이 ENUM 인 것은 아닙니다.**
`activity_logs.activity_type`은 자바에서 그냥 `String`이라 DB 도 `varchar(50)`입니다.
아무 값이나 들어가고 오타도 안 막힙니다. 어느 쪽인지 **컬럼 타입을 보면 바로 압니다.**

---

## E-2. FK 가 있으면 삭제가 막히고, 없으면 조용히 고아가 남는다

이 저장소는 두 방식이 섞여 있습니다.

```java
ActivityLog      @ManyToOne User user       // FK 있음
TalkVisitor      Long userId                // FK 없음
ExploreSeen      Long userId                // FK 없음
```

엔티티 참조로 잡으면 `ddl-auto`가 FK 를 만들어 줍니다. 그러면 회원을 하드 삭제할 때
**그 테이블을 먼저 지워야 합니다.** 안 지우면 삭제가 실패합니다.

숫자만 들고 있으면 안 막히는 대신 **회원이 사라져도 그 행이 그대로 남습니다.**
그래서 탈퇴 파기 목록을 손으로 관리하고, 손자 → 자식 → 부모 순서를 문서로 남기고 있습니다.

**둘 중 하나가 옳은 게 아니라, 어느 쪽을 골랐는지 알고 있어야 합니다.**
FK 없는 테이블을 파기 목록에서 빠뜨리면 조용히 쌓이고, FK 있는 테이블을 빠뜨리면 탈퇴가 실패합니다.
실제로 후자로 탈퇴가 전면 중단된 적이 있습니다.

존재하지 않는 테이블을 파기 목록에 넣어 두었다가 탈퇴할 때마다 에러가 나던 것도 같은 뿌리입니다.
**엔티티가 없는 테이블은 코드가 스키마를 검증해 주지 못합니다.**

# F. 호환성

## F-1. 응답 형태를 바꾸면 이미 배포된 앱이 깨진다

2026-07-30, 피드 API 응답을 배열에서 객체로 바꿔 배포했다가 **피드 탭 전체가 무한로딩**에 빠졌습니다.
스토어에 나가 있는 앱은 배열을 기대하고 있었습니다.

**필드 추가는 안전, 형태 변경은 앱 선배포 후에만. 바꿔야 하면 엔드포인트를 새로 판다.**

밀도 TALK 입장 이벤트가 그 규칙을 따른 사례입니다.
기존 앱은 `/topic/talk/{roomId}`에 오는 것을 전부 발화로 보고 말풍선을 그립니다.
거기 다른 모양을 흘리면 입장 알림이 발화로 렌더되거나 파싱에서 터집니다.

```
/topic/talk/{roomId}           발화        (건드리지 않음)
/topic/talk/{roomId}/events    방 이벤트    (새로 팜)
```

**토픽을 나누면 구독하지 않는 앱은 아무 영향을 받지 않습니다.**

Jackson 직렬화도 같은 종류의 계약입니다 — `boolean isNewUser`는 `"newUser"`로,
`Boolean isNewUser`는 `"isNewUser"`로 나갑니다. 타입만 바꿔도 **필드명이 바뀝니다.**

# G. 판단

## G-1. 코호트 지표는 "지금 유효한가"가 아니라 "그때 했는가"를 센다

관리자 대시보드의 페르소나 전환율이 **30.3%** 로 나왔습니다. 실제로는 63% 였습니다.

원인은 분자에 `personas.use_yn = 'Y'` 조건이 들어간 것이었습니다.
그 컬럼은 **페르소나 존재 여부가 아니라 탈퇴 플래그**입니다.
탈퇴하면 `N`이 되므로 **과거에 페르소나를 만든 사람도 탈퇴하면 분자에서 빠집니다.**

분모(전체 가입)는 그대로인데 분자만 줄어드니 시간이 갈수록 전환율이 떨어집니다.

```
지표가 나빠 보이는 이유가 「전환이 안 돼서」가 아니라 「탈퇴자가 쌓여서」였다
```

**규칙** — 코호트 지표의 분자에는 현재 상태 플래그(`use_yn`, `status`)를 쓰지 않습니다.
분모도 소급해서 줄어들면 안 됩니다.

같은 종류의 오염을 리텐션에서도 찾았습니다. 성별조차 없는 껍데기 계정 86명이 분모에 섞여 있었고,
빼고 보니 재방문율이 38.0% → 47.8% 로 달라졌습니다.
**지표가 나쁜 것이 아니라 분모가 오염돼 있었습니다.**

> 인접 사례: `troubleshooting.md` §12 — "알림 거부율 67%"는 측정 오류였다

## G-2. 부분 증거로 단정하지 않는다

같은 날 두 번 틀렸습니다.

**하나** — 이미지 캐시 히트율이 5% 인 것을 보고 "앱이 캐시를 안 쓴다"고 판단했습니다.
틀렸습니다. nginx 가 `Cache-Control: immutable`을 주고 있는데, 그 세만틱은
**조건부 요청 자체를 보내지 말라**는 뜻입니다(RFC 8246). 캐시가 잘 도는 클라이언트는
304 를 만드는 게 아니라 **요청을 안 보냅니다.** 304 비율은 애초에 지표가 못 됩니다.

제대로 재는 방법은 "같은 기기가 같은 URL 에 200 을 반복해서 받는가"였고,
그렇게 재니 재다운로드가 iOS 669건 · 안드로이드 7건으로 **플랫폼이 완전히 갈렸습니다.**

**둘** — 그 재다운로드를 파다가 한 기기의 타임스탬프 몇 개에서 "같은 사진을 3초 만에,
같은 초에 두 번" 받은 것을 보고 "용량 밀림이 아니라 중복 요청"이라고 판단했습니다.
전수로 세어 보니 1초 이내는 **47건(7%)** 이었습니다. 나머지 93% 는 용량 가설과 모순되지 않았습니다.

**패턴이 같습니다** — 눈에 띄는 몇 건을 보고 전체를 설명하려 했습니다.
그럴듯한 가설이 먼저 떠올랐을 때가 가장 위험합니다.
**반대 가설을 죽일 데이터를 먼저 세야 합니다.**

**B-1 · B-2 · C-3 · A-2 는 같은 날 실제로 코드를 고친 것들입니다.**
단건 테스트로는 전부 정상이었고, 동시 요청을 쳐 보고서야 드러났습니다.

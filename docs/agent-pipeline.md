# AI 에이전트 개발 파이프라인 구축기 — 이슈 하나가 사람 손 없이 PR 과 검증까지

> 2026-10-15. 「서비스 개발을 AI 에이전트로 자동화하자」는 요구를 받고, 하루 만에 **이슈 → 구현 에이전트 → 검증 에이전트 → 사람 승인**
> 한 바퀴를 실제로 돌린 기록이다. 결론부터: 구현 1분 40초, 검증 2분, 사람이 누른 건 머지 버튼 하나. 그리고 그 하루의 대부분은
> 에이전트가 아니라 **인증·브랜치·셸 환경** 같은 바닥 공사에 들어갔다.

> FE 줄기(실기기 점검 러너·출시 파이프라인·AOS/iOS 판정)는 fe 브랜치 [`docs/agent-qa-runner.md`](https://github.com/eomheeseung/mildo_eomheeseung/blob/fe/docs/agent-qa-runner.md) 에 있다.

## 1. 요구와 현실 — 「전부 자동화」는 어디까지 가능한가

대표의 요구는 PM·BE·FE·테스트·CS 에이전트를 두고 서비스 운영을 통째로 맡기는 것이었다. 먼저 해외 사례를 조사했다.

- 가장 앞선 실험(노트앱 「Software Factory」, Devin 연간 리뷰, Anthropic Project Vend)도 **사람이 결정하고 승인하는 반자동**에서 멈춰 있다.
  Devin 의 PR 머지율은 벤더 수치로 67%, 외부 시험은 20개 중 3개 성공.
- 완전 자동을 시도한 곳은 데이터를 잃었다. 코딩 에이전트가 운영 DB 를 지운 사고가 2025~2026 년에 9건, 공통 원인은 모델이 아니라 **접근 권한**이었다.
- 그래서 설계 원칙을 셋으로 잡았다. ① 되돌릴 수 없는 지점(운영 배포·돈·회원 발송·DB)에만 사람 게이트 ② 금지는 프롬프트가 아니라 **권한**으로
  ③ 에이전트가 쓰는 기계에는 운영 접근 수단을 두지 않는다.

같이 나온 요구가 「컴파일 때문에 Spring 이 자동화에 불리하니 스크립트 언어로 바꾸자」였다. 조사 결과 컴파일·타입 검사는 에이전트가 낸
틀린 코드를 실행 전에 잡는 **검증 장치**였고(한 분석에서 진단 통과를 완료 조건으로 강제하자 틀린 코드 수용률 90% → 8%), 언어 재작성은
에이전트 벤치마크에서 가장 못 하는 작업(SWE Refactor Bench 5.6점)이었다. 언어는 그대로 두고 **검증 체계**를 만드는 쪽으로 정했다.

## 2. 설계 — 역할·보드·게이트

```
사람: 이슈 작성 ──▶ agent:준비 완료
                        │  (GitHub Actions, issues.labeled → self-hosted 러너)
                        ▼
              BE 에이전트  claude -p + 역할 지시문
              브랜치 → 구현 → 컴파일·테스트 → 커밋 → PR → 이슈 댓글(## 결과)
                        │  agent:BE 완료
                        ▼
              QA 에이전트  브랜치 jar 빌드 → 스테이징 재기동 → 테스트 계정 초기화
              → 변경 API 를 명세와 curl 대조 → 핵심 API 회귀 → 이슈 댓글(## 판정)
                        │  agent:승인 대기
                        ▼
사람: PR 캡처·댓글 보고 머지 ──▶ agent:출시
```

- **보드는 GitHub Issues 라벨**이다. `명세 → 준비 완료 → BE 작업 → BE 완료 → FE 작업 → QA → 승인 대기 → 출시`, 막히면 `막힘`,
  `전체 정지` 라벨이 열린 이슈에 하나라도 있으면 모든 에이전트가 멈춘다. 별도 도구를 안 들인 이유는 PR·댓글·라벨이 이미 한곳에 있어서다.
- **역할 지시문은 파일**(`scripts/agent/roles/*.md`)이고, 진입점 스크립트가 「이슈 본문 + 지시문」을 `claude -p` 에 넣는다.
  도구는 `--allowedTools` 로 파일 편집·git·mvn·curl 만 허용했다. 마지막 출력의 `## 결과:` 블록이 그대로 이슈 댓글이 되고,
  그 제목 줄로 다음 라벨을 정한다.
- 지시문에 박은 규칙: API 응답 형태·에러코드 불변, 새 엔드포인트는 v2, 명세가 애매하면 **추측하지 말고 「질문」으로 멈춤**,
  같은 오류 2회면 3회째 없이 「막힘」, 돈·DB 스키마·푸시 라우팅은 초안까지만. 이 규칙은 사람 세션용 CLAUDE.md 에도 「에이전트 사규」로 같이 넣었다.

## 3. 사무실 — 러너 한 대에 스테이징까지

에이전트가 도는 기계는 사무실의 Mac mini 한 대다. iOS 빌드까지 한 대에서 하려면 macOS 여야 했고, 스테이징 서버를 따로 두지 않고
이 안에서 해결했다.

- **스테이징 프로파일**을 새로 만들었다. 로컬 프로파일은 푸시·메일이 실제로 나가서(실제 FCM 키·실제 토큰) 에이전트가 테스트하다
  회원 폰으로 보낼 수 있다. `firebase.enabled=false`, 메일 서비스에 `enabled` 플래그를 추가해 로그만 남기게 했고, 광고 수집도 껐다.
  DB 는 Docker MySQL 에 로컬 복사본을 넣었다.
- **테스트 계정 초기화 API** — 점검을 반복하면 테스트 계정에 매칭 신청·대화방·알림이 쌓여 다음 회차가 같은 화면을 못 본다.
  `POST /v2/dev/reset?userIds=…&berries=100` 이 두 계정을 「서로 아무 관계 없고 베리 100개」로 되돌린다. 테스트 계정이 아니면 400.
  나간 방·닫힌 방까지 지워야 해서 전용 조회를 하나 추가했다.
- **알림 종류별 발사 API** — 매칭 신청/수락/거절, 관심, 피드 관심/댓글/답글, 랜덤TALK 만료까지 dev 엔드포인트로 쏠 수 있게 했다.
  실기기 점검 러너가 「알림 탭 → 어느 화면으로 가는가」를 종류별로 돌릴 수 있어야 해서다.
- 운영 서버 ssh 키·운영 설정 파일은 이 기계에 **없다**. 운영 배포는 지금처럼 사람이 자기 PC 에서 한다.

## 4. 밟은 함정 — 하루의 대부분

| 증상 | 원인 | 해결 |
|---|---|---|
| 라벨을 붙여도 러너가 조용함 | GitHub 는 `issues` 이벤트에 **기본 브랜치의 워크플로**만 실행한다. 워크플로는 작업 브랜치에만 있었다 | 기본 브랜치를 작업 브랜치로 바꿈(옛 main 은 아카이브) |
| 잡이 12초 만에 「성공」 | 러너 세션이 macOS **키체인을 못 읽어** `gh` 가 401 → 「전체 정지」 검사가 오류를 0건으로 읽고 중단 | 인증 실패를 조용히 넘기지 않게 바꾸고, 토큰을 환경변수로 |
| 시크릿을 넣었는데 비어 있음 | 시크릿 등록 위치·이름 불일치가 반복됨. 그때마다 사람이 라벨을 떼었다 붙여야 했다 | 토큰을 **기계 로컬 파일**(`~/.config/…/env`, 600)에 두고 스크립트가 읽게. 이후엔 ssh 로 직접 재실행 가능 |
| QA 가 「통과」인데 라벨은 「막힘」 | 에이전트가 요약 제목을 영어(`## Verdict: Pass`)로 써서 패턴이 빗나감 | 지시문에 한국어 제목을 강제하고 스크립트는 영어 변형도 인식 |
| 스테이징에 로그가 한 줄도 없음 | logback 에 local·prod 프로파일만 루트 로거가 있어 staging 은 아무것도 안 찍혔다. 그래서 「메일이 안 나갔는지」를 확인할 수 없었다 | `springProfile name="local, staging"` |
| 기계에서 `git pull` 거부 | `chmod +x` 가 git 에는 수정으로 잡힘 | 실행 비트를 커밋(`update-index --chmod=+x`) |
| 러너 셸에 `mvn`·`claude` 없음 | LaunchAgent 셸은 로그인 셸이 아니라 PATH 가 비어 있다 | 스크립트 첫 줄에서 PATH·JAVA_HOME 직접 지정 |
| 「다른 클라이언트가 점검 중 스테이징을 썼다」 | QA 에이전트가 로그에서 자기 것이 아닌 로그인·초기화를 발견해 지적 | 다음 과제: QA 실행 중 스테이징 잠금 |

마지막 행은 에이전트가 **스스로 발견해 판정에 적은 것**이다. 지시문에 없던 관찰이었다.

## 5. 첫 실행 결과

시험 이슈: 「로컬·스테이징 전용 `GET /v2/dev/ping` 추가, 인증 필요, 테스트 1개」.

- **BE 에이전트, 1분 40초.** 컨트롤러·테스트·명세 문서(URI·응답 JSON·필드 표·실패 표·분기 처리) 작성, 관련 테스트 1건 그린,
  커밋·PR, 이슈 댓글에 「바꾼 것·검증·FE 영향 없음·명세 경로·푸시는 아직 안 함」까지. 보안 설정은 건드리지 않고 기존 인증을 그대로 탔다.
- **QA 에이전트, 2분.** 빌드·재기동 16초, 계정 초기화, 토큰 있음/없음/잘못됨 세 경우를 명세와 대조(200/401/401), 핵심 API 5개 회귀 200,
  로그 ERROR 2건 중 1건은 자기 테스트·1건은 외부 클라이언트로 분리해 적음. 「운영 404 는 운영을 건드리면 안 되니 안 했다」고 명시.
- 사람: PR 을 보고 머지. 라벨 `출시`, 이슈 자동 닫힘.

시험용 엔드포인트는 소스를 깨끗하게 두려고 머지 직후 되돌렸다.

## 6. 남은 것과 솔직한 평가

- 이번 PoC 는 **실행의 반쪽**이다. 이슈는 사람이 썼다. 대표가 원하는 건 「요청조차 스스로 파악하기」이고, 그건 운영 지표(응답률·5왕복 도달·
  오류·느린 API·문의)를 매일 읽어 이상 항목을 이슈 초안으로 올리는 **기획 에이전트**다. 지표 수집은 운영 서버에서 읽기 전용으로 뽑아
  JSON 만 넘긴다 — 러너에 운영 접근을 주지 않는 원칙은 유지한다.
- FE 줄기는 다른 문제를 안고 있다. 스크립트형 E2E 는 팝업·기기 상태 때문에 과거에 효과가 없었고, 대신 에이전트가 실기기를
  adb 로 조작하며 점검 목록을 도는 방식을 표준으로 잡았다. 사람보다 느리지만(동작당 10~30초 vs 2~3초) 상황 재현·반복·원인 분석에서 이긴다.
- 「자동화됐다」의 기준은 숫자로 못 박았다: 한 달 동안 PR 70% 무수정 머지, 문의 70% 사람 없이 종결, 배포 후 장애 0.
- 하루를 돌아보면 에이전트 자체는 거의 손이 안 갔다. 시간을 먹은 건 **인증이 어느 세션에서 보이는가, 워크플로가 어느 브랜치에서 읽히는가,
  셸에 무엇이 있는가** 였다. 자동화의 바닥은 모델이 아니라 환경이다.

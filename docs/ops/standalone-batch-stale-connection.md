# 연결 풀 밖에서 돈 백필 프로그램의 끊김 — 준비한 문장을 쥔 채 쉬면 세션이 죽는다

**이 서비스(밀도)가 아니라 사내 다른 프로젝트의 작업입니다.** CUBRID 를 쓰는 운영 시스템에서 기존 데이터를 채우는
일회성 백필(backfill) 프로그램이 중간에 죽었습니다. 개발 서버에서 재현해 원인을 확정했고, 같은 일이 밀도에서는 왜
프로그램이 죽는 데까지 가지 않는지 비교해 정리합니다.

이 문서가 짚는 것은 세 가지입니다.
- **연결 풀이 해 주던 일은 풀 밖에서는 아무도 안 해 준다.** 애플리케이션 서버 안에서는 당연했던 「쓰기 전 확인·죽은 연결 교체」가, 따로 띄운 배치 프로그램에는 없습니다.
- **DB 는 쉬는 세션을 끊는다.** DBMS 마다 기준과 조건이 다를 뿐, 오래 쉰 연결이 살아 있다는 보장은 어디에도 없습니다.
- **「한 번 준비해 반복 실행」은 정석이지만, DB 와 상관없는 긴 공백이 끼면 성능 이득 없이 위험만 남는다.**

---

## 1. 무슨 일이 있었나

- 첨부 파일 상세 테이블의 `file_size` 를 실제 파일 크기로 채우는 백필 프로그램입니다. 대상 23,111건입니다.
- 각 건마다 NAS 의 파일을 확인해 이미 처리된 건이면 건너뛰고, 아니면 UPDATE 합니다. 자동 커밋을 켜고 건마다 커밋합니다.
- 실행 도중 아래 예외로 프로그램 전체가 멈췄습니다.

```
CUBRIDException: Cannot communicate with the broker or received invalid packet
```

처음에는 잠금 대기나 쿼리 시간 초과를 의심하기 쉽습니다. 하지만 오류 문구가 둘 다 아니었고, 죽은 자리도 UPDATE 가
아니었습니다. **쉬었다가 처음 DB 를 다시 쓰는 곳(다음 단계 SELECT 를 준비하는 순간)** 이었습니다.

## 2. 코드 — 옛 판

```java
PreparedStatement upd = c.prepareStatement(
    "UPDATE atch_file_dtl SET file_size = ? WHERE atch_file_no = ? AND file_ordr = ? AND reger_id = ?");
                                         // 반복문 밖에서 한 번 준비 → 끝까지 쥔다
for (Target t : list) {                  // 23,111건
    if (alreadyDone(t)) continue;        // NAS 파일만 확인, DB 요청 없음
    upd.setLong(1, size);
    upd.setLong(2, t.fileNo());
    upd.setInt(3, t.order());
    upd.setString(4, t.regerId());
    upd.executeUpdate();
}
upd.close();                             // 다 끝나야 반납
```

교과서적인 JDBC 패턴입니다. 그런데 이번 실행에서는 **앞쪽 약 13,000건이 전부 「이미 처리됨」** 이었습니다.
그 구간은 파일만 확인하고 넘어가서 **5분 36초 동안 DB 요청이 0건**이었습니다.

## 3. 개념 — CUBRID 의 연결은 「브로커 세션」이다

MySQL·MariaDB 는 애플리케이션이 DB 서버와 직접 TCP 연결을 맺습니다. CUBRID 는 중간에 한 층이 더 있습니다.

```
애플리케이션(JDBC 드라이버) ──▶ 브로커 ──▶ CAS(작업 프로세스) ──▶ DB 서버
```

- **브로커**는 요청을 받아 CAS 에 배정하는 중계 프로세스입니다. **CAS** 가 실제로 DB 서버와 대화합니다.
- 애플리케이션 입장의 「연결」은 이 **브로커 세션**입니다. **준비한 문장(prepared statement)의 핸들도 이 세션에 묶여** 있습니다.
- 브로커는 쉬는 세션을 일정 시간 뒤 정리합니다(`SESSION_TIMEOUT`, 개발 서버 300초).

여기서 차이가 생깁니다.
- **아무것도 쥐고 있지 않은 세션**은 정리돼도 잃을 상태가 없습니다. 다음 요청 때 드라이버가 새로 붙으면 그만입니다.
- **준비한 문장을 쥔 세션**은 그 문장 핸들이 서버 쪽에서 사라집니다. 클라이언트는 여전히 그 연결과 문장이 유효하다고 믿고 쓰다가 통신 오류를 만납니다. 이른바 **낡은 연결(stale connection)** 입니다.

## 4. 재현 — 조건을 하나씩 바꿔 확정

개발 서버(운영과 같은 JDBC 드라이버 버전, 자동 커밋 켬)에서 프로세스를 멈춰(SIGSTOP) 쉬는 시간을 만들었습니다.

| 조건 | 결과 |
|---|---|
| 문장을 쥔 채 330초 쉼 | **끊김** (운영과 같은 오류 문구) |
| 문장 없이 330초 쉼 | 정상 |
| 문장을 쥔 채 200초 쉼 | 정상 |
| 330초 걸리는 쿼리 1개 실행 | 정상 |
| 옛 판 그대로 330초 멈춤 | 운영과 같은 호출 스택으로 죽음 |

- 「오래 걸리는 쿼리」는 문제가 아니었습니다. 일하는 중인 세션은 끊기지 않습니다.
- 「오래 쉼」만으로도 문제가 아니었습니다. 쥔 것이 없으면 다시 붙습니다.
- **「문장을 쥔 채 세션 한도보다 오래 쉼」** 두 조건이 겹칠 때만 끊겼습니다.

운영 브로커의 실제 한도는 확인하지 못했습니다. 다만 5분 36초에서 끊긴 것으로 보아 300초 근처로 추정합니다.

## 5. 일반화 — 쉬는 연결은 어느 DB 에서든 죽을 수 있다

이번 일은 CUBRID 의 브로커 구조 탓으로만 볼 일이 아닙니다. 끊는 주체와 기준이 다를 뿐 같은 종류의 일은 어디서든 납니다.

- **DB 서버의 유휴 한도**: MySQL·MariaDB 는 `wait_timeout` 이 지나면 쉬는 연결을 끊습니다. 밀도가 쓰는 공용 MariaDB 는 이 값이 60초입니다.
- **중간 네트워크 장비**: 방화벽·NAT 는 조용한 TCP 연결을 표에서 지웁니다. 양쪽 다 연결이 살아 있다고 믿는 채로 패킷만 버려집니다.
- **DB 재시작·장애 조치**: 연결이 통째로 사라집니다.

그래서 「연결은 언제든 죽어 있을 수 있다」를 전제로 두 가지 방어 중 하나는 있어야 합니다.

1. **짧게 빌리고 바로 돌려준다.** 쓸 때 준비하고 쓰고 닫습니다. 쥐고 있는 게 없으면 끊겨도 잃을 게 없습니다.
2. **쓰기 전에 확인하고, 죽었으면 바꾼다.** `SELECT 1` 같은 확인 쿼리나 주기적 keepalive 로 연결을 살려 두거나, 죽은 연결을 새 것으로 교체합니다.

## 6. 연결 풀이 해 주던 일 — 풀 밖에서는 아무도 안 한다

웹 애플리케이션 안에서 이 문제를 거의 겪지 않는 이유는 **연결 풀**이 위 방어를 대신 해 주기 때문입니다.

| 풀이 하는 일 | 효과 |
|---|---|
| 꺼내 주기 전 유효성 확인 | 죽은 연결을 애플리케이션에 넘기지 않음 |
| 쉬는 연결에 주기적 keepalive | DB·방화벽의 유휴 한도에 걸리지 않음 |
| 최대 수명(max lifetime) 지나면 폐기 | 서버가 끊기 전에 풀이 먼저 교체 |
| 요청 단위로 빌리고 반납 | 연결을 오래 쥐는 코드가 구조적으로 드묾 |

이번 백필은 애플리케이션 서버 밖에서 `main()` 으로 띄운 독립 프로그램이었습니다. 연결 하나를 직접 열어 끝까지 썼고,
**위 네 가지를 하나도 받지 못한 맨몸 연결**이었습니다. 운영 웹 화면에서는 같은 DB 를 몇 년째 문제없이 쓰고 있었기 때문에,
그 보호가 풀에서 온다는 걸 의식하지 못한 것이 진짜 원인입니다.

## 7. 밀도와 비교

밀도도 같은 종류의 문제를 겪었습니다. 공용 MariaDB 의 `wait_timeout` 이 60초인데, 연결 풀(HikariCP)의 keepalive 주기도
60초라 둘이 정확히 겹쳤습니다. 가끔 이미 끊긴 연결을 꺼내 써서 하루 몇 건씩 응답이 수십 초 걸리거나 500 이 났습니다.
그래도 **풀이 그 연결을 버리고 새것을 줘서 요청 한 건만 실패**했고, 서비스가 멈추지는 않았습니다. 이후 설정을 이렇게 바꿨습니다.

```yaml
hikari:
  keepalive-time: 30000                           # DB 유휴 한도(60초)의 절반 — 확인 신호가 항상 먼저 도착
  connection-init-sql: SET SESSION wait_timeout=600  # 이 연결의 서버 쪽 한도를 600초로
  max-lifetime: 570000                            # 서버 한도(600초)보다 먼저 풀이 스스로 교체
```

| | 밀도 (풀 안) | 백필 옛 판 (풀 밖) |
|---|---|---|
| 연결 관리 | HikariCP, 요청마다 빌리고 반납 | `main()` 에서 연 연결 1개를 끝까지 |
| 쉬는 동안 | 30초마다 keepalive | 아무 확인 없이 5분 36초 |
| 끊겼을 때 | 풀이 폐기하고 새 연결 | 예외 → 프로그램 종료 |
| 준비한 문장 | JPA 가 요청마다 준비하고 닫음 | 반복문 밖에서 준비해 끝까지 쥠 |

밀도도 **앱 밖에서 따로 도는 스크립트**(운영 데이터 정리, 이관 도구)를 짜면 똑같이 맨몸이 됩니다. 「앱에서는 괜찮았다」는
그 스크립트의 안전을 보장하지 않습니다. 연결을 오래 쥐는 다른 경우는 [트러블슈팅 §18](./troubleshooting.md) 의
「AI 응답을 기다리는 40초 동안 DB 커넥션을 붙잡고 있던 것」과 같은 뿌리입니다.

## 8. 수정 — 새 판

```java
for (Target t : list) {
    if (alreadyDone(t)) continue;
    try (PreparedStatement upd = c.prepareStatement("UPDATE … ?")) {   // 쓸 때 준비
        upd.set…(…);
        upd.executeUpdate();
    }                                                                  // 바로 닫음
}
// + Connection 을 감싸서, 60초 넘게 안 쓴 뒤 문장을 만들 때 SELECT 1 로 확인하고
//   끊겼으면 새로 연결한다 — 풀의 「꺼내기 전 유효성 확인」을 직접 구현
```

- 둘 중 **하나만 했어도** 이번 오류는 나지 않았습니다. 첫째는 쥔 것을 없애고, 둘째는 끊긴 연결을 쓰지 않습니다.
- 둘 다 넣은 이유는 둘째가 방화벽 끊김·DB 재시작 같은 다른 경우까지 막기 때문입니다.
- 개발 서버에서 「330초 멈춤」과 「브로커 재시작」 두 시험을 모두 끝까지 처리했고, 재연결 경로가 실제로 타는 것도 로그로 확인했습니다.

## 9. 준비를 아낀 성능 이득은 있었나

「한 번 준비해 반복 실행」은 파싱·실행계획 비용을 아끼려는 정석입니다. 이번에는 그 이득이 거의 없었습니다.

- CUBRID 는 서버가 **같은 SQL 문장의 실행계획을 캐시**합니다. 반복문 안에서 매번 준비해도 캐시를 다시 쓰므로, 추가 비용은 왕복 한 번 정도입니다.
- 실제 UPDATE 는 약 1만 건이었고, 실행 시간 대부분은 **NAS 파일 확인**이었습니다. 병목이 DB 가 아니었습니다.

DB 쓰기를 정말 빠르게 하고 싶다면, 문장을 오래 쥐기보다 **수백 건씩 묶어 한 번에 보내는 편**(`addBatch` / `executeBatch`)이
효과도 크고 연결을 쥐는 시간도 짧습니다. 자원 수명은 실제로 쓰는 구간에 맞추고, 최적화는 병목을 잰 뒤에 합니다.

## 10. 독립 배치 프로그램 체크리스트

- [ ] 연결을 직접 여는가? 그렇다면 풀이 해 주던 확인·교체를 누가 하는지 정했는가
- [ ] 반복문 안에 DB 와 상관없는 긴 작업(파일·외부 API·대기)이 끼는가? 그 동안 연결·문장을 쥐고 있지 않은가
- [ ] 쉬었다가 다시 쓰기 전에 연결을 확인하거나, 실패 시 재연결 후 그 건부터 이어 갈 수 있는가
- [ ] 중간에 죽어도 다시 돌리면 이어서 처리되는가(이미 처리한 건을 건너뛰는 멱등성) — 이번 백필은 이게 있어서 재실행이 안전했습니다
- [ ] 대상 DB 의 유휴 한도(`wait_timeout`, 브로커 세션 한도 등)를 알고 있는가

## 11. 정리

- **오류 문구가 원인을 가리킨다.** 잠금 대기도 쿼리 시간 초과도 아닌 「브로커와 통신 불가」는 연결 자체가 죽었다는 뜻이었고, 죽은 자리도 쉬고 난 첫 DB 호출이었습니다.
- **연결의 생존은 보장되지 않는다.** DB·브로커·네트워크 장비 모두 쉬는 연결을 끊습니다. DBMS 마다 다른 것은 기준과 조건뿐입니다.
- **풀이 숨겨 주던 문제는 풀 밖에서 드러난다.** 같은 DB 를 웹에서 오래 문제없이 썼다는 사실이 독립 프로그램의 안전을 말해 주지 않습니다.
- **자원은 쓰는 동안만 쥔다.** 짧게 빌리고 바로 돌려주거나, 쓰기 전에 확인하고 교체한다. 둘 중 하나면 이번 일은 없었습니다.

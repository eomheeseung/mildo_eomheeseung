# 공용 DB 이웃 서비스의 DELETE 분석 — 요구사항을 그대로 옮긴 WHERE 와 옵티마이저의 비용 오판

**우리 서비스의 코드가 아닙니다.** 같은 공용 DB 인스턴스를 쓰는 **다른 사내 서비스**의 주간 배치 쿼리입니다.
그 쿼리 때문에 우리 서비스를 포함한 공용 DB 전체의 쓰기가 두 번 멈췄습니다. 원인을 분석해 측정값과 수정안을
정리했고, 이후 그 배치를 직접 맡게 되어 **수정 반영과 밀린 데이터 정리(934만 건)까지** 했습니다(§4-1, §5-1).

우리가 겪은 일이 아니라서 [트러블슈팅](./troubleshooting.md)과 [실제로 밟은 함정](./pitfalls.md)에는 넣지 않았습니다.
그래도 **「논리적으로 맞는 쿼리가 실행계획 때문에 수백 배 느려지는」** 전형적인 사례라 따로 정리합니다.

이 문서가 짚는 것은 두 가지입니다.
- **WHERE 를 요구사항 그대로 옮기는 것과, DB 가 그 조건을 어떤 순서로 찾아가는지는 별개다.** 같은 결과를 내는 조건이라도 쓰는 방식에 따라 타는 인덱스와 반복 비용이 완전히 달라집니다. 이건 문법이 아니라 **접근 경로를 설계하는 알고리즘 문제**입니다.
- **옵티마이저의 비용 오판.** 범위 조건 + `LIMIT` 조합에서 옵티마이저가 「곧 끝난다」고 비용을 잘못 추정해 엉뚱한 인덱스를 고릅니다.

---

## 1. 무슨 일이 있었나

- 두 주 연속 토요일 00:30 무렵부터 약 50분 동안, 공용 DB 를 쓰는 서비스들의 **쓰기만** 멈췄습니다. 읽기는 됐습니다.
- 우리 서비스에서는 로그인·저장·출석이 실패했습니다.

운영 DB 는 호스팅사가 관리하는 MariaDB 한 대를 여러 사내 서비스가 나눠 쓰는 공용 인스턴스입니다.
그래서 **남의 쿼리가 내 장애**가 될 수 있습니다.

## 2. 규명 — 멈춰 있는 동안 processlist 를 떴다

```
[이웃 서비스] DELETE … LIMIT 10000        ← 수백 초째 실행 중 (실측 573초 이상)
[호스팅 백업] FLUSH TABLES WITH READ LOCK  ← 위 문장이 끝나야 전역 잠금을 얻는다 → 대기
[우리 · 다른 서비스들] INSERT / UPDATE …   ← 「Waiting for backup lock」 줄줄이
```

- 백업은 시작할 때 전역 읽기 잠금(`FLUSH TABLES WITH READ LOCK`)이 필요합니다. 실행 중인 문장이 끝나야 이 잠금을 얻습니다.
- **잠금을 기다리는 동안에도** 그 뒤로 오는 모든 쓰기가 줄을 섭니다. 그래서 문장 하나가 오래 걸리면 인스턴스 전체의 쓰기가 멈춥니다.
- 원인 문장은 이웃 서비스가 금요일 밤에 돌리는 배치였습니다.
  - 매주 더미 데이터 200만 건을 넣습니다.
  - 2회차 지난 더미를 `DELETE … LIMIT 10000` 으로 1만 건씩 지웁니다.
  - 이 한 문장이 수 분씩 걸리면서 토요일 00:30 백업과 겹쳤습니다.
- slow log·binlog·performance_schema 가 꺼진 인스턴스라 지나간 일은 볼 수 없었습니다. **멈춘 그 순간 processlist 를 떠 둔 것**이 유일한 증거였습니다.
- 당일에는 그 배치의 요청과 남은 DELETE 세션을 끊어 잠금 줄을 풀었습니다.

## 3. 그 DELETE 는 왜 느렸나

```sql
DELETE FROM saved_numbers
WHERE round <= 1241               -- 회차 (범위)
  AND rank IS NULL                -- 당첨 등수 없음 = 꽝
  AND user_id BETWEEN 1 AND 100   -- 더미 유저
LIMIT 10000;
```

`round` 는 회차, `rank` 는 당첨 등수 칼럼입니다. 최근 2회차와 당첨 행은 남겨야 하고, 그 이전 회차의 꽝 더미만 지웁니다.

인덱스는 둘이 있었습니다.
- `idx_user_id (user_id)`
- 복합 인덱스 `idx_round_rank (round, rank)`

```
EXPLAIN:  type=range  key=idx_user_id  used_key_parts=[user_id]  rows=5,720,910  filtered=100  Extra=Using where
```

### 3-0. 왜 이렇게 쓰게 되나 — 요구사항을 그대로 옮긴 WHERE

요구사항은 「2회차 지난 + 꽝 + 더미 유저의 행을 지운다」입니다. 이걸 그대로 옮기면 위 쿼리가 됩니다.
조건 하나하나가 요구사항과 1:1 로 맞고, 결과도 틀린 데가 없습니다. 「더미 유저가 대상이니 `user_id` 인덱스로 찾으면 된다」는 생각도 자연스럽습니다.

문제는 이 쿼리가 **한 번이 아니라 1만 건씩 수백 번 반복**된다는 점입니다. 반복될 때 무엇이 남고 무엇이 사라지는지를 따져야 합니다.

- 지우는 행: 오래된 회차의 꽝 → 매 배치 사라집니다.
- 남는 행: 최근 2회차와 당첨 행 → 회원마다 계속 남습니다.
- `user_id` 순서로 찾으면 남는 행이 **찾는 길 앞쪽에 계속 쌓입니다.** 그래서 반복할수록 헛걸음이 늘어납니다.
- `(회차, 등수)` 순서로 찾으면 남는 행은 **다른 칸**에 있어 찾는 길에 끼지 않습니다. 반복해도 매번 같은 양만 읽습니다.

즉 「어떤 조건으로 거르나」보다 **「반복할 때 남는 데이터가 찾는 길을 막지 않는가」**를 봐야 하는 문제입니다.
데이터가 작을 때는 둘 다 빨라서 차이가 안 보이고, 남는 행이 쌓인 뒤에야 드러납니다.

### 3-1. 복합 인덱스는 앞 칼럼이 `=` 일 때만 뒤 칼럼까지 쓴다

복합 인덱스는 전화번호부처럼 `round` 로 먼저, 같은 `round` 안에서 `rank` 로 정렬돼 있습니다.

```
(1237,NULL)(1237,NULL)…(1237,3)  (1238,NULL)…(1238,4)  …  (1241,NULL)(1241,NULL)…(1241,2)
```

- `round = 1241 AND rank IS NULL` 이면 `(1241,NULL)` 묶음의 시작점으로 바로 갑니다. 두 칼럼을 다 씁니다.
- `round <= 1241 AND rank IS NULL` 이면 여러 회차가 섞인 구간이라 `rank IS NULL` 끼리 붙어 있지 않습니다.
  인덱스로는 `round` 범위만 좁히고 `rank` 는 하나씩 봐야 합니다. 그런데 그 범위가 **테이블 거의 전체**입니다.

### 3-2. 옵티마이저의 비용 오판 — LIMIT 이 붙으면 비용을 너무 싸게 잡는다

- `round` 쪽 범위가 넓어 보이니 옵티마이저는 `idx_user_id`(더미 유저 572만 행)를 고릅니다.
- 572만 행도 많지만, **`LIMIT 10000` 이 있으니 조건에 맞는 행이 고르게 섞여 있다고 가정하고 「1만 행쯤 읽으면 끝난다」고 판단**합니다. `filtered=100` 이 그 가정입니다.

실제로는 고르게 섞여 있지 않습니다. 회원별 인덱스를 따라가면 회원마다 **남겨야 할 행(최근 회차·당첨)** 이 그대로 남아 있습니다.
그래서 매 배치가 **이미 정리한 회원들의 남길 행을 처음부터 다시 훑은 뒤에야** 지울 행을 만납니다.

```
배치 1 : [user1 지울 행 1만]                                      → 끝
배치 2 : [user1 남길 행 4만 통과] [user2 지울 행 1만]               → 끝
배치 k : [남길 행 4만 × (k-1) 통과] [지울 행 1만]
```

- DELETE 한 번 한 번이 독립된 문장이라, DB 는 「지난번에 user 1 까지 정리했다」는 걸 기억하지 않습니다.
- `round`·`rank` 는 `idx_user_id` 에 없으니, 지나치는 행마다 본체까지 찾아가 확인하는 비용이 붙습니다.
- 배치 하나의 시간은 일정하게 늘고(산술급수), **전체 시간은 배치 수의 제곱**으로 늘어납니다.
- 배치 로그를 보면 1만 건당 55초에서 355~460초까지 계속 늘었습니다.
- 느려서 실패하면 삭제를 건너뛰는 코드라 못 지운 행이 쌓였고, 그래서 다음 주가 더 느려지는 악순환이었습니다. 매주 200만 건을 넣는데 60만 건 남짓만 지워졌습니다.

### 3-3. 그렇다고 LIMIT 을 빼면 더 나빠진다

같은 조건에서 `LIMIT` 을 빼면 옵티마이저는 「어차피 다 읽는다」고 보고 테이블 전체 읽기(rows 1,141만)를 고릅니다.

## 4. 수정안 — 범위를 쪼개 `=` 로 묻고, 반복은 애플리케이션이 한다

```sql
-- MIN(round) 부터 기준 회차까지, 회차마다 (반복은 애플리케이션 코드):
DELETE FROM saved_numbers
WHERE round = {회차} AND rank IS NULL AND user_id BETWEEN 1 AND 100
LIMIT 10000;      -- 1만 건 지워지면 같은 회차 다시, 아니면 다음 회차
```

- 지우는 대상은 `round <= 1241` 과 같습니다. 달라지는 건 DB 가 고르는 길뿐입니다.
- `(round, rank)` 를 둘 다 써서 지울 행만 읽습니다(`r_rows=10,000`, `r_filtered=100%`).
- 지운 행은 인덱스에서도 빠지니, 다음 배치도 헛읽기 없이 시작합니다.
- **새 인덱스는 필요 없었습니다.** 1,144만 행 테이블에 인덱스를 더하는 작업과 매주 200만 건 INSERT 마다 늘어나는 갱신 비용을 피했습니다.
- `round = 기준회차` 하나만 지우지 않고 `MIN(round)` 부터 도는 이유가 있습니다. 어느 주에 실패해도 남은 회차를 다음 주에 이어서 지우기 위해서입니다. 지울 게 없는 회차는 0.00001초에 끝나서 반복 비용은 무시할 수 있습니다.

### 4-1. `=` 로도 부족했다 — 데이터가 줄자 옵티마이저가 다시 틀렸다

밀린 데이터를 정리하던 중, 테이블이 1,144만 행에서 489만 행으로 줄자 **같은 `round = 1242` 쿼리가 다시 `idx_user_id` 를 골랐습니다.**

```
round = 1241 :  key=idx_round_rank   rows=1          ← 정리 전 (회차 하나가 테이블의 작은 일부)
round = 1242 :  key=idx_user_id      rows=2,442,895  ← 정리 후 (회차 하나가 테이블의 30%)
```

- 회차 하나가 테이블에서 차지하는 비중이 커지자, 옵티마이저가 「회차 인덱스로 찾아도 많이 읽는다」고 보고 다시 유저 인덱스로 돌아갔습니다.
- 매주 회차 하나가 200만 건이니, 정상 운영 상태에서도 같은 일이 반복될 구조였습니다.
- 측정 쿼리처럼 정리 배치에도 `max_statement_time=60` 을 걸어 둔 덕에, 첫 배치가 60초에서 끊기고(자동 롤백) 정리가 멈춰서 원인을 바로 볼 수 있었습니다.

**인덱스를 고정했습니다.** MariaDB 10.9 는 단일 테이블 `DELETE` 에 인덱스 힌트를 쓸 수 없어서, 지울 id 를 먼저 고르는 서브쿼리에 `FORCE INDEX` 를 걸고 그 id 로 지웁니다.

```sql
DELETE t FROM saved_numbers t
JOIN (
    SELECT id FROM saved_numbers FORCE INDEX (idx_round_rank)
    WHERE round = {회차} AND rank IS NULL AND user_id BETWEEN 1 AND 100
    LIMIT 10000
) x ON t.id = x.id;
```

- 안쪽: `(round, rank)` 로 지울 id 1만 개만 고릅니다(`r_rows=10,000`, 0.1초).
- 바깥: 기본 키로 바로 찾아 지웁니다.
- 옵티마이저가 데이터 분포에 따라 계획을 바꿔도, 이 쿼리는 늘 같은 길로 갑니다.

## 5. 수정 전후 측정

운영에서 기존 쿼리로 대량 삭제를 실제로 돌리면 또 공용 DB 를 멈출 수 있습니다. 그래서 세 갈래로 쟀습니다.

| 측정 | 수정 전 `round <= X` | 수정 후 `round = 회차` |
|---|---|---|
| 지울 1만 건 찾기 — 운영, `ANALYZE` SELECT | 120초 넘어 강제 중단 | **0.068초** |
| 1만 건 실제 삭제 — 운영 | 355~460초 (배치 로그 추정) | **4.5~7.6초** (실측) |
| 1만 건 배치 — 로컬 재현 | 평균 24.9초, 배치마다 +0.6초 | 평균 1.9초, 일정 |
| 58.5만 건 전체 — 로컬 재현 | 22만 건에서 중단 (487.8초) | **132초에 완료** |

- **운영 측정**
  - `SET STATEMENT max_statement_time=60 FOR …` 를 붙여, 측정 쿼리 자체가 공용 DB 를 오래 잡지 않게 했습니다.
  - 실제 삭제 측정은 「원래 그 배치가 지워야 할 행」만 대상으로 했습니다. 그 전에 테이블에 트리거와 참조 FK 가 없는 것을 확인했습니다.
- **로컬 재현**
  - 같은 테이블 구조·인덱스로 가짜 데이터 100만 행을 만들고, 쿼리마다 데이터를 원상복구하고 DB 를 재시작해 캐시를 비웠습니다.
  - 버퍼 풀도 데이터 크기 비율에 맞춰 줄였습니다(운영 128MB : 2.8GB ≈ 로컬 16MB).
  - 로컬 추세에 「운영의 남길 행 배율」과 「디스크 속도 배율」을 곱하면 운영 배치 로그 추정(355~460초)과 맞았습니다.
- **운영 규모 환산** — 매주 정상분 200만 건 삭제가 「3~4.5시간 이상」에서 「15~25분」이 됩니다. 금요일 밤에 시작해도 00:30 백업 전에 끝납니다.

### 5-1. 운영 반영 후 실측 — 밀린 934만 건 정리

수정을 반영한 뒤, 몇 주째 밀려 있던 지난 회차 더미를 운영에서 정리했습니다. 회차마다 1만 건씩 지우고, 배치 사이에 0.3초 쉬고, 문장마다 `max_statement_time=60` 을 걸었습니다.

| 구간 | 지운 행 | 걸린 시간 | 1만 건 배치 (평균 / 중간값 / 95%) |
|---|---|---|---|
| 1237~1241회 (`round =` 방식) | 6,521,641 | 15분 35초 | 1.13초 / 0.45초 / 4.25초 |
| 1242~1243회 (`FORCE INDEX` 방식, §4-1) | 2,794,763 | 7분 18초 | 1.27초 / 0.53초 / 4.86초 |
| 합계 (측정용 30,001건 포함) | **9,346,405** | **약 23분** | |

- 수정 전 방식으로 같은 양을 지우면 1만 건당 355~460초 × 650배치 이상이라 **2.5~3.7일 이상**이 걸렸을 양입니다(배치가 갈수록 느려지므로 이것도 하한).
- 정리 후 지울 대상은 0건입니다. 당첨 행과 회차별 통계는 지우지 않았습니다. 통계는 추첨 직후 최신 회차 하나만 계산해 별도 테이블에 저장하므로, 지난 회차 더미를 지워도 바뀌지 않습니다.

## 6. 실행계획 확인 습관

- 범위 조건·`LIMIT`·다른 인덱스 조건이 한 쿼리에 섞이면 `EXPLAIN FORMAT=JSON` 의 `key`·`used_key_parts`·`rows` 를 **운영 규모 데이터로** 봅니다.
- 실측은 `ANALYZE FORMAT=JSON` 으로 합니다. 단 **`ANALYZE DELETE` 는 진짜로 지우므로**, 같은 WHERE 의 `SELECT id …` 로 바꿔서 잽니다.
- 공용 DB 에서는 측정 쿼리 앞에 `SET STATEMENT max_statement_time=60 FOR` 를 붙입니다.

## 7. 정리

- **공용 인스턴스에서는 남의 문장 하나가 백업 잠금을 거쳐 내 쓰기를 멈춘다.** 쓰기만 멈추고 읽기가 되면 processlist 에서 `Waiting for backup lock` 과 그 앞의 긴 문장부터 찾습니다.
- **WHERE 는 요구사항을 옮기는 것으로 끝나지 않는다.** 같은 결과를 내는 조건이라도, 반복 실행될 때 남는 데이터가 찾는 길을 막지 않는지까지 따져야 합니다. 문법이 아니라 접근 경로를 설계하는 알고리즘 문제입니다.
- **옵티마이저의 비용 오판.** 범위 조건 + `LIMIT` + 다른 인덱스 조건이 섞이면 옵티마이저가 「곧 끝난다」고 믿고 엉뚱한 인덱스를 고릅니다. 쿼리 문장이 아니라 실행계획을 봐야 보입니다.
- **복합 인덱스는 앞 칼럼을 `=` 로 줄 때 뒤 칼럼까지 쓴다.** 범위를 쪼개 `=` 로 묻고 반복을 애플리케이션으로 옮기면, 새 인덱스 없이 같은 결과를 수십 배 빠르게 얻습니다.
- **좋은 실행계획도 데이터 분포가 바뀌면 뒤집힌다.** 정리로 테이블이 줄자 같은 `=` 쿼리가 다시 나쁜 인덱스를 골랐습니다. 반복 배치처럼 데이터가 크게 오가는 쿼리는 `FORCE INDEX` 로 길을 고정하고, 문장마다 실행 시간 상한을 걸어 두면 틀어져도 바로 드러납니다.
- **느려진 원인을 「데이터가 많아서」로 보고 재시도·타임아웃만 늘리면 악순환이 커진다.** 원인 배치의 코드에는 재연결·재시도·타임아웃 3600초가 붙어 있었습니다.

# 엔지니어링 결정 (왜 그렇게 했나)

"무엇을 만들었나"보다 **"왜 그 선택을 했나"**를 정리했습니다. 실제 개발·운영하며 내린 판단입니다.

## 1. JDK 17 → 21 마이그레이션 — 가상 스레드

**배경.** mildo의 요청은 **외부 I/O 대기가 지배적**입니다. 한 요청이 AI(Claude/OpenAI) 응답, 결제 영수증 검증, NICE 본인인증, OAuth 토큰 교환 등 외부 호출을 기다리는 시간이 CPU 연산보다 훨씬 깁니다.

**결정.** 플랫폼 스레드(요청당 OS 스레드) 모델에서는 이런 I/O 대기가 스레드를 점유해, 동시성을 높이려면 스레드 풀을 키우고 튜닝해야 합니다. **JDK 21의 가상 스레드(Loom)** 로 올려, 블로킹 코드를 **그대로 유지하면서** 대기 중 캐리어 스레드를 반납하도록 했습니다.

```yaml
spring:
  threads:
    virtual:
      enabled: true   # Tomcat 워커 + @Async 태스크에 자동 적용
```

- **리액티브(WebFlux)를 안 쓴 이유** — 명령형 코드의 가독성·디버깅 편의를 포기하지 않으면서 동시성 이득만 취하려고. 팀(1인) 유지보수 관점에서 리액티브의 학습·디버깅 비용이 과함.
- **주의점** — 가상 스레드는 I/O에는 강하지만 `synchronized` 블록에서 캐리어가 pin될 수 있어, 커넥션 풀 등은 `ReentrantLock` 기반인지 확인. HikariCP 풀 크기도 "동시 요청 = 가상 스레드"가 아니라 **DB 커넥션 상한**에 맞춰 별도로 명시.

## 2. HTTP 클라이언트 — 상황에 맞춰 3가지

외부 연동 성격에 따라 클라이언트를 나눠 썼습니다. "하나로 통일"이 항상 옳은 게 아니라, **각 연동의 요구가 달라서** 내린 선택입니다.

| 클라이언트 | 쓴 곳 | 이유 |
|---|---|---|
| **HTTP Interface** (`@HttpExchange`) | AI(Anthropic Messages API) | 인터페이스 선언만으로 호출 — 베이스URL·인증헤더·타임아웃을 설정에 모으고, 호출부는 메서드 하나. 가장 자주·중요하게 쓰는 연동이라 **선언적**으로. |
| **`java.net.http.HttpClient`** | Google Ads, TikTok, Google Play 검증 | 읽기 위주 단발 호출 + **무거운 벤더 SDK를 피하려고**. 의존성 0으로 REST 직접 호출. |
| **RestTemplate** | 카카오·네이버·애플 OAuth, NICE, PortOne | 단순 폼/JSON 교환. 기존 안정 동작 코드라 굳이 교체 안 함(불필요한 리스크 회피). |

> **HTTP Interface 예시** — 선언 한 줄로 끝:
> ```java
> public interface AnthropicApi {
>     @PostExchange("/v1/messages")
>     JsonNode createMessage(@RequestBody Map<String, Object> body);
> }
> ```
> 베이스URL/헤더/타임아웃은 `AnthropicConfig`에서 프록시 팩토리로 주입.

## 3. 트랜잭션 관리 전략

### 부가 작업은 커밋 후 별도 트랜잭션 (`AFTER_COMMIT` + `REQUIRES_NEW`)

회원가입에서 **핵심(유저 저장)과 부가(보너스 적립·초대 보상·광고 전환 이벤트)를 분리**했습니다.

```
가입 트랜잭션 T1 (유저 저장) ── 커밋
      └─ AFTER_COMMIT 이벤트 → REQUIRES_NEW T2 (보상 적립)
```

- **왜** — 보상 적립이 실패해도 **회원가입은 이미 커밋**되어야 함. 부가 로직이 핵심 UX를 볼모로 잡으면 안 됨.
- **주의로 배운 것** — 초기엔 약관 저장 서비스에 `@Transactional`이 붙어 있어, 호출부가 `try-catch`로 삼켜도 프록시가 rollback-only를 표시 → 커밋 시 `UnexpectedRollbackException`으로 가입이 깨졌습니다. **best-effort로 삼켜야 하는 메서드에는 트랜잭션을 붙이지 않는다**는 규칙을 세움.

### 읽기 전용은 `@Transactional(readOnly = true)`
집계·조회 서비스는 명시해 flush/dirty-checking 비용을 줄이고 의도를 드러냄.

### 동시성 제어는 5번 항목에서 별도로 다룹니다
베리 잔액(`token_account`)의 동시 갱신 전략은 운영 사고를 거쳐 한 번 바뀌었습니다. → [5. 잔액 동시 갱신](#5-잔액-동시-갱신--왜-비관적-락인가)

## 4. 멱등성을 데이터 레벨에서 강제

재시도·중복 웹훅·재가입 파밍은 애플리케이션 로직으로 막으면 경쟁 조건이 남습니다. 그래서 **DB 유니크 제약**으로 못 박았습니다.
- 결제: `idempotency_key` UNIQUE (스토어 거래 ID)
- 1회성 보상: `(type, ref_type, ref_id=사람 CI 해시)` UNIQUE
- 초대: `invitee_id` + `invitee_ci_hash` UNIQUE

## 5. 잔액 동시 갱신 — 왜 비관적 락인가

**처음엔 낙관적 락이었고, 운영 사고를 겪고 바꿨습니다.** 판단이 틀렸던 지점과 근거를 남깁니다.

### 무엇이 틀렸나

`token_account`에 `@Version`을 두고 "충돌 시 재시도가 값싸다"는 이유로 낙관적 락을 골랐습니다. **그런데 재시도를 구현하지 않았습니다.** 선택의 전제였던 것이 코드에 없었던 겁니다.

차감(`spend`)·회수(`clawback`)는 비관적 락을 쓰고 있었고 **적립 경로만 락 없이 읽고 있었습니다.** 같은 테이블에 두 전략이 섞여 있었고, 그 사실을 사고가 나서야 알았습니다.

결과는 [`troubleshooting.md` 9번](./troubleshooting.md#9-동시-지급-하나가-조용히-사라지던-문제-) — 앱 기동 시 이벤트 보상과 출석 보상이 같은 계정 행을 동시에 갱신하다 한쪽이 409로 지고, 재시도가 없어 그 지급이 사라졌습니다. 한 유저는 **2시간 51분** 뒤에야 받았습니다.

### 무슨 일이 벌어지는가 — 트랜잭션 생애주기로 보기

이 사고의 핵심은 **"동시에 썼다"가 아니라 "읽은 뒤 남이 먼저 커밋했다"** 입니다. JPA의 쓰기 지연이 그 창을 벌립니다.

**트랜잭션 배치.** 지급 한 건은 이렇게 구성돼 있습니다.

```
@Transactional  ping()
├─ currentSlot()                    메모리 캐시 (DB 접근 없음)
├─ findIdByEmail()                  SELECT
├─ participation.insertIgnore()     INSERT (네이티브 → 이 시점에 flush 유발)
├─ creditFree()  @Transactional     ← REQUIRED. 같은 트랜잭션에 합류
│   ├─ 멱등 중복검사                SELECT
│   ├─ getOrCreateAccount()         SELECT  ★ 여기서 version 을 손에 쥔다
│   ├─ tokenGrant.save()            영속화만 — SQL 안 나감 (쓰기 지연)
│   ├─ account.setFreeBalance(+n)   더티 마킹만 — UPDATE 안 나감 (쓰기 지연)
│   └─ tokenTransaction.saveAndFlush()  ★ 여기서 비로소 flush
│        → INSERT token_grant
│        → UPDATE token_account SET free_balance=?, version=? WHERE id=? AND version=?
│        → INSERT token_transaction
└─ saveEventRewardInbox()  REQUIRES_NEW   별도 트랜잭션(알림함)
   COMMIT
```

**쓰기 지연이 만드는 창.** `setFreeBalance()`를 호출한 순간 UPDATE가 나가는 게 아닙니다. Hibernate는 더티 체킹만 해두고 **flush 시점까지 미룹니다.** 그래서 `★` 두 지점 사이가 벌어집니다.

```
계정 SELECT (version=N 확보)  ─────── 그 사이 ─────── UPDATE ... WHERE version=N
                                    ↑
                        다른 트랜잭션이 같은 version 을 읽을 수 있는 구간
```

**실패 시퀀스.** 앱 기동 시 이벤트 핑과 출석 체크인이 같은 계정을 건드리면 이렇게 됩니다.

```
T1(ping)      read(v=N) ──────────── UPDATE ─ commit(v=N+1)
T2(check-in)      read(v=N) ───────────────────── UPDATE ... WHERE v=N → 0 rows
                      ↑                                        ↓
              T1 커밋 전에 읽음                    StaleStateException
                                          → ObjectOptimisticLockingFailureException → 409
```

두 요청이 마이크로초 단위로 부딪힐 필요가 없습니다. **T2의 읽기가 T1의 커밋보다 앞서기만 하면** 집니다. 반대로 T2가 T1 커밋 뒤에 읽으면, 시작이 더 빨랐더라도 이깁니다.

**한 가지 더 — T2는 즉시 실패하지 않고 기다립니다.** UPDATE는 현재 읽기(current read)라 락이 필요한데, T1이 이미 그 행에 X 락을 쥐고 있습니다. T2는 **T1이 커밋할 때까지 UPDATE 문에서 대기**했다가, 풀려난 뒤 최신 행을 보고 그제서야 `version=N`이 0건임을 알게 됩니다. **기다린 보람 없이 지는 구조**였습니다.

### 롤백은 사고가 아니라 방어가 작동한 것

여기서 헷갈리기 쉬운데, **ACID가 깨진 게 아니라 깨지려는 걸 막은 겁니다.**

버전 검사가 없었다면 이렇게 됩니다.

```
잔액 1517
  T1 read 1517 → 1517+3 = 1520 기록
  T2 read 1517 → 1517+2 = 1519 기록   ← T1 의 3베리가 증발
```

이게 **lost update**이고, 진짜로 원자성·일관성이 깨지는 경우입니다. `@Version`은 "내가 본 값이 아직 그대로인가"를 쓰기 직전에 확인하고, 아니면 **자기가 한 일을 전부 되돌립니다.** 409는 그 방어가 발화했다는 신호지 결함이 아닙니다.

**롤백 범위도 트랜잭션 경계 그대로입니다.** 출석의 경우 계정 UPDATE만이 아니라 `attendance_log` INSERT까지 함께 사라집니다.

```
BEGIN
  INSERT attendance_log            ← 이것도
  UPDATE token_account WHERE v=N   ← 여기서 0 rows
ROLLBACK                            ← 둘 다 없던 일로
```

그래서 "오늘 출석함" 기록이 안 남고, **다음 호출이 다시 시도 가능한 상태**가 됩니다. 실제로 한 유저는 앱을 다시 켠 2시간 51분 뒤에 받았습니다. **영구 유실이 아니라 "재시도 가능한 상태로 되돌아간 것"** 이 정확한 표현이고, 진짜 결함은 그 재시도를 아무도 안 해줬다는 점입니다.

> 반대로 `attendance_log`가 남았다면 `INSERT IGNORE`가 다음에도 0을 반환해 **그날은 영영 못 받았을** 겁니다. 트랜잭션 경계를 어디까지 잡았느냐가 피해 성격을 갈랐습니다.

### 비관적 락이 바꾸는 것은 "대기 지점"이다

```
before  read(락 없음, v=N) ─────────── UPDATE 에서 대기 → 깨어보니 실패
after   SELECT ... FOR UPDATE 에서 대기 ─→ 최신 v=N+1 읽음 → UPDATE 성공
```

기다리는 시간은 전과 같습니다. **대기를 UPDATE에서 읽기로 앞당겼을 뿐**인데, 기다린 뒤 최신 값을 읽으므로 질 이유가 사라집니다. 뒤 요청이 조금 느려지고 실패하지 않습니다.

검증에서 커밋이 정확히 3초 간격(주입한 지연만큼)으로 **직렬화**된 것이 이 동작을 그대로 보여줍니다.

### 교과서적 선택지 4가지

| # | 방법 | 원리 | 적합한 상황 |
|---|---|---|---|
| 1 | **비관적 락** `SELECT … FOR UPDATE` | 읽는 순간부터 줄 세움 | 경합이 낮고 트랜잭션이 짧을 때 |
| 2 | **낙관적 락 + 재시도** `@Version` | 부딪히면 다시 읽고 다시 계산 | 경합이 드물고 처리량이 중요할 때 |
| 3 | **원자적 UPDATE** `SET balance = balance + :n` | 읽기-수정-쓰기 자체를 없앰 | 초당 수백 건이 같은 행을 때릴 때 |
| 4 | **원장 합계** 잔액 컬럼 제거, `SUM()` | 경합 지점을 없앰 | 감사 추적이 최우선일 때 |

이론적으로 가장 깔끔한 건 **3번**입니다. 애초에 "읽고 → 계산하고 → 쓰기"를 안 하니 충돌할 게 없습니다.

### 그런데 1번을 골랐습니다

**첫째, 이미 절반이 1번이었습니다.** 차감·회수·소멸 경로가 원래 `findByUserIdForUpdate`를 쓰고 있었고 적립만 빠져 있었습니다. 3번으로 가면 **한 테이블에 두 가지 동시성 전략이 섞이고, 그게 이번 사고의 원인이었습니다.** 같은 실수를 반복하지 않는 게 성능보다 중요했습니다.

**둘째, 규모가 3번을 정당화하지 않습니다.** 하루 979건 호출에 충돌 3건입니다. 3번의 이점이 의미를 갖는 구간이 아니고, 오히려 JPA 더티체킹을 우회하는 네이티브 UPDATE가 13개 호출부에 퍼지면서 영속성 컨텍스트 불일치라는 **새 위험**이 생깁니다.

**셋째, 4번은 이미 절반 적용돼 있습니다.** `token_account.free_balance`는 원래 `token_grant.remaining` 합의 **캐시**입니다. 진짜 잔액은 원장에 있어서, 이 캐시가 잠깐 틀어져도 돈은 안 깨집니다. 실제로 이번 사고에서도 금액은 정확했고 "줘야 할 게 안 들어간" 문제였습니다.

### 비관적 락으로 오면서 생긴 새 위험 — 락 순서

적립이 락을 잡게 되면서 **한 트랜잭션에서 계정 행을 여러 개 잠그는 경로**가 데드락 위험을 갖게 됐습니다. 두 곳이었습니다.

| 지점 | 잠그는 순서(수정 전) |
|---|---|
| 친구 초대 보상 | 초대자 → 피초대자 (인자 순서) |
| 무상 베리 만료 배치 | `HashMap` 순회 = 해시 순서 (실행마다 다름) |

**둘 다 userId 오름차순으로 고정**했습니다(`HashMap` → `TreeMap`). 순서가 같으면 순환 대기가 구조적으로 만들어지지 않습니다. 내가 만든 위험을 같은 커밋에서 닫는 것이 맞다고 봤습니다.

### 검증 방법

충돌이 확률적이라(979건 중 3건) 그냥 돌려서는 재현이 안 됐습니다. **계정 읽기 직후에 `Thread.sleep(3000)`을 임시로 넣어 충돌 창을 강제로 벌리고** 수정 전/후를 대조했습니다.

```
락 없음  → ping 409, 이벤트 3베리 유실, 잔액 +2
락 적용  → 둘 다 200, 커밋이 3초 간격으로 직렬화, 잔액 +5 정확
```

임시 코드는 검증 후 제거했습니다. **"고쳤다"고 말하려면 고치기 전에 깨지는 것을 먼저 봐야 한다**는 게 이 건에서 얻은 규칙입니다.

### 남은 개선 여지

지급 트랜잭션 안에서 알림함 저장(`REQUIRES_NEW`)을 호출하는데, **중단은 락 해제가 아니라서** 바깥 트랜잭션이 락을 쥔 채 대기합니다. 락 보유 시간이 그만큼 길어집니다. 현재 규모에서는 몇 ms 수준이라 손대지 않았고, 이벤트 규모가 커지면 컨트롤러 계층으로 빼는 것이 다음 수순입니다.

## 6. 저장 시각은 앱이 정한다 — OS·DB 시계 의존 제거

모든 시각을 **KST wall-clock**으로 저장하는 규칙인데, 그 규칙이 두 군데서 **환경 설정에 기대고** 있었습니다.

**첫째, JVM 기본 타임존.** 존을 안 붙인 `LocalDateTime.now()`가 약 170곳이고 JPA `@CreationTimestamp`도 JVM 기본 타임존을 따릅니다. 지금 KST인 이유는 **운영 서버 OS가 우연히 `Asia/Seoul`이라서**였고 `-Duser.timezone`도 없었습니다. 클라우드 이미지 기본값인 UTC로 서버를 재구축하면 **예외 하나 없이 데이터만 9시간 틀어집니다.**

**둘째, DB 시계.** 출석 로그와 알림 읽음 시각이 SQL `NOW()` / JPQL `CURRENT_TIMESTAMP`를 쓰고 있었습니다. 그건 앱이 아니라 **DB 서버의 시계**입니다. 운영 DB가 `+09:00`이라 맞아떨어졌을 뿐이고, 로컬(UTC 컨테이너)에서는 같은 요청인데 컬럼마다 9시간 어긋나 있었습니다.

```
token_transaction.created_at   11:18:45   (앱 시계)
attendance_log.created_at      02:18:45   (DB 시계)   ← 같은 요청
```

**해결** — ① `SpringApplication.run` 이전에 `TimeZone.setDefault`로 못박고(커넥션 풀·Hibernate 초기화까지 적용), ② DB 시계를 쓰던 쿼리는 앱이 계산한 KST를 파라미터로 넘기도록 바꿨습니다.

> **운영에서는 값이 바뀌지 않습니다.** 이미 맞고 있던 것을 **환경 설정에 대한 의존만 끊은** 변경입니다. "지금 맞으니 됐다"와 "왜 맞는지 코드가 보장한다"는 다르다고 봤습니다.

## 7. 관리자 백오피스를 Spring에서 들어냈다

관리자 API 17개(컨트롤러 기준)를 **PHP로 이관하고 Spring에서 삭제**했습니다. 앱 API와 관리자 API는 **트래픽 특성·배포 주기·장애 영향 범위가 전부 다른데** 한 애플리케이션에 있으면 관리자 화면 하나 고치려고 앱 서버를 재기동해야 합니다.

- **이중 차단** — nginx에서 `/api/v1/mdo` 차단 + `SecurityConfig`에서 `denyAll`. 한쪽 설정 실수로 뚫리지 않게.
- **되돌릴 수 있게** — 삭제 전 태그(`pre-admin-removal`)와 브랜치(`archive/spring-admin`)로 아카이빙.
- **서비스·DTO는 남겼습니다** — 통계 로직 자체는 재사용 가치가 있고, 지우면 되살릴 때 다시 짜야 합니다.

## 8. 법적 요구가 걸린 기능은 토글로 감쌌다

탈퇴 시 거래기록 보존(5년)은 **개인정보처리방침에 항목·기간·근거가 고지돼 있어야 적법**합니다. 그런데 방침 개정본 배포가 iOS 심사에 막혀 있었습니다.

기능은 완성해두고 **설정값 하나로 끌 수 있게** 했습니다(`retain-years <= 0`이면 이관 건너뜀). 방침이 배포되면 값만 5로 되돌리고 재기동하면 **코드 변경 없이** 켜집니다.

**파기 계열은 이 스위치의 영향을 받지 않게 분리**했습니다. 데이터를 더 지우는 쪽이라 어떤 방침과도 충돌하지 않고, 오히려 현재의 무기한 잔존(위반) 상태를 해소하기 때문입니다. **"켜는 것"과 "지우는 것"은 법적 성격이 반대**라는 판단입니다.

## 9. 기능 토글 & 설정 분리

- **민감 설정**(키·DB·시크릿)은 `application-credentials.yaml`·`application-prod.yaml`로 분리, **git 추적 제외 + 배포 jar에 내장.**
- **위험한 신기능**(구글 IAP 실검증, 환불 폴링, 광고비 수집)은 **토글**로 감싸 운영에서 단계적으로 켬. 로컬 기본 off, 운영 yaml에서 on.
- 환경별 프로필(local/prod)로 로그 레벨·검증 강도 분리 (로컬 DEBUG, 운영 조용).

## 10. 알림을 7종 카테고리로 세분화 — 판정은 발사 지점이 아니라 조회 쿼리에서

알림 수신 동의를 마스터 스위치 하나에서 **7종 카테고리**(매칭·소셜·채팅·신고·이벤트·공지·거래성 + 광고)로 세분화했습니다. 발송 = **마스터 AND 세부** 동의.

설계에서 중요한 결정은 **판정 위치**입니다. 푸시를 쏘는 지점이 코드 전체에 11곳인데, 각 지점이 토글을 검사하면 하나만 빠져도 정책 구멍이 됩니다. 대신:

- 호출부는 `sendToUser(PushCategory.CHAT, ...)`처럼 **카테고리만 선언**
- 수신 동의 판정은 **디바이스 토큰 조회 쿼리**(`findActiveTokensForCategory`)가 수행 — 필터를 통과한 토큰이 없으면 발송이 없던 일이 됨
- **미발송도 push_log에 남깁니다**(`requested=0`). "토글에 걸려 안 나갔다"를 로그로 증명할 수 있어야 검증이 됩니다

**광고(MARKETING)만 판정이 반대 방향**입니다. 서비스 알림은 "거부하지 않으면 발송"이지만 광고는 **별도 옵트인이 있어야 발송**이고(정보통신망법 §50), 옵트인이 있어도 **야간(21~08시 KST)은 차단**합니다. 법적 요구를 사람의 주의력이 아니라 발송 진입점의 코드로 강제한 것입니다.

→ [`PushService.java`](../code-excerpts/PushService.java)

기존 유저 마이그레이션은 **컬럼 추가 시 NULL = ON(발송)** 규칙으로 처리했습니다. 세분화 이전 유저는 모든 알림을 받고 있었으므로, 기본값이 OFF면 배포 순간 알림이 끊기는 조용한 사고가 됩니다.

검증에는 별도 도구가 필요했습니다 — 공지 발송의 유일한 트리거(관리자 API)는 백오피스 이관으로 Spring에서 `denyAll`, 채팅 푸시는 웹소켓 경유, 이벤트 푸시는 스케줄러 전체발송뿐이라 **HTTP로 재현할 수단이 없었습니다.** `@Profile("local")` 발사 컨트롤러를 만들어 운영과 동일한 발송 경로를 태우되, **토큰 주인 본인에게만** 쏘게 제한했습니다(로컬 DB에 운영과 동일한 실물 토큰이 있어 전체발송은 실사용자 오발송 사고가 됩니다).

## 11. LLM 채점 응답 — "형식을 강제할 수 있는가"보다 "깨졌을 때 무엇을 잃는가"

AI 대화에 호감도 점수(4축 채점)를 붙이면서, 모델 응답에서 본문과 점수를 분리하는 방식을 골라야 했습니다.

- **JSON으로 감싸 받기 — 탈락.** 형식이 깨지는 순간(토큰 잘림, 따옴표 이스케이프) 점수만이 아니라 **본문까지 못 꺼냅니다.** 기존 공용 파서는 파싱 실패 시 재호출 후 예외를 던지므로, 형식 오류가 곧 "답장이 안 옴"이 됩니다.
- **구조화 출력(tool use) — 구현했지만 기본 OFF.** 스키마가 생성을 제약하므로 형식 위반이 원천 차단되지만, 실측에서 응답이 **+37% 느렸습니다.** 채팅은 지연에 가장 민감한 화면입니다.
- **응답 말미 마커(`[[SCORE n,n,n,n]]`) — 운영 채택.** 모델이 형식을 어길 수 있다는 약점은, **채점 실패 시 점수만 포기하고 본문은 살리는** 파서로 받아냅니다.

판단 기준을 한 문장으로: **"가끔 점수가 안 뜬다"가 "가끔 답장이 안 온다"보다 낫다.** 두 경로 모두 구현하고 토글로 전환할 수 있게 해, 지연이 개선되면 구조화로 넘어갈 수 있습니다.

마커 방식의 비용은 방어 코드입니다 — 실측 48턴 중 2턴(4.2%)에서 모델이 대괄호 없이 숫자만 남겨 `4,4,3,4`가 사용자 화면에 그대로 노출됐고, "마지막 줄 전체가 1~5 정수 4개일 때만"이라는 좁은 폴백 패턴으로 잡았습니다. 넓게 잡으면(`\d`) 정상 문장을 삼킬 수 있어 범위를 일부러 좁혔습니다.

→ [`AffinityScoring.java`](../code-excerpts/AffinityScoring.java)

## 12. 버튼 잠금도 서버가 판정한다

탐색 카드 갱신 버튼(과금 기능)의 활성/비활성을 프론트가 자체 계산하다가, 정책이 바뀔 때마다 서버·앱 판정이 어긋나는 문제가 반복됐습니다. 응답에 `refreshAvailable`(갱신 가능 여부)과 `charged`(이번 갱신이 과금이었는지)를 명시해 **프론트는 판정하지 않고 표시만** 하게 바꿨습니다.

앱은 스토어 심사 때문에 배포가 느립니다. 판정을 서버로 옮겨두면 정책 변경(예: "후보를 다 못 채우면 무과금")이 **서버 배포만으로** 전 유저에게 적용됩니다.

## 13. 연속 일수를 매번 세지 않고 상태로 저장한다 ★

연속 출석 도장판을 붙일 때, "며칠째인가"를 **저장하지 않고 매번 로그에서 다시 세는** 방식으로 시작했습니다. 오늘부터 하루씩 거슬러 올라가며 출석 로그가 끊기는 지점에서 멈추는 구조입니다. 장점이 분명했습니다 — `attendance_log`가 유일한 진실이라 **저장값이 어긋날 수가 없습니다.** 운영에서 로그를 손대도 다음 조회에 자동으로 맞춰집니다.

**그런데 읽어야 할 행 수가 곧 그 사람의 연속 일수입니다.** "하루라도 빠지면 초기화"라는 규칙은 이걸 줄여주지 못합니다 — 줄여주는 것은 *끊긴 사람*이고, 문제가 되는 것은 *한 번도 안 끊긴 사람*이기 때문입니다. 무한정 읽지 않으려고 넣은 상한이 결국 정답을 바꿔버렸습니다(troubleshooting §14).

**상태 테이블로 전환했습니다.** 게임 출석부가 대개 취하는 형태입니다.

```
attendance_streak   유저당 1행 — streak_count, last_attend_date
attendance_log      날짜별 1행 — 기존 그대로 (지급 이력)
```

체크인 때 *마지막 출석일이 어제면 +1, 아니면 1로 리셋*합니다. **결석 허용이 없으므로 마지막 출석일 하나만 보면 되고**, 읽기가 1행으로 끝납니다.

**로그를 없애지 않은 것이 핵심입니다.** 상태는 캐시고 로그가 진실입니다. 둘이 어긋나면 로그에서 다시 계산해 덮어쓸 수 있습니다. 상태값을 유일한 진실로 삼았다면 자가 복구 경로를 통째로 잃었을 겁니다.

**나눈 값을 저장하지 않습니다.** 도장판이 7칸이라 `streak % 7`을 저장하고 싶어지지만, 그러면 **7일차와 "출석 없음"이 같은 0으로 뭉개집니다.** `% 8`로 바꿔도 문제가 한 칸 뒤로 밀릴 뿐입니다. 누적 원본을 저장하고 표시 위치는 읽을 때 계산합니다.

```java
// 저장: 1, 2, 3, ... 7, 8, 9 (원본)
// 표시: ((누적 - 1) % 7) + 1   →  7일차는 7, 8일차는 새 주기 1
```

API가 실제 연속 일수(`totalStreak`, 7을 넘어도 계속 오름)를 함께 내려주므로 **어차피 원본이 필요**하기도 합니다.

**부수 효과가 하나 더 있었습니다.** 상태 테이블은 배포 시점에 비어 있으므로 전원이 0에서 시작합니다 — **소급 적용이 구조적으로 불가능해집니다.** 덕분에 §14에서 설명한 "시작일" 설정을 따로 둘 필요가 없어졌고, 배포일마다 날짜를 챙기는 운영 부담이 사라졌습니다.

## 14. 새로 여는 이벤트는 소급 적용하지 않는다

출석 체크(2베리)와 출석 로그는 **예전부터 돌던 기능**이고, 이번에 새로 연 것은 **도장판과 3일차·7일차 보너스**뿐이었습니다. 기획 문서에는 "기존 로그 재활용이라 오픈 첫날부터 소급 표시된다"가 **기능으로** 적혀 있었고, 저도 그대로 구현했습니다.

**배포 직전에 뒤집었습니다.** 소급하면 오픈 당일에 누군가는 5일차부터 시작하는데, **그 사람은 3일차 보너스를 받을 기회 없이 지나친 상태**가 됩니다. 게다가 도장판에는 「받음」으로 표시됩니다 — `granted` 판정이 원장이 아니라 *현재 일차*를 기준으로 하기 때문입니다. **받은 적 없는 보상이 받은 것으로 보이는** 상태입니다.

배포 시점 실측으로 대상이 11명, 합계 43베리였습니다. 금액은 작지만 성격이 나빴습니다.

새로 여는 이벤트는 **여는 날부터 세는 것**이 맞습니다. 전원이 같은 날 1일차로 출발하면 설명이 필요 없고, 3일차·7일차 보너스를 **모두가 온전히** 받습니다. "기존에 매일 접속하던 사람이 리셋된다"는 손해처럼 보이지만, 그 사람들은 어차피 첫 주기 보너스를 못 받는 상태였으므로 **오히려 이득**입니다.

구현은 지급 로그를 건드리지 않습니다. 2베리 지급은 그대로 돌고 **도장판과 보너스만** 시작일 이후를 셉니다 — 정책을 되돌릴 여지를 남기기 위해서입니다(이후 §13의 상태 저장으로 전환하면서 이 조건 자체가 불필요해졌습니다).

## 15. 두 형식이 섞인 컬럼 — 마이그레이션 대신 읽는 쪽에서 흡수한다

지역 컬럼에 영문 코드(`SEOUL`, `SEOUL_GANGNAM`)와 한글(`서울`, `경기 여주시`)이 섞여 있었습니다. 코드가 영문 코드 + 언더바 구분자를 전제로 짜여 있어, **한글로 저장된 값은 권역 매핑에서 아예 안 잡혔습니다.**

증상이 조용했습니다. 「가까운 곳에 살아요」 추천에서 서울 유저가 같은 서울 사람과 안 묶이고 곧장 전국 단계로 떨어졌지만, **후보가 비지는 않아** 화면상으로는 정상이었습니다. 실측해보니 서울에서만 18명이 65명과 분리돼 있었습니다.

**`UPDATE`로 통일하지 않았습니다.** 두 가지 이유입니다.

- **되돌리기 어렵습니다.** 원본 형식 정보가 사라지고, 잘못 매핑된 값을 나중에 발견해도 복구 근거가 없습니다.
- **앱이 계속 한글을 보내면 또 섞입니다.** 저장 시점 검증을 함께 넣지 않는 한 마이그레이션은 그때뿐입니다.

대신 **읽는 함수 하나를 정규화 지점으로** 삼았습니다. 시도를 떼어내는 `sidoOf` 하나만 두 형식·두 구분자를 모두 받게 하면, 그 위에 있는 권역 판정과 추천 분기는 손대지 않아도 맞아떨어집니다.

```
"SEOUL_GANGNAM" → SEOUL      "서울"       → SEOUL
"경기 여주시"    → GYEONGGI    "서울특별시"  → SEOUL   (접두 일치로 흡수)
```

**모르는 값은 `null`이 아니라 원본을 대문자로 돌려줍니다.** `null`로 만들면 매핑 테이블에 없는 값끼리도 서로 안 묶여서, **지금 잘 되던 문자열 완전 일치 매칭까지 깨집니다.** 정규화를 넣다가 기존 동작을 퇴행시키는 흔한 지점이라 명시적으로 처리했습니다.

저장 시점 통일은 별건으로 분리했습니다 — 급하지 않지만 방치하면 계속 늘어나는 종류입니다.

## 16. 트랜잭션 경계에서 외부 호출을 걷어낸다 ★

[트러블슈팅 §18](troubleshooting.md)에서 나온 문제입니다. `@Transactional` 하나가 외부 LLM 호출 40~50초까지 감싸고 있어서, 그 시간 내내 DB 커넥션이 잡히고 실패 시 가입까지 롤백됐습니다. 여기서는 **어떻게 쪼갰는지와 그 과정에서 걸린 것들**을 적습니다.

### 목표 모양

```
바깥 메서드                      트랜잭션 없음. 순서만 잡는다
├─ tx1  준비·검증               커밋 → 커넥션 반납
├─      외부 호출(LLM)          트랜잭션 밖
└─ tx2  저장                    커밋
```

이미 이 모양으로 되어 있던 코드가 프로젝트 안에 있었습니다(시뮬레이션 생성 경로). **새 패턴을 도입한 게 아니라 이미 있던 규칙을 안 지킨 곳들을 맞춘 것**입니다.

### ① 같은 클래스 안에서 나누면 트랜잭션이 아예 안 생긴다

가장 먼저 걸린 것입니다. 메서드를 셋으로 쪼개고 각각 `@Transactional`을 붙이면 될 것 같지만, **자기호출은 Spring 프록시를 타지 않습니다.** 프록시는 빈 외부에서 들어올 때만 개입하므로, `this.persist(...)` 호출에는 트랜잭션이 열리지 않습니다. 경계를 만들려다 오히려 없애는 셈입니다.

그래서 선택지는 둘입니다.

- **트랜잭션 구간을 별도 빈으로 뺀다** — 프록시를 타므로 정상 동작합니다.
- **`TransactionTemplate`으로 경계를 프로그래밍 방식으로 잡는다** — 프록시를 거치지 않으므로 자기호출 함정 자체가 없습니다.

### ② 별도 빈으로 빼면 그 클래스의 테스트가 무력해진다

처음에는 별도 빈으로 갔습니다. 그런데 만들고 나서 되돌렸습니다.

리팩토링의 안전망으로 쓰던 단위 테스트가 `@InjectMocks`로 대상 클래스를 조립하는데, **로직이 새 빈으로 옮겨가면 테스트는 그 빈을 모릅니다.** 목으로 채워 넣으면 컴파일은 되지만 **검증하려던 로직 자체가 목으로 덮여서** 테스트가 아무것도 확인하지 않게 됩니다.

그래서 대부분은 `TransactionTemplate`을 썼습니다. 로직은 클래스 안에 `private` 메서드로 남기고 경계만 밖에서 잡습니다.

```java
public Response create(String email, Request request) {
    Draft draft = txTemplate.execute(status -> prepare(email, request));   // tx1
    AiResult ai = aiService.generate(draft.payload());                     // tx 밖
    return txTemplate.execute(status -> persist(draft, ai));               // tx2
}
```

**예외를 하나 뒀습니다.** 직접 단위 테스트 대상이 아닌 클래스는 별도 빈으로 뺐습니다. 프로젝트에 이미 같은 구조(채팅 서비스 / 채팅 트랜잭션 서비스)가 있어 그쪽과 모양을 맞추는 편이 읽기 좋았습니다. **규칙을 하나로 강제하기보다 각 클래스의 검증 방식에 맞췄습니다.**

부수 효과로 `TransactionTemplate`은 테스트에서 다루기도 쉽습니다. 목으로 만들고 콜백을 그 자리에서 실행하게 스텁하면, **원본 코드에는 그 필드가 아예 없으므로 같은 테스트가 리팩토링 전후 양쪽에 붙습니다.**

### ③ 준영속 엔티티를 외부 호출에 넘겨도 되는가

tx1이 커밋되면 엔티티는 **준영속(detached)** 이 됩니다. 이 상태에서 지연로딩 필드를 건드리면 `LazyInitializationException`이 납니다.

리포트 생성 경로가 여기 걸렸습니다. LLM에 페르소나 엔티티를 통째로 넘기고 있었기 때문입니다. 실제로 무엇을 읽는지 따라가 보니 **JSON 컬럼 다섯 개만 읽고 연관관계는 손대지 않았습니다.** 그래서 그대로 넘겨도 안전하다고 판단하고 호출을 유지했습니다.

프로젝트에는 이미 같은 인자를 `Map`으로 받는 변형이 있었고 주석에 *"트랜잭션 분리용"*이라고 적혀 있었습니다. 그쪽으로 가면 더 안전하지만 프롬프트 서비스를 이 클래스에 추가로 주입해야 해서, **의존성 하나를 늘리는 값과 얻는 안전 사이에서 후자가 이미 확보됐다고 보고 넘기지 않았습니다.**

### ④ 더티 체킹은 트랜잭션을 쪼개는 순간 조용히 멈춘다

가장 위험한 함정이었습니다.

소개글 재생성 코드에 `save()` 호출이 없었습니다. 한 트랜잭션 안이라 **영속 상태 엔티티의 변경이 커밋 시점에 자동으로 flush** 되고 있었기 때문입니다(쓰기 지연). 이 상태로 트랜잭션만 쪼개면 엔티티가 준영속이 되어 **변경이 어디에도 반영되지 않은 채 조용히 사라집니다.** 예외도 안 나고 로그도 안 남습니다.

그래서 저장 구간에서 **다시 읽어 영속 상태로 만든 뒤 명시적으로 `save`** 하도록 바꿨습니다.

이건 테스트 설계에도 영향을 줬습니다. 특성화 테스트를 *"`save`가 불렸는가"*로 쓰면 원본에서는 red가 납니다(원본은 안 부르니까). 그래서 **엔티티의 최종 상태**로 단언했습니다. 더티 체킹이든 명시적 저장이든 같은 단언이 성립합니다.

### ⑤ 커밋 후에 발사되는 이벤트는 트랜잭션이 없으면 안 불린다

광고 전환 이벤트를 옮기다 걸렸습니다.

수신자가 `@TransactionalEventListener(AFTER_COMMIT)`입니다. 이름 그대로 **커밋이 있어야** 불립니다. 트랜잭션을 다 닫고 나서 발행하면 리스너가 조용히 호출되지 않고 이벤트가 증발합니다. 예외도 안 납니다.

이 이벤트를 어디에 두느냐는 성능이 아니라 **의미의 문제**였습니다.

- 예전에는 페르소나까지 성공해야 커밋됐으므로, 이 이벤트는 사실상 **"온보딩 완주"** 를 뜻했습니다.
- 가입 커밋 직후로 옮기면 페르소나 실패자까지 전환으로 집계됩니다. 외부 광고 서버로 나가는 값이라 **취소도 안 되고 멱등 처리도 없습니다.** 지표가 부풀면 매체가 잘못된 신호로 최적화합니다.

그래서 **페르소나 성공 뒤에, DB 작업이 없는 짧은 트랜잭션을 하나 열어 그 안에서 발행**했습니다. 열자마자 커밋되므로 리스너가 정상적으로 걸리고 커넥션은 수 ms만 잡습니다.

### ⑥ 원자성을 포기하면 무엇이 남는지 먼저 센다

트랜잭션을 쪼갠다는 건 **"전부 되거나 전부 안 되거나"를 버린다**는 뜻입니다. 성능 최적화가 아니라 비즈니스 규칙 선언을 바꾸는 일입니다.

그래서 쪼개기 전에 **중간 상태를 전부 열거**했습니다.

| 어디서 끊기면 | 남는 상태 | 판단 |
|---|---|---|
| tx1 후 LLM 실패 | 계정 있음 · 페르소나 없음 | **이미 존재하던 정상 상태.** 앱이 재진입을 처리함 |
| tx2 준비 후 실패 | 아무것도 안 바뀜 | 준비 구간을 읽기 전용으로 만들어 확보 |
| LLM 성공 후 저장 실패 | LLM 비용만 소모 | **예전과 동일.** 달라지는 게 없음 |

**새로 생기는 나쁜 상태가 없다**는 걸 확인하고 진행했습니다. 오히려 예전이 더 나빴습니다 — LLM 하나가 실패하면 계정이 사라져서 본인인증부터 다시 해야 했습니다.

### ⑦ 재화 차감은 순서를 옮기면서 의미가 바뀐다

재분석 기능은 트랜잭션 안에서 **차감을 먼저 하고 LLM을 호출**했습니다. 주석에 *"LLM 실패 시 롤백 = 환불"* 이라고 적혀 있었습니다. 롤백을 환불 수단으로 쓰고 있었던 겁니다.

쪼개면 이 장치가 사라집니다. 그래서 **차감을 LLM 성공 뒤로 옮겼습니다.** 최종 결과는 같고(실패 시 차감 없음) 환불이라는 개념 자체가 필요 없어집니다. 저장이 실패하면 차감도 같은 트랜잭션에서 롤백되므로 "돈만 나가고 결과가 없는" 상태도 안 생깁니다.

**그런데 이 변경이 회귀를 하나 만들었습니다.** 잔액이 0인 사람도 LLM을 한 번 태우고 나서야 402를 받게 됐습니다. 응답 코드는 같지만 20~45초를 기다리고, 그동안 우리는 LLM 비용을 헛되이 씁니다. 예전에는 차감이 먼저라 즉시 402였습니다.

그래서 **준비 구간에 잔액 사전 확인을 넣었습니다.** 실제 차감은 그대로 뒤에 두므로 "실패 시 차감 없음"은 유지되고, 사전 확인과 차감 사이의 경합은 차감이 다시 검사하므로 이중 방어가 됩니다.

**리팩토링이 만든 회귀를 스스로 찾아 되돌린 케이스**라 기록해둡니다. 응답 코드만 봤으면 못 잡았을 것입니다.

## 17. 테스트가 없는 코드를 고치는 순서 — 특성화 테스트 ★

§16의 트랜잭션 리팩토링을 하려는데 **이 프로젝트에는 테스트가 사실상 0개**였습니다. 스프링 컨텍스트가 뜨는지 보는 기본 테스트 하나뿐이었고, 손대려는 250줄짜리 회원가입 메서드를 검증하는 것은 없었습니다.

처음에는 **정적 대조**로 갈음하려 했습니다. 주석과 공백을 제거한 실행 코드 줄을 리팩토링 전후로 전수 비교해서, 사라지거나 새로 생긴 줄이 전부 알려진 동작보존 변환(가드절 반전, if/else → early return, 지역변수 → record 접근자)인지 확인하는 방식입니다.

**이건 "실수로 한 줄 빠뜨리지 않았다"까지만 증명합니다.** 컴파일 여부도, 실제 호출 순서도, 런타임 동작도 증명하지 않습니다. 원리상 안 되는 일이었습니다.

### TDD의 순서를 뒤집는다

새 기능이 아니라 **기존 동작을 보존해야 하는 리팩토링**이므로, red-green-refactor가 아니라 **특성화 테스트(characterization test)** 가 맞습니다. 순서가 반대입니다.

```
1. 리팩토링을 치우고(원본 상태) 테스트를 돌려 green 확인   ← 기준선
2. 리팩토링을 얹고 다시 돌려 green                        ← 동작 보존 증명
```

**1번을 건너뛰면 아무것도 증명하지 못합니다.** 리팩토링이 이미 바꿔버린 동작을 그대로 옮겨 적은 테스트일 수 있기 때문입니다. 그래서 실제로 `git stash`로 원본 상태를 만들어 1번을 먼저 통과시켰습니다.

테스트는 *"이래야 한다"* 가 아니라 **"지금 이렇게 동작한다"** 를 기록합니다. 이상해 보이는 동작도 그대로 붙잡습니다 — 바꾸는 건 그다음 일입니다.

### 같은 테스트가 양쪽 버전에 붙어야 한다

기준선 측정이 성립하려면 **테스트 코드가 리팩토링 전후로 동일**해야 합니다. 이걸 가능하게 한 조건이 둘 있었습니다.

- **공개 시그니처를 안 바꿨습니다.** 컨트롤러도 요청·응답 DTO도 그대로입니다.
- **새로 생긴 의존성은 원본에 없어도 무해합니다.** 리팩토링본에만 있는 `TransactionTemplate`을 목으로 선언해두면, 원본에서는 주입도 스텁 사용도 일어나지 않습니다. Mockito를 `LENIENT`로 두면 그대로 통과합니다.

### 구현 방식이 아니라 결과를 단언한다

특성화 테스트를 쓰다 보면 **구현 detail을 붙잡고 싶어지는 유혹**이 있습니다. 그러면 정당한 리팩토링에도 red가 납니다. 세 번 걸렸습니다.

**① `save` 호출 여부** — 원본은 더티 체킹이라 `save`를 안 부릅니다. 호출을 단언하면 원본에서 red입니다. 그래서 **엔티티 최종 상태**로 단언했습니다.

**② 재화 차감 시점** — 원본은 LLM 전에 차감하고 실패 시 롤백합니다. *"LLM 실패 시 차감이 불렸는가"* 를 단언하면 리팩토링 후 반드시 깨집니다. 호출 순서는 구현 detail이고, **관찰 가능한 결과(최종 차감 없음)** 는 양쪽이 같습니다. 그래서 성공 시 차감 여부만 붙잡았습니다.

**③ 잔액 부족 차단** — 원본은 차감이 던져서, 수정본은 사전 확인으로 막습니다. 그래서 **잔액 부족을 두 방식으로 동시에 표현**했습니다.

```java
when(tokenLedger.canAfford(anyLong(), anyInt())).thenReturn(false);          // 사전 확인 경로
doThrow(new CustomException(INSUFFICIENT_TOKENS)).when(tokenLedger).spend(…); // 차감 경로
```

이러면 어느 구현이든 *"402이면서 LLM 미호출"* 이라는 같은 결과를 검증합니다.

### red를 먼저 본 두 건

**전부 특성화는 아니었습니다.** 없던 동작을 만드는 두 건은 테스트가 먼저 red여야 했습니다.

```
① 잔액 부족을 LLM 호출 전에 차단
   red: NeverWantedButInvoked: aiService.reanalyze(…)     ← LLM이 불리고 있었다
   → 사전 확인 추가 → green

② 탐색 갱신에서 후보 조회를 1회로
   red: TooManyActualInvocations: findByGenderAndIdNot    ← 2회 불리고 있었다
   → 조립/정렬 분리 → green
```

**red를 눈으로 확인하는 게 중요합니다.** 처음부터 green이면 그 테스트는 아무것도 잡고 있지 않다는 뜻입니다.

### 테스트로 못 잡는 것은 실호출로 확인한다

목은 진짜 트랜잭션이 아닙니다. 그래서 이번 작업의 **본래 목적** 두 가지는 단위 테스트로 증명되지 않습니다.

- 커넥션 점유가 실제로 줄었는가 → `performance_schema` 폴링으로 측정(22.5초 → 0초)
- LLM이 실패해도 계정이 남는가 → 로컬에서 모델명을 없는 이름으로 바꿔 실패를 강제하고 DB 확인

두 번째는 **비용이 0원**이라는 점이 좋았습니다. 존재하지 않는 모델은 즉시 404로 거절되므로 토큰을 쓰지 않습니다. 실패 경로를 값싸게 재현하는 방법을 찾는 게 검증 설계의 절반입니다.

### 커밋을 테스트와 리팩토링으로 번갈아 쌓는다

각 리팩토링 커밋 **바로 앞이 그 안전망**이 되도록 배치했습니다.

```
test(auth)        회원가입 특성화 15개      ← 원본에서 green
refactor(auth)    트랜잭션 분리 + 251줄 추출  ← 같은 테스트로 green
test(persona)     재분석·생성 특성화 12개
refactor(persona) …
```

문제가 생겼을 때 어느 커밋을 되돌리면 되는지가 이력에서 바로 읽힙니다. 그리고 **동작이 바뀌는 변경(트랜잭션 경계)과 안 바뀌는 변경(메서드 추출)을 섞지 않았습니다.** 섞으면 깨졌을 때 둘 중 뭐 때문인지 가릴 수 없습니다.

### 결과

```
테스트          0개 → 52개
LLM 호출이 트랜잭션 안에 있는 곳   5곳 → 0곳
커넥션 점유     22.5초 → 0초      (실측)
가장 긴 메서드  251줄 → 48줄      (7개로 추출)
공개 API 변경   0                 (컨트롤러·DTO·에러코드 무변경)
```

마지막 줄은 말이 아니라 **명령 하나로 증명**했습니다.

```bash
git diff --name-only <base> -- '*Controller.java' '*/dto/*' '*ErrorCode.java'
# → 0건
```

프론트에 *"바뀐 것 없습니다"* 라고 말할 때, 근거를 같이 줄 수 있는 형태로 만들어두는 편이 서로 편합니다.

## 코딩 정책 (팀 컨벤션)

실제로 지킨 프로젝트 규칙입니다.

### API 계약 우선
- **요청/응답 구조를 임의로 바꾸지 않는다.** 프론트가 참조하는 계약이므로, 필드 추가/삭제/이름변경은 합의 후. AI 프롬프트를 바꿔도 **출력 JSON 구조는 유지**(파싱 호환성).

### Jackson 직렬화 규칙
- `boolean isNewUser` → 직렬화 시 `newUser`(is 제거), `Boolean isNewUser` → `isNewUser`(유지).
- 명세와 실제 응답을 일치시키려 **`@JsonProperty`를 명시**하고, 문서 작성 전 실제 JSON 응답을 확인.

### 커밋 단위
- **한 도메인은 전 계층(엔티티~컨트롤러) 완료 후 한 커밋.** 횡단 리팩토링은 별도 커밋.
- 빌드/배포/커밋은 명시적으로만 — 자동 실행 안 함.

### 로깅
- 공통은 조용(INFO), 개발 프로필만 DEBUG. PII(전화번호 평문 등)는 로그에 남기지 않음.

### 예외/에러
- 도메인 에러는 `ErrorCode` enum(HTTP status + 코드 + 메시지)으로 표준화, 프론트가 코드로 분기.

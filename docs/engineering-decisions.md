# 엔지니어링 결정

"무엇을 만들었나"가 아니라 **왜 그 선택을 했나**를 남깁니다. 고르지 않은 선택지와 그 이유, 그리고 그 선택이 치른 대가까지 씁니다.

---

## 1. 포그라운드에서는 OS 배너를 끄고 인앱 토스트만 쓴다

| 선택지 | 판단 |
|---|---|
| OS 배너 그대로 노출 | ✗ 앱을 보고 있는 사람의 화면을 가리고, 탭 동선이 앱 밖으로 나갔다 돌아온다 |
| **배너를 끄고 인앱 토스트로 대체** | **채택** |
| 둘 다 노출 | ✗ 같은 알림이 두 번 보인다 |

**대가를 알고 골랐습니다.** 이 설계 때문에 *"앱을 켜둔 채로 푸시를 눌렀다"* 는 사용자 제보가 **성립하지 않게** 됩니다. 실제로 지급 누락 제보를 분석할 때, 제보자가 탭한 것은 포그라운드 배너가 아니라 백그라운드 배너였다는 것부터 짚어야 했습니다. 사용자의 진술과 앱의 실제 상태가 어긋날 수 있는 구조라는 걸 문서로 남겨 뒀습니다.

SDK가 표시 옵션을 신규 스펙(`banner` / `list` 분리)으로 바꾸면서 기존 옵션이 deprecated 됐을 때도, **의도(포그라운드 배너 없음)를 유지한 채** 스펙만 옮겼습니다. 네이티브가 세 플래그를 OR로 합쳐 판정하기 때문에 값 하나만 바꾸면 동작이 뒤집힙니다.

## 2. 보상 안내는 토스트가 아니라 "확인을 눌러야 닫히는" 전체 화면

- **근거**: 재화를 지급했는데 사용자가 **받은 줄 모르면 이벤트를 한 의미가 없습니다.** 토스트는 몇 초 뒤 사라지고, 스크롤 중이거나 다른 알림과 겹치면 놓칩니다.
- **대가**: 화면을 통째로 가리는 강한 UI라서, **잘못 뜨면 앱을 못 쓰게 됩니다.** 실제로 이 결정이 프리징 사고로 이어졌습니다 → [트러블슈팅 10](./troubleshooting.md)
- **사고 후 보정**: 강한 UI를 포기하는 대신, **실패해도 화면이 잠기지 않는 구조**로 바꿨습니다(Modal → 절대배치 뷰, 애니메이션 결과와 무관한 정리). 목적은 유지하고 실패 모드만 낮춘 선택입니다.

## 3. 미확인 보상을 다시 띄우기 위해 서버에 필드를 요청했다

- **문제**: 확인을 누르지 않고 앱을 끄면 보상 안내가 사라집니다. 지급은 됐는데 사용자는 모르는 상태가 남습니다.
- **선택지**
  - (a) 로컬에 저장했다가 다음 실행에 복원 → **채택**
  - (b) 포기하고 알림함 기록으로만 대체 → 알림함을 안 보는 사용자에게는 여전히 미인지
- **(a)에는 전제가 하나 필요했습니다**: *"이미 본 보상"* 을 구분할 키. 없으면 앱을 켤 때마다 같은 보상이 **무한 재노출**됩니다.
- **서버에 슬롯 식별자 추가를 요청**하고, 그 필드가 없는 동안은 **저장 자체를 건너뛰도록** 만들었습니다. 필드가 없으면 기능이 조용히 비활성될 뿐, 오작동(무한 재노출)은 하지 않습니다.
- 서버가 필드를 내려주기 시작한 뒤 실기기에서 검증했습니다 — 확인을 누르지 않고 강제 종료 → 재실행 시 그대로 복원.

## 4. 서버가 제안한 필드를 거절했다

실시간 수신 알림에 `id`가 없어 목록이 깨지자, 서버 쪽에서 **"슬롯 식별자를 payload에 실어주겠다"** 고 제안했습니다.

**거절했습니다.** 그 값은 알림 테이블의 id가 아니어서, 목록을 다시 불러오면 **같은 알림이 서로 다른 키로 두 번** 들어옵니다. 문제를 해결하는 대신 형태만 바꿔 놓는 제안이었습니다.

**대신 요청한 것**은 알림 테이블 id였습니다. 그러면
- 실시간 수신분과 목록 조회분의 키가 같아져 **중복이 자연히 합쳐지고**,
- 푸시를 탭했을 때 **읽음 처리 API를 부를 수 있습니다**(지금은 id가 없어 미읽음으로 남습니다).

그와 별개로 앱은 **"id 없는 항목은 목록에 넣지 않는다"** 로 방어했습니다. 서버가 무엇을 보내든 리스트가 깨지지 않아야 하고, 이 방어는 서버 배포를 기다리지 않아도 됩니다. **협상과 방어를 분리한 선택**입니다.

## 5. 배포 순서 요구를 실측으로 반박했다

서버가 적립 경로의 락 문제를 고치면서, **"앱의 즉시 호출 추가는 서버 배포 뒤에 켜 달라"** 고 요청했습니다. 근거는 *"지금까지는 두 호출이 서로 어긋나 있었는데, 즉시 호출을 넣으면 기동 묶음 안으로 들어와 겹친다"* 였습니다.

앱 로그로 **세 번 실측**했습니다.

```
11:20:17.590  check-in
11:20:17.599  ping        9ms
11:44:53.654  check-in
11:44:53.660  ping        6ms
11:57:27.130  check-in
11:57:27.138  ping        8ms
```

**셋 다 즉시 호출을 넣기 전 코드입니다.** 두 요청은 같은 화면 진입 시점에 발사되므로 구조적으로 겹칩니다. 순서를 미뤄도 충돌은 그대로 남고, 미루는 동안 사용자 쪽 지연만 유지됩니다.

**동시에, 순서가 실제로 걸린 항목은 따로 찾아 인정했습니다.** 기동 시 같은 요청이 2.6초 간격으로 두 번 나가는 중복이 있었는데, **그 중복이 우연히 재시도 역할**을 하고 있었습니다. 서버 락 수정 전에 중복만 없애면 복구 경로가 사라집니다. 그 항목은 서버 배포 뒤로 미뤘습니다.

> 서버 측 기록에는 이 복구가 "60초 타이머 덕분"으로 적혀 있었지만, 같은 초에 복구된 사례가 있어 60초 주기로는 설명되지 않았습니다. 2.6초 간격의 중복 호출이라야 맞습니다.

**반박과 수용을 같은 기준(실측)으로 처리한 것**이 이 건의 요점입니다.

## 6. 무선 업데이트 식별값을 사용자 화면에 노출했다

- **문제**: 버그 수정만 담긴 번들은 화면에 보이는 변화가 없습니다. **배포한 게 이 기기에 내려왔는지 확인할 방법이 없었습니다.** 배포 대시보드는 "서버에 올라갔다"까지만 알려주고 기기별 수신 여부는 알려주지 않습니다.
- **선택지**
  - (a) 관리자 계정에만 노출 → ✗ **검증 대상은 앱 번들이지 계정이 아닙니다.** 운영 앱에 관리자 계정으로 로그인해야만 확인되는 건, 측정하려는 것과 무관한 조건을 하나 더 만드는 일입니다
  - (b) 숨겨진 진입(버전 여러 번 탭) → ✗ 구현 대비 이득이 적음
  - (c) **버전 뒤에 빌드번호처럼 붙이기** → **채택**
- **표기 규칙**: 괄호가 있으면 업데이트 적용, 없으면 스토어 번들 그대로.
  ```
  v1.1.9                스토어 번들 그대로
  v1.1.9 (0804.1820)    08/04 18:20 발행분이 적용됨
  ```
  사용자 눈에는 평범한 빌드번호로 보이고, 개발자는 발행 시각과 바로 대조할 수 있습니다.
- **부수 효과 하나가 오히려 정확합니다**: 업데이트를 내려받아도 **다음 실행 전까지는 괄호가 안 붙습니다.** "2회차 실행부터 적용"이라는 규칙이 화면에 그대로 드러납니다.
- **안전장치**: 개발 빌드·웹에서는 표시가 생략되고, 값을 읽지 못하면 빈 문자열입니다. **이 표시 때문에 화면이 깨지는 일은 없어야 한다**를 기준으로 했습니다.

## 7. 네이티브 설정을 "기억"이 아니라 git과 빌드 가드로 지킨다

- **사고**: 네이티브 프로젝트를 재생성하는 명령이 수동으로 넣어 둔 설정(소셜 로그인 SDK 키, 무선 업데이트 설정)을 통째로 날렸습니다. 그 결과 특정 소셜 로그인이 **전면 불가**했고, 동의 화면에 라이브러리 기본값이 노출됐습니다.
- **선택지**
  - (a) 절차를 문서화하고 사람이 챙긴다 → ✗ **이미 한 번 실패한 방식입니다**
  - (b) **생성물을 git 추적 대상으로 올리고, 릴리즈 빌드에 값 검증 가드를 물린다** → **채택**
- **(b)를 고른 결정적 이유**: 무선 업데이트 설정은 값이 틀려도 **앱이 에러를 내지 않고 조용히 업데이트를 무시합니다.** 사후에 발견하기가 매우 어려운 종류라, 사람의 주의력에 맡길 수 없었습니다.
- 같은 원칙으로 릴리즈 env 가드도 만들어 두었습니다 → [트러블슈팅 1](./troubleshooting.md), [`api-and-build.md`](./api-and-build.md)

## 8. 검증 방법 자체를 설계한다

버그 수정은 "고쳤다"보다 **"고쳐진 걸 어떻게 보이느냐"** 가 어렵습니다. 이번 사이클에서 실제로 쓴 방법들입니다.

- **재현이 안 되는 조건은 서버에 만들어 달라고 요청했습니다.** 실패 시 재시도 검증에는 실패 자체가 필요한데, 서버가 이미 고쳐서 실패를 만들 수 없었습니다. 로컬 전용 강제 실패 플래그를 요청해 켜고 검증한 뒤 껐습니다.
- **로컬 알림으로 대체할 수 있는 것과 없는 것을 갈랐습니다.** 표시 억제·수신 즉시 동작은 로컬 알림으로 같은 경로를 탑니다. 하지만 **FCM 핸들러 중복은 실제 푸시가 아니면 그 코드가 실행되지 않습니다.** 대체 검증으로 덮지 않고 실제 발송을 요청했습니다.
- **완전 종료 상태 테스트에는 함정이 있습니다.** 프로세스를 강제 종료(`force-stop`)하면 예약된 알람이 지워지고, 앱이 "정지 상태"가 되어 **푸시 자체가 배달되지 않습니다.** 사용자가 최근 앱에서 밀어 닫는 것과 다릅니다. 프로세스만 죽이는 방식으로 바꿔야 실제 상황과 같아집니다.
- **관측 도구도 맞춰 바꿨습니다.** 푸시 도착 순간의 화면(토스트와 오버레이가 겹치는 구간)은 몇 초 만에 사라져 수동으로는 못 잡습니다. 로그를 1초 간격으로 폴링하다가 도착을 감지하면 자동으로 연속 캡처하도록 만들었습니다. 스트림에 건 초기 방식은 버퍼링 때문에 첫 발송을 놓쳤고, 그 실패를 근거로 방식을 바꿨습니다.

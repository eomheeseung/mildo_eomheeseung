# 실운영 트러블슈팅

실서비스를 운영하며 진단·해결한 사례입니다. "왜 그런지"를 데이터로 규명한 과정에 초점을 뒀습니다.

## 1. 소셜 가입자가 설문 완료 직전에 막히던 버그

**증상** — 카카오로 가입한 유저가 12문항 페르소나 설문을 다 채우고 "완료"를 누르는 순간 "허용되지 않은 이메일 도메인" 오류. @kakao.com 가입자 15명 중 완주 0명.

**원인** — 이메일 도메인 화이트리스트 검증이 **v1(이메일 가입) 경로에만** 있고, 소셜 가입이 타는 `signupWithPersona` 경로의 화이트리스트에는 `kakao.com`·`daum.net`·`nate.com`·`hanmail.net`이 누락돼 있었음. 소셜 로그인은 통과하지만 마지막 가입 확정에서 막히는 구조.

**해결** — 화이트리스트를 통합하고 소셜 도메인을 추가. 프로덕션 로그와 DB로 "완주 0명"을 먼저 정량 확인한 뒤 수정 → 배포 후 send-code 200 검증.

## 2. NICE 본인인증 CI 도난 (1인 1계정)

**증상** — 재인증할 때마다 기존 계정의 CI/DI가 새 계정으로 옮겨가, 기존 계정이 본인인증을 잃음.

**원인** — 재인증 로직이 CI 중복 검사 없이 새 계정에 CI를 **덮어씀**.

**해결** — `users.ci` 유니크 제약 + "살아있는 계정이 이미 그 CI를 보유하면 가입 거부(U007)". 탈퇴 계정의 CI는 승계 허용. 운영 데이터로 기존 CI 보유 계정이 전부 distinct임을 확인해 유니크 인덱스가 깨끗이 생성되는지 사전 검증.

## 3. push-consent 403 — 백엔드가 아니었다

**증상** — 알림 동의 API가 403.

**규명** — 처음엔 서버 로직을 의심했으나, 서버 로그에 해당 요청이 **0건**. Spring Security에서 토큰 누락은 401이 아니라 403으로 떨어짐 → **클라이언트가 Authorization 헤더를 안 실은 것**. 도메인 이전(dev.mildo.us → mildo.us) 중 origin-scoped localStorage의 토큰이 유실된 것이 원인. 백엔드는 정상이었음을 데이터로 입증하고, 프론트에 원인을 전달.

**교훈** — "500이 아닌 4xx는 클라이언트 계약 문제일 수 있다"를 로그 부재로 먼저 확인.

## 4. Claude 5 세대 API 대응

**증상** — 최신 모델(sonnet-5 등)로 바꾸자 ①`temperature is deprecated`(400) ②그 후 `No content to map`(빈 응답 파싱 실패).

**원인** — ①신세대 모델이 `temperature` 파라미터를 폐기. ②복잡한 프롬프트에서 응답 `content[0]`에 `thinking` 블록이 자동 삽입돼, 기존의 `content[0].text` 추출이 빈 문자열을 반환.

**해결** — ①지원 모델에만 `temperature`를 싣도록 분기. ②`type=text`인 **첫 블록**을 찾아 추출(구형 모델은 동작 변화 없음). 운영 서버에서 직접 API를 curl로 때려 `content_blocks=2, block0=thinking`을 확인한 뒤 수정.

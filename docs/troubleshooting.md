# 트러블슈팅 (실운영)

실서비스를 빌드·배포·운영하며 진단하고 해결한 사례입니다. "무엇을 고쳤나"보다 **원인을 어떻게 좁혔나**를 남깁니다.

## 1. 로컬 서버 주소가 프로덕션 앱에 박힘 → 빌드 가드로 재발 차단

- **증상**: 라이브에 나간 빌드가 로컬 백엔드(LAN·http)를 가리켜 실사용자가 접속 불가.
- **원인**: Expo가 `.env.local`을 `.env`보다 우선 읽는다. 릴리즈 전에 `.env`를 운영으로 바꿔도, 개발용 `.env.local`의 로컬 IP가 덮어써서 번들에 박혔다.
- **해결**: 임기응변(그때그때 `.env.local` 비활성)에 기대지 않고, **Expo와 동일한 우선순위로 실제 값을 재현해 사설망이면 빌드를 실패시키는 가드**를 만들어 `app.config.js`·`build.gradle`에 물렸다. 이제 사람이 깜빡해도 파이프라인이 막는다. → [`api-and-build.md`](./api-and-build.md)

## 2. 릴리즈에서 어트리뷰션이 통째로 죽어있던 문제

- **증상**: 광고/리퍼럴 어트리뷰션 SDK가 릴리즈에서만 동작 안 함.
- **원인**: SDK 키(`EXPO_PUBLIC_*`)가 **개발용 `.env.local`에만** 있었는데, 릴리즈 빌드는 오배포 방지를 위해 `.env.local`을 비활성한다. 그래서 릴리즈 번들엔 키가 안 구워져 SDK가 빈 키로 초기화됐다.
- **해결**: `EXPO_PUBLIC_*` 값은 릴리즈에서도 살아있는 운영 env에 두도록 이동. 빌드 후 **번들에 값이 실제로 박혔는지까지 검증**하는 절차를 추가. (오배포 방지 장치가 만든 부작용을, 검증으로 되짚어 찾은 사례.)

## 3. 리퍼럴 딥링크가 특정 진입 경로에서 안 잡힘

- **증상**: 초대 링크로 앱은 열리는데 초대자(inviter)가 저장되지 않는 경우가 있었다.
- **진단**: 콜백에 무조건 로그를 찍어, `onDeepLink`이 **호출 자체가 안 된 것**을 확인. AppsFlyer의 UDL은 신규 설치(deferred) 귀속엔 강하지만, 직접(raw) 스킴 진입은 못 잡는 케이스가 있었다.
- **해결**: `expo-linking`으로 스킴 URL의 파라미터를 직접 파싱하는 **백업 경로**를 얹어(콜드/웜스타트 모두), 어느 경로로 들어와도 inviter가 유실되지 않게 이중화. → [`../code-excerpts/analytics.ts`](../code-excerpts/analytics.ts)

## 4. 동의 저장 403 — "백엔드 탓"으로 오진했다가 원인 재규명

- **증상**: 약관/알림 동의 저장이 403.
- **처음 진단(오진)**: "토큰이 안 붙었다"고 봤다.
- **실제 원인**: 그 시점은 **아직 계정이 없어** `/users/me/*` 자체를 못 치는 단계였다(토큰 유무 문제가 아님).
- **해결**: 동의를 가입 요청 body에 실어 보내고, 가입 후 best-effort로 재저장하는 **deploy-order-safe** 구조로 재설계. 백엔드 배포 순서에 무관하게 동작. → [`state-management.md`](./state-management.md)

## 5. 비ASCII 사용자 경로에서 Android 네이티브 빌드 크래시

- **증상**: 특정 개발 환경에서 릴리즈 빌드가 prefab/CMake 단계에서 IOException.
- **원인**: Gradle이 캐시/임시 디렉토리로 쓰는 사용자 홈 경로에 비ASCII 문자가 있으면 네이티브 툴체인이 경로를 깨뜨렸다. `local.properties`의 단일 백슬래시가 Java properties 파서에서 뭉개진 것도 겹쳤다.
- **해결**: Gradle 캐시/TEMP를 ASCII 경로로 강제하고, 경로는 슬래시로 정규화. 빌드 전 체크리스트에 편입해 재발 방지.

## 6. 관리자 사이드바 스크롤이 메뉴 클릭마다 최상단으로 리셋

- **원인**: 메뉴 선택을 `location.hash` 변경으로 처리했는데, 이게 fragment 네비게이션 → 라우터가 화면을 remount → ScrollView가 새로 만들어짐.
- **해결**: `history.pushState`로 바꿔 remount 없이 상태만 갱신하고, `popstate`/`hashchange` 리스너로 동기화. 스크롤 위치 보존.

## 7. 웹 초대 링크 복사가 http/LAN에서 안 됨

- **원인**: `navigator.clipboard`는 **보안 컨텍스트(https/localhost)에서만** 동작. LAN·http로 접속하면 `undefined`라 복사가 조용히 실패하는데 "복사됨"이라고 안내해 오해를 줬다.
- **해결**: 레거시 `execCommand('copy')` 폴백을 얹고, **실제 복사 성공 여부에 따라 안내 문구를 정직하게** 표기.

## 8. 출석 보상이 하루 종일 안 들어오던 문제 — 예외를 던지지 않는 API 래퍼

- **증상**: 어느 날 일부 사용자에게 데일리 출석 보상이 지급되지 않았다. 한 사용자는 **2시간 51분 뒤**에야 들어왔고, 그 사이 공통점은 "앱을 강제 종료했다 다시 켰다"였다.
- **서버 쪽 원인**: 적립 로직이 락 없이 계정 행을 읽어, 앱 기동 시 함께 나가는 다른 적립 요청과 충돌하면 `409`로 지고 롤백됐다.
- **앱 쪽 원인(핵심)**: 앱에는 "오늘 이미 호출했다"를 기억하는 하루 1회 가드가 있고, 실패 시 그 가드를 풀어 재시도하게 돼 있었다. **그런데 그 해제 코드가 `catch` 블록 안에만 있었다.** API 래퍼가 4xx/5xx에서 예외를 던지지 않고 `{ success: false }`를 반환하는 구조라 **`catch`가 아예 실행되지 않았다.** 가드가 오늘 날짜로 박힌 채 남아, 프로세스가 죽기 전까지 재시도가 없었다.
- **해결**: 실패 판정을 예외가 아니라 응답의 성공 플래그로 바꿨다. 서버에 강제 실패 플래그를 요청해 실기기에서 재현·검증했다.
  ```
  14:13:47  check-in → 409
  14:14:57  포그라운드 복귀 시 check-in 재호출됨   ← 수정 후에만 나오는 줄
  ```
- **남긴 것**: 서버(락 없음)와 앱(가드 미해제) **양쪽이 겹쳐야** 나는 문제였다. 서버만 고쳤다면 네트워크 오류 같은 다른 실패에서 여전히 하루를 날렸을 것이다. 원인을 한쪽에서 찾고 멈추지 않은 게 이 건의 요점이다.

## 9. 푸시 한 건이 7번 처리되던 문제 — 개발 환경이 버그를 가린 사례

- **증상**: 같은 알림이 알림함에 2줄로 쌓이고, 서버 로그엔 같은 요청이 2.5초 간격으로 2발 찍혔다.
- **진단**: 앱 로그를 보니 **동일한 `messageId`가 7번 처리**되고 있었다. 포그라운드 FCM 핸들러가 구독 해제 없이 매번 새로 등록되는 구조였고, 등록 함수 호출부가 로그인·세션복구·동의화면·권한동기화 **4곳**이었다.
- **★ 고친 뒤에도 7회 그대로였다**: Fast Refresh는 모듈 코드만 교체할 뿐 **이미 등록된 구독은 해제하지 못한다.** 수정 전에 쌓인 핸들러가 그대로 살아 있어 증상이 재현됐다. 앱을 완전히 재시작해야 판정이 됐다.
  ```
  수정 후 · 오래된 프로세스     7회
  수정 후 · 완전 재시작 후      1회
  ```
- **해결**: 구독 해제 함수를 보관했다가 재등록 전에 호출. 호출부를 줄이는 대신 **구독 쪽을 멱등하게** 만들었다 — 4곳 각각에 이유가 있어서 호출 자체를 없애는 건 다른 회귀를 만든다.
- **남긴 것**: "고쳤는데 그대로다"를 만나면 코드보다 **프로세스 나이를 먼저 의심해야 한다**는 걸 검증 절차에 넣었다.

## 10. 화면은 멀쩡한데 아무것도 안 눌리던 프리징

- **증상**: 알림으로 앱에 들어오면 화면이 멈춘다. 강제 종료 외에 빠져나올 방법이 없다. 다시 켜면 보상 화면과 출석 안내가 버벅이며 순차로 떴다.
- **진단**: 크래시 로그가 없다 = 앱은 살아 있다. 전체화면 보상 오버레이가 `Modal`이었고, **닫기 처리가 애니메이션 완료 콜백(`finished`) 안에만** 있었다. 애니메이션이 중간에 끊기면(백그라운드 전환 등) 마운트 상태가 `true`로 남아 **투명한 전체화면 Modal이 모든 터치를 흡수**한다.
- **겹친 원인 하나 더**: 기동 스플래시도 `Modal`이라, 둘이 겹치는 순간 iOS가 두 번째 present를 조용히 무시한다. 이 경우 보상 화면은 **영영 뜨지 않는다**(지급은 됐는데 사용자는 못 본다).
- **해결**: Modal을 걷어내고 **최상단 절대배치 뷰**로 바꿨다. 정리 조건을 `finished`에서 분리해 애니메이션이 끊겨도 반드시 닫히게 하고, 등장 애니메이션이 아예 안 도는 경우까지 대비해 일정 시간 뒤 값을 확정하도록 했다.
- **남긴 것**: Modal 중첩은 실패 모드가 **"안 보임"과 "터치 잠김"** 두 방향으로 갈린다. 뷰로 내리면 최악이 "가려짐"이 되고, 가린 것이 사라지면 자연히 드러난다.

## 11. 알림함 진입 시 렌더 크래시 — id 없는 알림

- **증상**: 알림함을 열면 `Cannot read property 'toString' of undefined`.
- **진단**: 리스트의 `keyExtractor`가 `item.id.toString()`이었다. 목록 API 응답에는 `id`가 항상 있는데, **실시간 푸시로 받은 알림에만 없었다**(그 타입의 payload에 알림 테이블 id가 빠져 있었다). 서버 응답을 전수 확인해 "서버가 빠뜨린 게 아니라 실시간 경로만 다르다"를 갈라낸 게 진단의 분기점이었다.
- **더 이상했던 것**: 바로 위 수신 리스너는 **`id`가 없을 수 있다는 걸 이미 알고 있었다** — 중복 검사만 건너뛰고 삽입은 그대로 했다. 알고도 렌더링 쪽을 안 맞춘 상태였다.
- **해결**: 근본은 **id 없는 항목을 목록에 넣지 않는 것**. 토스트는 별도 컴포넌트가 받으므로 사용자에게는 그대로 보이고, 정식 항목은 다음 목록 조회에서 서버 id와 함께 들어온다. `keyExtractor` 방어는 이중으로 남겼다.

## 12. 아이폰에서만 보상이 늦게 지급되던 문제 — AppState는 3상태다

- **증상**: "알림을 눌렀는데 지급이 안 된다"는 제보. **안드로이드에서는 재현되지 않았다.**
- **진단**: 앱은 포그라운드 상주 중 60초마다 서버에 신호를 보내고, 백그라운드로 가면 멈춘다. 복귀 시 즉시 1발을 쏘는데 그 함수 첫 줄이 `if (timer) return`이었다. **iOS의 AppState는 `active` / `inactive` / `background` 3상태인데 인터벌 정지는 `background`에서만** 한다. 알림센터를 내려서 탭하면 `inactive → active`라 타이머가 살아 있고 → 조기 return → **다음 틱까지 최대 60초** 대기.
- **★ 안드로이드로는 원리상 재현이 불가능했다**: React Native에서 `inactive`는 iOS 전용 상태다. "안드로이드에서 안 되는 재현"이 곧 원인의 단서였다.
- **해결**: 판정 기준을 **타이머 유무 → 마지막 호출 시각**으로 바꿨다. 원래 이 가드는 제어센터를 잠깐 열었다 닫는 깜빡임에 재발화하는 걸 막으려던 것인데, **알림 탭까지 같이 막고 있었다.**

## 13. iOS가 안드로이드 버전 번호를 자기 것으로 읽던 문제

- **증상**: 앱 업데이트 게이트(권고/강제)가 iOS에서 잘못된 버전으로 판정될 수 있는 상태였다.
- **원인**: 두 플랫폼의 버전 번호를 **의도적으로 다르게** 관리하는데(iOS는 네이티브 설정을 직접 올리는 구조), 버전을 읽는 코드가 공통 설정 파일 하나만 보고 있었다.
- **위험**: 최소지원버전을 올리는 순간 **최신 iOS 사용자까지 강제 업데이트 모달에 갇힌다.** 사용자가 스스로 빠져나올 수 없는 종류의 사고다.
- **해결**: 플랫폼별 실제 버전을 읽는 **단일 진입점**을 만들고, 파싱이 조금이라도 불확실하면 아무 조치도 하지 않도록(fail-safe) 규칙을 못박았다. 이 기능 때문에 앱을 못 쓰게 되는 일만은 없어야 한다는 게 설계 기준이었다.

## 14. 24시간마다 로그아웃되던 문제 — 원인이 우리 쪽이 아니었다

- **증상**: 사용자가 하루가 지나면 로그인이 풀린다는 제보.
- **처음 의심**: 토큰 갱신 로직. 앱은 `401`을 받으면 리프레시를 돌리게 돼 있었다.
- **실제 원인**: 서버가 **만료된 토큰에 `401`이 아니라 `403`을 반환**하고 있었다. 갱신은 `401`에서만 발화하므로 아예 트리거되지 않았다. 앱 코드에는 잘못이 없었고, 재현도 앱만 봐서는 되지 않았다.
- **판단**: `403`을 갱신 트리거에 추가하는 건 **거부했다.** `403`은 정지·차단·권한 부족에도 쓰이는 코드라, 갱신을 걸면 차단된 계정이 무한히 재시도한다. 상태 코드의 의미를 흐리는 대신 **서버가 `401`을 주도록** 요청했다.
- **앱이 한 것**: 서버 수정이 나가기 전 이미 배포된 구버전을 위해, 인증 상태 불명확 시 사용자 정보 재조회로 한 번 더 확인하는 보완 경로만 얹었다.
- **남긴 것**: 남의 시스템이 원인일 때도 **관측과 추정을 구분해서** 전달해야 한다. "서버가 403을 준다"는 관측이고, "그래서 갱신이 안 돈다"까지가 검증된 인과였다.

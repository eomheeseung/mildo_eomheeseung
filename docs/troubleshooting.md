# 트러블슈팅 (실운영)

실서비스를 빌드·배포·운영하며 진단하고 해결한 사례입니다. "무엇을 고쳤나"보다 **원인을 어떻게 좁혔나**를 남깁니다.

## 1. 로컬 서버 주소가 프로덕션 앱에 박힘 → 빌드 가드로 재발 차단

- **증상**: 라이브에 나간 빌드가 로컬 백엔드(LAN·http)를 가리켜 실사용자가 접속 불가.
- **원인**: Expo가 `.env.local`을 `.env`보다 우선 읽는다. 릴리즈 전에 `.env`를 운영으로 바꿔도, 개발용 `.env.local`의 로컬 IP가 덮어써서 번들에 박혔다.
- **해결**: 임기응변(그때그때 `.env.local` 비활성)에 기대지 않고, **Expo와 동일한 우선순위로 실제 값을 재현해 사설망이면 빌드를 실패시키는 가드**를 만들어 `app.config.js`·`build.gradle`에 물렸다. 이제 사람이 깜빡해도 파이프라인이 막는다. → [`api-and-build.md`](./api-and-build.md)

## 2. 릴리즈에서 어트리뷰션이 통째로 죽어있던 문제

- **증상**: 광고/리퍼럴 어트리뷰션 SDK가 릴리즈에서만 동작 안 함.
- **원인**: SDK 키(`EXPO_PUBLIC_*`)가 **개발용 `.env.local`에만** 있었는데, 릴리즈 빌드는 오배포 방지를 위해 `.env.local`을 비활성한다. 그래서 릴리즈 번들엔 키가 안 구워져 SDK가 빈 키로 초기화됐다.
- **해결**: `EXPO_PUBLIC_*` 값은 릴리즈에서도 살아있는 운영 env에 두도록 이동. 빌드 후 **번들에 값이 실제로 박혔는지까지 검증**하는 절차를 추가. (오배포 방지 장치가 만든 부작용을, 검증으로 되짚어 찾은 사례.)

## 3. 리퍼럴 딥링크가 특정 진입 경로에서 안 잡힘

- **증상**: 초대 링크로 앱은 열리는데 초대자(inviter)가 저장되지 않는 경우가 있었다.
- **진단**: 콜백에 무조건 로그를 찍어, `onDeepLink`이 **호출 자체가 안 된 것**을 확인. AppsFlyer의 UDL은 신규 설치(deferred) 귀속엔 강하지만, 직접(raw) 스킴 진입은 못 잡는 케이스가 있었다.
- **해결**: `expo-linking`으로 스킴 URL의 파라미터를 직접 파싱하는 **백업 경로**를 얹어(콜드/웜스타트 모두), 어느 경로로 들어와도 inviter가 유실되지 않게 이중화. → [`../code-excerpts/analytics.ts`](../code-excerpts/analytics.ts)

## 4. 동의 저장 403 — "백엔드 탓"으로 오진했다가 원인 재규명

- **증상**: 약관/알림 동의 저장이 403.
- **처음 진단(오진)**: "토큰이 안 붙었다"고 봤다.
- **실제 원인**: 그 시점은 **아직 계정이 없어** `/users/me/*` 자체를 못 치는 단계였다(토큰 유무 문제가 아님).
- **해결**: 동의를 가입 요청 body에 실어 보내고, 가입 후 best-effort로 재저장하는 **deploy-order-safe** 구조로 재설계. 백엔드 배포 순서에 무관하게 동작. → [`state-management.md`](./state-management.md)

## 5. 비ASCII 사용자 경로에서 Android 네이티브 빌드 크래시

- **증상**: 특정 개발 환경에서 릴리즈 빌드가 prefab/CMake 단계에서 IOException.
- **원인**: Gradle이 캐시/임시 디렉토리로 쓰는 사용자 홈 경로에 비ASCII 문자가 있으면 네이티브 툴체인이 경로를 깨뜨렸다. `local.properties`의 단일 백슬래시가 Java properties 파서에서 뭉개진 것도 겹쳤다.
- **해결**: Gradle 캐시/TEMP를 ASCII 경로로 강제하고, 경로는 슬래시로 정규화. 빌드 전 체크리스트에 편입해 재발 방지.

## 6. 관리자 사이드바 스크롤이 메뉴 클릭마다 최상단으로 리셋

- **원인**: 메뉴 선택을 `location.hash` 변경으로 처리했는데, 이게 fragment 네비게이션 → 라우터가 화면을 remount → ScrollView가 새로 만들어짐.
- **해결**: `history.pushState`로 바꿔 remount 없이 상태만 갱신하고, `popstate`/`hashchange` 리스너로 동기화. 스크롤 위치 보존.

## 7. 웹 초대 링크 복사가 http/LAN에서 안 됨

- **원인**: `navigator.clipboard`는 **보안 컨텍스트(https/localhost)에서만** 동작. LAN·http로 접속하면 `undefined`라 복사가 조용히 실패하는데 "복사됨"이라고 안내해 오해를 줬다.
- **해결**: 레거시 `execCommand('copy')` 폴백을 얹고, **실제 복사 성공 여부에 따라 안내 문구를 정직하게** 표기.

## 8. 출석 보상이 하루 종일 안 들어오던 문제 — 예외를 던지지 않는 API 래퍼

- **증상**: 어느 날 일부 사용자에게 데일리 출석 보상이 지급되지 않았다. 한 사용자는 **2시간 51분 뒤**에야 들어왔고, 그 사이 공통점은 "앱을 강제 종료했다 다시 켰다"였다.
- **서버 쪽 원인**: 적립 로직이 락 없이 계정 행을 읽어, 앱 기동 시 함께 나가는 다른 적립 요청과 충돌하면 `409`로 지고 롤백됐다.
- **앱 쪽 원인(핵심)**: 앱에는 "오늘 이미 호출했다"를 기억하는 하루 1회 가드가 있고, 실패 시 그 가드를 풀어 재시도하게 돼 있었다. **그런데 그 해제 코드가 `catch` 블록 안에만 있었다.** API 래퍼가 4xx/5xx에서 예외를 던지지 않고 `{ success: false }`를 반환하는 구조라 **`catch`가 아예 실행되지 않았다.** 가드가 오늘 날짜로 박힌 채 남아, 프로세스가 죽기 전까지 재시도가 없었다.
- **해결**: 실패 판정을 예외가 아니라 응답의 성공 플래그로 바꿨다. 서버에 강제 실패 플래그를 요청해 실기기에서 재현·검증했다.
  ```
  14:13:47  check-in → 409
  14:14:57  포그라운드 복귀 시 check-in 재호출됨   ← 수정 후에만 나오는 줄
  ```
- **남긴 것**: 서버(락 없음)와 앱(가드 미해제) **양쪽이 겹쳐야** 나는 문제였다. 서버만 고쳤다면 네트워크 오류 같은 다른 실패에서 여전히 하루를 날렸을 것이다. 원인을 한쪽에서 찾고 멈추지 않은 게 이 건의 요점이다.

## 9. 푸시 한 건이 7번 처리되던 문제 — 개발 환경이 버그를 가린 사례

- **증상**: 같은 알림이 알림함에 2줄로 쌓이고, 서버 로그엔 같은 요청이 2.5초 간격으로 2발 찍혔다.
- **진단**: 앱 로그를 보니 **동일한 `messageId`가 7번 처리**되고 있었다. 포그라운드 FCM 핸들러가 구독 해제 없이 매번 새로 등록되는 구조였고, 등록 함수 호출부가 로그인·세션복구·동의화면·권한동기화 **4곳**이었다.
- **★ 고친 뒤에도 7회 그대로였다**: Fast Refresh는 모듈 코드만 교체할 뿐 **이미 등록된 구독은 해제하지 못한다.** 수정 전에 쌓인 핸들러가 그대로 살아 있어 증상이 재현됐다. 앱을 완전히 재시작해야 판정이 됐다.
  ```
  수정 후 · 오래된 프로세스     7회
  수정 후 · 완전 재시작 후      1회
  ```
- **해결**: 구독 해제 함수를 보관했다가 재등록 전에 호출. 호출부를 줄이는 대신 **구독 쪽을 멱등하게** 만들었다 — 4곳 각각에 이유가 있어서 호출 자체를 없애는 건 다른 회귀를 만든다.
- **남긴 것**: "고쳤는데 그대로다"를 만나면 코드보다 **프로세스 나이를 먼저 의심해야 한다**는 걸 검증 절차에 넣었다.

## 10. 화면은 멀쩡한데 아무것도 안 눌리던 프리징

- **증상**: 알림으로 앱에 들어오면 화면이 멈춘다. 강제 종료 외에 빠져나올 방법이 없다. 다시 켜면 보상 화면과 출석 안내가 버벅이며 순차로 떴다.
- **진단**: 크래시 로그가 없다 = 앱은 살아 있다. 전체화면 보상 오버레이가 `Modal`이었고, **닫기 처리가 애니메이션 완료 콜백(`finished`) 안에만** 있었다. 애니메이션이 중간에 끊기면(백그라운드 전환 등) 마운트 상태가 `true`로 남아 **투명한 전체화면 Modal이 모든 터치를 흡수**한다.
- **겹친 원인 하나 더**: 기동 스플래시도 `Modal`이라, 둘이 겹치는 순간 iOS가 두 번째 present를 조용히 무시한다. 이 경우 보상 화면은 **영영 뜨지 않는다**(지급은 됐는데 사용자는 못 본다).
- **해결**: Modal을 걷어내고 **최상단 절대배치 뷰**로 바꿨다. 정리 조건을 `finished`에서 분리해 애니메이션이 끊겨도 반드시 닫히게 하고, 등장 애니메이션이 아예 안 도는 경우까지 대비해 일정 시간 뒤 값을 확정하도록 했다.
- **남긴 것**: Modal 중첩은 실패 모드가 **"안 보임"과 "터치 잠김"** 두 방향으로 갈린다. 뷰로 내리면 최악이 "가려짐"이 되고, 가린 것이 사라지면 자연히 드러난다.

## 11. 알림함 진입 시 렌더 크래시 — id 없는 알림

- **증상**: 알림함을 열면 `Cannot read property 'toString' of undefined`.
- **진단**: 리스트의 `keyExtractor`가 `item.id.toString()`이었다. 목록 API 응답에는 `id`가 항상 있는데, **실시간 푸시로 받은 알림에만 없었다**(그 타입의 payload에 알림 테이블 id가 빠져 있었다). 서버 응답을 전수 확인해 "서버가 빠뜨린 게 아니라 실시간 경로만 다르다"를 갈라낸 게 진단의 분기점이었다.
- **더 이상했던 것**: 바로 위 수신 리스너는 **`id`가 없을 수 있다는 걸 이미 알고 있었다** — 중복 검사만 건너뛰고 삽입은 그대로 했다. 알고도 렌더링 쪽을 안 맞춘 상태였다.
- **해결**: 근본은 **id 없는 항목을 목록에 넣지 않는 것**. 토스트는 별도 컴포넌트가 받으므로 사용자에게는 그대로 보이고, 정식 항목은 다음 목록 조회에서 서버 id와 함께 들어온다. `keyExtractor` 방어는 이중으로 남겼다.

## 12. 아이폰에서만 보상이 늦게 지급되던 문제 — AppState는 3상태다

- **증상**: "알림을 눌렀는데 지급이 안 된다"는 제보. **안드로이드에서는 재현되지 않았다.**
- **진단**: 앱은 포그라운드 상주 중 60초마다 서버에 신호를 보내고, 백그라운드로 가면 멈춘다. 복귀 시 즉시 1발을 쏘는데 그 함수 첫 줄이 `if (timer) return`이었다. **iOS의 AppState는 `active` / `inactive` / `background` 3상태인데 인터벌 정지는 `background`에서만** 한다. 알림센터를 내려서 탭하면 `inactive → active`라 타이머가 살아 있고 → 조기 return → **다음 틱까지 최대 60초** 대기.
- **★ 안드로이드로는 원리상 재현이 불가능했다**: React Native에서 `inactive`는 iOS 전용 상태다. "안드로이드에서 안 되는 재현"이 곧 원인의 단서였다.
- **해결**: 판정 기준을 **타이머 유무 → 마지막 호출 시각**으로 바꿨다. 원래 이 가드는 제어센터를 잠깐 열었다 닫는 깜빡임에 재발화하는 걸 막으려던 것인데, **알림 탭까지 같이 막고 있었다.**

## 13. iOS가 안드로이드 버전 번호를 자기 것으로 읽던 문제

- **증상**: 앱 업데이트 게이트(권고/강제)가 iOS에서 잘못된 버전으로 판정될 수 있는 상태였다.
- **원인**: 두 플랫폼의 버전 번호를 **의도적으로 다르게** 관리하는데(iOS는 네이티브 설정을 직접 올리는 구조), 버전을 읽는 코드가 공통 설정 파일 하나만 보고 있었다.
- **위험**: 최소지원버전을 올리는 순간 **최신 iOS 사용자까지 강제 업데이트 모달에 갇힌다.** 사용자가 스스로 빠져나올 수 없는 종류의 사고다.
- **해결**: 플랫폼별 실제 버전을 읽는 **단일 진입점**을 만들고, 파싱이 조금이라도 불확실하면 아무 조치도 하지 않도록(fail-safe) 규칙을 못박았다. 이 기능 때문에 앱을 못 쓰게 되는 일만은 없어야 한다는 게 설계 기준이었다.

## 14. 24시간마다 로그아웃되던 문제 — 원인이 우리 쪽이 아니었다

- **증상**: 사용자가 하루가 지나면 로그인이 풀린다는 제보.
- **처음 의심**: 토큰 갱신 로직. 앱은 `401`을 받으면 리프레시를 돌리게 돼 있었다.
- **실제 원인**: 서버가 **만료된 토큰에 `401`이 아니라 `403`을 반환**하고 있었다. 갱신은 `401`에서만 발화하므로 아예 트리거되지 않았다. 앱 코드에는 잘못이 없었고, 재현도 앱만 봐서는 되지 않았다.
- **판단**: `403`을 갱신 트리거에 추가하는 건 **거부했다.** `403`은 정지·차단·권한 부족에도 쓰이는 코드라, 갱신을 걸면 차단된 계정이 무한히 재시도한다. 상태 코드의 의미를 흐리는 대신 **서버가 `401`을 주도록** 요청했다.
- **앱이 한 것**: 서버 수정이 나가기 전 이미 배포된 구버전을 위해, 인증 상태 불명확 시 사용자 정보 재조회로 한 번 더 확인하는 보완 경로만 얹었다.
- **남긴 것**: 남의 시스템이 원인일 때도 **관측과 추정을 구분해서** 전달해야 한다. "서버가 403을 준다"는 관측이고, "그래서 갱신이 안 돈다"까지가 검증된 인과였다.

## 15. 푸시가 27%에게만 닿던 문제 — 고칠 대상은 사용자가 아니라 계측이었다

- **증상**: 등록 사용자 대비 푸시가 실제로 배달 가능한 기기가 27%에 그쳤다.
  ```
  등록 사용자            288명
  배달 가능(토큰 보유)     79명   27%
  권한 상태 보고 도달      86명
    ├ 거부(DENIED)       58명   67%
    └ 허용(GRANTED)      28명
  ```
- **처음 결론(오진)**: "67%가 거부했으니 가입 시점 권한 팝업이 문제다." **이 해석은 틀렸다.** 측정된 것은 거부율뿐이고, *언제* 거부했는지는 데이터에 없었다. 인과를 데이터가 말해주지 않는 부분까지 밀고 나간 것이 오진의 시작이었다.
- **실제 원인**: 그 67%가 **거부한 사람이 아니었다.** 안드로이드에는 iOS의 `undetermined`(아직 안 물어봄)가 없다. 한 번도 묻지 않은 기기도 `status='denied'`로 온다. 구분 수단은 `canAskAgain` 하나뿐인데, 보고 코드는 `status`를 그대로 대문자로 올리고 있었다. **신규 설치자가 전부 "거부"로 집계되고 있었다.**
- **더 큰 문제가 같이 있었다**: 권한 요청을 `status === 'undetermined'`로 게이팅하고 있었다. 안드로이드에서는 그 값이 **영원히 오지 않으므로**, OS 권한 팝업이 **한 번도 뜨지 않았다.** 거부율이 높았던 게 아니라 **묻지를 않고 있었다.**
- **해결**: 판정 기준을 `status`에서 `canAskAgain`으로 옮기고, 그 판정을 `getPermissionStatus()` 한 곳으로 모아 보고·요청·프리퍼미션이 같은 규칙을 보게 했다. → [`../code-excerpts/pushPermission.ts`](../code-excerpts/pushPermission.ts)
- **검증의 함정**: 처음에 쓴 검증 기기가 Android 11이었다. `POST_NOTIFICATIONS` 권한은 **Android 13(API 33)부터** 존재하고 그 이하는 항상 허용이라, 재현이 될 수 없는 기기였다. 재현 실패를 코드 문제로 의심하며 시간을 썼다. **"재현이 안 된다"를 만나면 코드보다 검증 환경의 전제를 먼저 확인해야 한다.**
- **남긴 것**: 지표가 나쁘게 나오면 제품을 의심하게 되는데, **이 건은 지표를 만드는 코드가 틀려 있었다.** 계측이 틀리면 개선 방향도 같이 틀린다. 실제로 이 오진대로 갔다면 "거부자 회수"에만 힘을 쏟고, 정작 **묻지도 않고 있던 다수**는 계속 놓쳤을 것이다.

## 16. 포그라운드 알림이 통째로 사라지던 문제 — JS로 올라오지 않는 예외

- **증상**: 안드로이드에서 앱을 켜둔 상태로 푸시가 오면 **아무것도 뜨지 않았다.** 인앱 토스트도, 알림함 갱신도 없었다. 백그라운드에서는 정상이었다.
- **진단**: 포그라운드 FCM 핸들러는 수신 로그까지 정상으로 찍혔다. 그 다음 줄인 로컬 알림 재발행에서 끊겼는데, **에러 로그가 없었다.** 네이티브에서 죽으면 JS의 `catch`로 올라오지 않는다.
- **원인**: 재발행 호출의 트리거가 `null`(즉시)이었다. 안드로이드에서 SDK가 사운드 URI를 만들 때 **트리거에서 채널을 읽는데**, 트리거가 없으니 그 시점에 NPE로 죽었다. iOS는 채널 개념이 없어 `null`이 정상이라 **iOS만 멀쩡했다** — 플랫폼 한쪽만 되는 증상이 단서였다.
- **해결**: 안드로이드만 `{ channelId: 'default' }` 트리거를 주고 iOS는 즉시(null)를 유지. 그리고 재발행 실패를 삼키되 **알림을 통째로 잃지는 않도록** 경로를 분리했다.
- **남긴 것**: 이 설계는 [엔지니어링 결정 1](./engineering-decisions.md)(포그라운드 배너를 끄고 인앱 토스트만 쓴다)의 **대가**이기도 하다. 배너를 껐기 때문에 재발행이 죽으면 사용자에게 남는 게 아무것도 없었다. 대체 경로를 만든 선택에는 그 경로가 죽었을 때의 폴백까지 따라와야 한다.

## 17. 거부 직후 회수 안내가 안 뜨던 문제 — 억제 장치가 회수 기회를 막았다

- **증상**: 교차 플랫폼 검증에서 iOS 담당이 보고했다. 권한 팝업에서 **거부한 직후** 떠야 할 "설정에서 켜기" 안내가 뜨지 않는다.
- **원인**: 프리퍼미션 모달은 `ask`(설명 후 OS 팝업)와 `settings`(설정 유도) 두 모드가 있는데, **재노출 억제(7일) 키를 두 모드가 공유**하고 있었다. `ask`를 띄우며 찍은 도장이, 그 직후 거부해서 떠야 할 `settings`까지 7일간 막았다. **거부 직후가 가장 좋은 회수 기회인데 그때를 정확히 놓치는 구조**였다.
- **겹쳐 있던 두 번째 결함**: 스누즈 검사가 **모드 결정보다 먼저** 실행됐다. 어느 키로 볼지 모르는 상태에서 검사하니 공용 키를 쓸 수밖에 없었다. 순서가 원인을 고착시키고 있었다.
- **해결**: 키를 모드별로 분리(`push.primer.lastShownAt.{ask|settings}`)하고, **모드를 먼저 정한 뒤 그 모드의 키로 검사**하도록 순서를 뒤집었다. → [`../code-excerpts/usePushPrimer.ts`](../code-excerpts/usePushPrimer.ts)
- **남긴 것**: iOS에서 올라온 보고였지만 확인해 보니 **안드로이드도 같은 코드로 미검증 상태**였다. 한쪽 플랫폼의 결함 보고를 받으면 공용 로직인지부터 갈라야 한다. 이 건은 공용이었고, 양쪽 다 고쳐야 했다.

## 18. 버튼이 통째로 사라진 채 2주간 운영에 나가 있던 문제 — 가로용 스타일을 세로에 재사용

- **증상**: 안드로이드에서 AI 대화를 나갈 때 뜨는 확인 모달의 **주 CTA(「지금 신청하기」)가 보이지 않았다.** 아래의 보조 링크(「나중에 하기」)만 있었다. 그 모달로는 매칭 신청을 할 방법이 없었다.
- **왜 늦게 발견됐나**: 세 가지가 겹쳤다. ① **에러가 나지 않는다** — 요소는 존재하고 높이만 0이라 로그에 흔적이 없다. ② **웹에서는 정상으로 보인다** — react-native-web 이 같은 스타일 조합을 다르게 해석한다. 디자인 확인을 웹에서 하면 통과한다. ③ **마주치기 어려운 화면이다** — 대화에서 나갈 때만, 그것도 한 번 "나중에"를 누르면 다음 응답이 올 때까지 다시 안 뜬다.
- **진단**: 스크린샷을 픽셀로 떠서 안드로이드/웹을 비교했다. 버튼이 있어야 할 자리의 세로 간격이 정상의 절반이었고, 뷰 트리 덤프에는 **노드 자체가 없었다**(크기 0인 뷰는 덤프에서 빠진다). "조건부로 안 그려졌다"와 "그려졌는데 크기가 0이다"를 이 두 근거로 갈랐다.
- **원인**: 공용 버튼 스타일이 **좌우 2버튼용**으로 만들어져 있었다.
  ```ts
  btn: { flex: 1, height: 44, ... }
  ```
  `flex: 1`은 `flexGrow`·`flexShrink`와 함께 **`flexBasis: 0`**을 켠다. `flexBasis`는 *배치 방향 쪽* 크기라 의미가 뒤집힌다.
  - 가로 배치 → basis 는 **너비**. 두 버튼이 반씩 나눠 갖고 `height: 44`는 무사하다
  - 세로 배치 → basis 는 **높이**. `height: 44`를 덮어써 **0**이 된다

  디자인 변경으로 이 모달만 「위 큰 버튼 + 아래 작은 텍스트」인 **세로 배치**가 되면서, 같은 한 줄이 정반대로 작동했다. 변경 자체는 `stackedCta` 플래그 한 줄이었다.
- **첫 수정이 안 먹었다**: `flexGrow: 0, flexShrink: 0, flexBasis: 'auto'` 로 덮었는데 기기에서 그대로였다. **`flex` 와 이 셋은 키가 달라 서로 덮어쓰지 못한다.** 둘 다 최종 스타일에 남고, 네이티브에서 `flex` 가 나중에 적용되며 basis 0 으로 되돌아간다. `flex: 0` 으로 **같은 키를 덮어야** 했다.
- **그 과정에서 한 번 더 틀렸다**: 첫 수정 후 화면이 그대로이길래 "원인이 다른 데 있다"고 결론을 뒤집었다. 실제로는 **번들이 갈렸는지 확인하지 않은 상태**였다. 이후로는 수정 검증 전에 프로세스 재시작으로 새 번들 적재를 먼저 확정한다.
- **남긴 것**: 공용 스타일을 재사용할 때 **배치 방향이 바뀌면 같은 속성이 다른 축에 적용된다**는 점을 놓쳤다. 그리고 이 결함은 크래시도 경고도 없이 **조용히** 기능 하나를 없앴다 — 웹에서 정상으로 보이는 크로스플랫폼 UI는, 실기기에서 **눌러봐야** 검증된 것이다.

## 19. 출석 보상이 하루 통째로 누락될 수 있던 구조 — 클라이언트 시계를 판정에 쓴 대가

- **증상 이전에 발견**: 사용자 신고가 아니라 코드 검토 중에 나왔다. 출석 호출을 "오늘 이미 불렀나"로 거르는 가드가 **단말 시계**로 날짜를 계산하고 있었다.
- **왜 문제인가**: 서버 응답의 `granted: false` 가 두 가지를 동시에 뜻했다.
  1. 오늘 이미 출석했다
  2. **서버는 아직 어제다** (단말 시계가 앞서 있다)

  단말이 1분 빠른 상태로 자정을 넘기면 2번이 "성공"으로 보이고, 가드에 **내일 날짜**가 박힌다. 실제 자정이 지나도 "이미 했다"로 판정해 **그날 출석이 한 번도 나가지 않는다.** 가드는 프로세스 단위라 앱을 강제 종료해야 풀렸다.
- **반대 방향(시계가 느림)은 경미하다**: 단말이 자정을 넘기는 순간 값이 달라져 저절로 풀린다. 지연 폭이 곧 시계 오차다. **같은 오차가 방향에 따라 하루 누락과 수 초 지연으로 갈린다**는 점이 이 문제의 핵심이었다.
- **해결**: 서버에 **판정에 사용한 날짜**를 응답에 실어달라고 요청하고(`date`), 가드를 그 값으로 박았다. 단말이 어느 쪽으로 틀어져 있든 서버 날짜와 달라지는 동안 호출이 계속 열려 있으므로 누락이 없다. 필드가 없는 구버전 서버에서는 단말 값으로 폴백해 종전과 동일하게 동작한다. → [`../code-excerpts/attendanceGuard.ts`](../code-excerpts/attendanceGuard.ts)
- **대가와 그 처리**: 두 날짜가 어긋난 창에서는 포커스마다 호출이 나갈 수 있다. 지급은 서버가 멱등이라 안전하지만 낭비이므로 **그 창에서만** 30초 쓰로틀을 걸었다. 가드가 비어 있을 때(첫 호출·직전 실패)는 통과시킨다 — 정작 복구가 필요한 순간을 늦추면 안 된다.
- **이중 방어**: 클라이언트가 "부를지 말지"를 정하는 구조는 어긋나도 스스로 알아채지 못한다. 그래서 미션 화면 진입 시 **서버가 오늘 출석을 갖고 있는지**(`checkedToday`)를 보고, 없으면 가드를 무시하고 한 번 더 부른다. 이미 하던 조회에 실려 오는 값이라 추가 왕복이 없고, 날짜를 키로 하루 1회만 재시도해 루프가 되지 않는다.
- **검증**: 백엔드에 협조를 요청해 **DB에서 그날 출석 행만 삭제**하고, 앱은 켜둔 채로(가드를 살린 채) 화면에 진입해 재현했다. 앱을 껐다 켜면 가드가 초기화돼 조건이 사라지므로 그 상태를 유지하는 게 핵심이었다. 시계 오차 쪽은 단말 날짜를 하루 앞당겨 재현했다.
- **남긴 것**: 클라이언트 시계는 사용자가 바꿀 수 있고 실제로 어긋나 있다. **판정에 쓰는 값은 서버가 내려준 것이어야 한다.** 응답 하나가 두 가지 상태를 뜻하고 있다면, 그건 필드가 부족한 것이지 클라이언트가 추론할 문제가 아니다 — 그래서 추측 대신 **필드 추가를 요청**했다.

## 20. 방에 안 들어온 사람이 「들어왔어요」로 뜨던 문제 — 조회 API에 부작용이 붙어 있었다

- **증상**: 공개 대화방에 입장 표시(「○○님이 들어왔어요」)를 붙인 뒤 실기기 검증에서 **실제로 방에 들어갔는데 입장 이벤트가 오지 않았다.** 한 번은 우연히 30분 억제에 걸린 것으로 보고 넘길 뻔했다.
- **처음 판단(보류)**: "억제 규칙 때문인지, 수신 스크립트가 못 받은 건지 모르겠다"로 보고했다. **두 가설을 가를 실험을 하지 않은 채** 결론을 미룬 것이었다.
- **가설을 가른 실험**: 이벤트 토픽을 구독해 두고, 소켓 연결 없이 **방 정보 API를 curl로 한 번만** 호출했다. 곧바로 입장 이벤트가 왔다.
  ```
  구독  /topic/talk/1/events
  GET  /v2/talk/room            (소켓 연결 없음, 방 화면 아님)
  → {"type":"ENTER","userId":..,"ai":false}    ← 조회만으로 입장 처리
  ```
  수신 쪽은 정상이었고, **입장은 방 화면이 아니라 이 API 호출 시점에 처리**되고 있었다.
- **원인**: 앱은 방 정보 API를 **방 화면 밖에서도** 부른다 — 라운지 카드의 인원수·아바타, 설정 화면의 "스태프 방 버튼을 보여줄지" 판정. 검증 5분 전에 다크모드를 확인하느라 설정·라운지를 열었고, 그때 입장이 이미 나갔다. 5분 뒤 실제 입장은 **30분 억제에 걸려** 아무것도 안 나갔다.
  ```
  10:48  설정·라운지 열람      → ENTER 발화 (아무도 안 봄)
  10:53  실제 방 입장          → 억제로 발화 없음
  11:29  같은 호출 재시도       → 정상 발화 (30분 경과)
  ```
- **사용자에게 미치는 영향**: ① 라운지만 열어도 방 안에 입장이 뜬다 ② **정작 진짜로 들어올 때는 안 뜬다** ③ 백엔드 확인 결과 **누적 방문자 수도 같은 호출로 올라가** 라운지 열람만으로 부풀려지고 있었다.
- **해결 방향 판단**: 앱에서 피하려면 카드·설정이 이 API를 안 불러야 하는데, 그러면 인원수·권한 정보를 받을 곳이 없어진다. **조회와 상태 변경이 한 엔드포인트에 묶인 게 원인**이므로 분리는 서버에서 하는 게 맞다고 전달했다. 합의된 계약:
  ```
  GET /v2/talk/room?enter=1   → 방문 기록 + ENTER(30분 억제) + 응답   ← 방 화면 진입 한 곳
  GET /v2/talk/room           → 응답만                               ← 카드·설정·복귀 갱신
  ```
  앱은 **방 화면 최초 진입 한 곳에만** `enter=1` 을 붙였다. 같은 화면 안에서도 포커스 복귀·소켓 재연결 때의 재조회에는 붙이지 않았다 — 붙이면 프로필을 보고 돌아올 때마다 입장이 다시 잡힌다.
- **검증의 함정**: 억제가 **서버 재기동 뒤에도 유지**됐다. 그래서 "0건"이 "앱이 조회만 했다"인지 "억제에 걸렸다"인지 또 구분되지 않는 상황이 됐다. 억제 기록이 없는 계정으로 먼저 **조회만으로는 억제가 걸리지 않음**을 확인한 뒤, 기기 계정의 억제 창이 풀린 시점에 설정·라운지 열람 0건 → 방 입장 → 직후 같은 계정의 `enter=1` 재호출이 억제되는 것으로 앱의 입장 호출을 확정했다.
- **남긴 것**: "원인을 모르겠다"는 보고는 **가설을 가를 가장 작은 실험을 해 본 뒤에** 해야 한다. 이 건은 curl 한 번이면 갈렸다. 그리고 GET 에 부작용(방문 기록·이벤트 발행)이 붙어 있으면, **그 API를 부르는 모든 화면이 부작용의 발화 지점**이 된다 — 호출부가 늘어나는 순간 조용히 지표가 오염된다.

## 21. 알림을 다 읽었을 뿐인데 채팅 알림이 사라지던 문제 — 「배지 0」이 안드로이드에선 「알림 전체 삭제」였다

- **배경**: 앱 아이콘에 알림함 미읽음 개수(iOS 빨간 숫자)를 띄우는 기능. 숫자의 출처를 **서버 미읽음 API 하나**로 고정했다 — 앱이 켜져 있을 땐 앱이 그 값으로 맞추고, 꺼져 있을 땐 서버가 같은 함수로 센 값을 푸시 페이로드(`aps.badge` / `notification_count`)에 싣는다. 두 곳이 따로 세면 아이콘과 앱 안 숫자가 어긋나기 때문이다.
- **실기기 검증 중 발견**: 단계별로 서버 값·아이콘 숫자·기기의 알림 레코드(`dumpsys notification`)를 같이 대조했다. 푸시 쪽은 28→29→30 모두 일치했는데, **앱을 켜서 숫자를 맞추는 쪽은 아이콘에 아무것도 안 떴다.** 로그를 보니 앱은 숫자를 제대로 넣고 있었다.
  ```
  BadgeProvider: update, [BadgeCount] : badgecount=30   ← 앱이 넣은 값은 기록됨
  BadgeCache: reloadBadge size : 0                     ← 런처는 이 값을 안 씀
  ```
  이 런처는 앱이 넣은 숫자를 무시하고 **알림창에 남은 푸시의 `notification_count`**로 배지를 그린다. 안드로이드에선 사실상 서버 페이로드가 표시값이다.
- **진짜 문제는 0 쪽이었다**: 라이브러리 구현을 열어 보니 배지를 0으로 맞추는 호출이 안드로이드에선 이렇게 돼 있었다.
  ```kotlin
  if (badgeCount == 0) notificationManager.cancelAll()   // 숫자 지우기가 아니라 알림 전부 삭제
  ```
  처음 구현은 홈의 30초 주기 갱신에서도 값을 그대로 넣었으므로, **알림함을 다 읽은 사용자는 앱을 열기만 해도 30초마다 알림창이 비워진다.** 알림함에 쌓이지 않는 **채팅 알림까지** 같이 사라진다. 에러도 없고, 알림함 화면만 보면 정상이라 운영에서였다면 "알림이 가끔 안 온다"는 문의로만 드러났을 것이다.
- **해결**: 안드로이드의 0은 **사용자가 실제로 읽었을 때**(하나 읽음·모두 읽음·삭제)와 **로그아웃**에만 보낸다. 주기 갱신·화면 복귀처럼 사용자 행동이 아닌 경로에서는 0을 건너뛴다. 읽음으로 0이 되는 순간 알림창을 비우는 건 오히려 의도에 맞는다(아이콘 숫자와 알림창이 함께 정리된다).
  ```ts
  if (Platform.OS === 'android' && n === 0 && !opts?.clearShade) return;
  ```
  → [`../code-excerpts/appBadge.ts`](../code-excerpts/appBadge.ts)
- **검증**: 수정 전 증상을 가장 잘 드러내는 경로로 재현했다 — 앱이 백그라운드일 때 채팅 푸시를 받아 알림창에 둔 채, **알림이 아니라 아이콘으로** 앱을 연다(알림함 미읽음 0). 40초 뒤에도 알림이 남아 있는 것을 확인했다. 캐시로 "같은 값이면 호출 생략"도 넣지 않았다 — 백그라운드에서 푸시가 배지를 바꿔 놓으므로 "지난번과 같은 값"이 실제 아이콘 숫자와 같다는 보장이 없다.
- **남긴 것**: 크로스플랫폼 API의 같은 호출이 플랫폼마다 **부작용의 크기**가 다를 수 있다. iOS에선 숫자만 바꾸는 호출이 안드로이드에선 파괴적인 동작이었다. 그리고 "푸시를 안 켜도 개수가 보인다"는 기획 전제는 성립하지 않았다 — 배지는 알림 권한의 일부라, 권한이 없으면 OS가 무시한다. 구현 전에 이걸 먼저 짚었다.

## 22. 「누가 내 프로필을 봤어요」 모달 — 출시 하루 만에 드러난 세 가지 전제 오류

조회 알림을 누르면 「대화해 보기 / 프로필 보러 가기」를 고르게 하는 모달. 진입 경로는 ① 앱 실행 중 푸시 탭 ② 앱이 꺼진 상태에서 푸시 탭 ③ 홈에 20초 머물면 자동 1회. 서로 다른 세 가지가 각각 다른 전제를 깨고 있었다. → [`../code-excerpts/profileViewModalGate.ts`](../code-excerpts/profileViewModalGate.ts)

### (1) 모달을 띄웠을 뿐인데 상대에게 「프로필을 확인했어요」가 거꾸로 나갔다
- **원인**: 사진을 받으려고 프로필 상세를 조회했다. 모달 작성자는 "한 줄 분석 API는 알림을 보내니 프로필 상세를 쓴다"고 주석까지 남겼는데, **바로 전날 서버 정책이 "프로필 상세 조회 = 실제 열람(기록 + 알림)"으로 바뀌어** 있었다. 전제가 하루 만에 뒤집힌 것.
- **영향**: A가 B를 본다 → B 폰에 모달 → B는 아무것도 안 눌렀는데 A에게 「B가 내 프로필을 확인했어요」. 자동 노출(③)이 있어 사용자 행동 없이도 발생한다.
- **판단**: 앱이 이 조회를 피하는 대신(사진·차단 판정을 받을 곳이 없어진다) 서버와 **기록·알림을 남기지 않는 조회 플래그 `from=noti`** 를 합의했다. 응답·404 판정은 그대로라 모달 변경은 한 줄. 모달 안의 「프로필 보러 가기」는 실제 열람이라 플래그 없이 부른다 — 조회 의미를 호출부가 명시하게 했다.
- **같이 잡은 것**: 이 푸시는 본 사람 id를 `referenceId`가 아니라 `viewerId`로 싣고 있었다. 탭 핸들러가 `referenceId`만 읽어 **모달이 아예 안 뜨고 있었다**(이전 버전도 이 푸시는 눌러도 이동이 없었다).

### (2) iOS에서만 앱이 꺼진 상태의 푸시 탭(②)이 통째로 죽었다
- **원인**: 스플래시도 `<Modal>`이다. iOS는 Modal이 이미 present 중이면 두 번째 present를 **조용히 무시**하고, `visible`이 true 그대로라 스플래시가 사라져도 재시도하지 않는다. 같은 이유로 업데이트 안내 모달에는 이미 `splashDone` 가드가 있었는데 새 모달에만 빠져 있었다.
- **함정**: `{splashDone && <Modal/>}`로 마운트를 늦추면 이번엔 요청이 사라진다 — 화면 밖 요청을 전달하는 버스는 보관 없이 지금 붙은 리스너에만 보내는데, 콜드스타트 요청이 정확히 그 틈에 온다.
- **해결**: 마운트는 유지(요청 수신)하고 **그리기만** 스플래시 뒤로 미뤘다. 버스에 보관 로직을 넣는 안도 있었지만 중복 발화·수명 관리라는 곁가지가 생겨 택하지 않았다. iOS 담당 동료가 원인과 두 안을 정리해 왔고, 본류 브랜치에서 고쳐 양 플랫폼이 같은 코드를 쓰게 했다.

### (3) 마이페이지·대화 탭에 있어도 「홈 20초」 모달이 떴다
- **원인**: 하단 탭이 라우트가 아니라 `/home` 한 화면 안의 state였다. 타이머는 경로가 `/home`인지만 봤다.
- **해결**: 홈 화면이 탭 변경을 버스로 알리고, 타이머는 "경로 + 홈 탭"일 때만 돈다. 다른 탭으로 가면 풀리고 돌아오면 다시 센다.
- **같이 바꾼 것**: 자동 노출(③)은 **볼 수 있는 사람일 때만** 띄운다. 권유하려고 먼저 띄우는 모달인데 「지금은 볼 수 없는 프로필이에요」(상대의 숨김·탈퇴)만 뜨면 할 수 있는 게 없다. 띄우기 전에 `from=noti`로 조회해 404면 다음 후보로 넘어가고, 건너뛴 알림은 **읽음 처리하지 않는다**(사용자가 본 적 없다). 푸시를 직접 눌러 온 ①②는 사용자가 연 것이라 지금처럼 안내한다.
- **검증**: 실기기에서 마이페이지 탭 40초 → 안 뜸 / 홈 탭 24초 → 뜸 / 볼 수 있는 상대가 없게 만든 뒤 홈 30초 → 안 뜨고 해당 알림은 안 읽음 유지. 역알림은 상대 계정의 미읽음 수가 모달 표시 전후로 그대로인지, 「프로필 보러 가기」 뒤에는 +1인지로 확인했다.

- **남긴 것**: 세 문제 모두 **"이 조회는 부작용이 없다", "모달은 겹쳐도 뜬다", "경로가 곧 화면이다"** 라는, 코드에 적혀 있지 않은 전제에서 나왔다. 부작용이 있는 조회는 호출부가 의도를 플래그로 밝히게 하고, 플랫폼 제약은 같은 이유로 막아 둔 옆 코드를 먼저 찾아본다.

## 23. 같은 iOS 모달 버그가 세 번째로 — 화면마다 막지 말고 신호를 하나로

- **증상**: 서버 장애 사과 공지를 홈 팝업으로 띄운 날, iPhone 사용자에게서 「팝업은 안 뜨고 홈이 멈춰서 스크롤이 안 된다」는 제보가 왔다. 안드로이드는 정상.
- **처음 판단**: 공지 본문이 길어 확인 버튼이 화면 밖으로 밀려났다고 봤다(팝업 카드에 높이 제한·스크롤이 없었다). 안드로이드 실기기에서 450자 본문까지 넣어 봤지만 **버튼은 보였고 닫은 뒤 스크롤도 정상** — 재현되지 않아 이 가설은 버렸다.
- **원인**: 공지 팝업은 홈에 들어오고 0.5초 뒤 뜨는데, 콜드스타트에서는 그때 **스플래시(이것도 `<Modal>`)가 아직 떠 있다.** iOS는 Modal이 present 중이면 두 번째 present를 조용히 무시하고 `visible`은 true로 남는다 → **보이지 않는 Modal이 홈의 터치를 막는다.** 업데이트 안내 모달(1번째), 조회 알림 모달(2번째, [22-(2)](#22-누가-내-프로필을-봤어요-모달--출시-하루-만에-드러난-세-가지-전제-오류))과 같은 메커니즘의 **3번째 재발**이었다. 안드로이드는 겹쳐 띄우기 때문에 안드로이드 실기기 테스트로는 원리상 잡히지 않는다.
- **왜 또 났나**: 앞의 두 번은 앱 루트(`_layout`)에 있는 모달이라 루트의 `splashDone` state를 prop으로 넘겨 막았다. 공지 팝업은 **화면 안에 있는 모달**이라 그 state에 닿지 않았다. 가드가 "그 state를 받을 수 있는 모달"에만 걸리는 구조였던 것.
- **해결**: 「스플래시가 끝났는가」를 앱 어디서나 읽는 **공용 신호**(`markSplashDone` / `useSplashDone`)를 만들고, 루트가 스플래시 종료 때 한 번 알린다. 공지 팝업은 이 값이 true가 된 뒤에만 그린다. 22번에서 정한 규칙(마운트·요청 수신은 그대로, **그리기만** 늦춘다)을 그대로 따라 팝업 상태는 유지되고 스플래시가 끝나면 뜬다. → [`../code-excerpts/splashGate.ts`](../code-excerpts/splashGate.ts)
- **검증의 한계**: 손에 iOS 기기가 없어 재현은 못 했다. 원인 판단은 증상(iOS만·콜드스타트만·팝업 미표시+터치 잠김)이 앞의 두 사례와 정확히 겹친다는 데 근거했고, 실기기 확인은 iOS 담당 동료에게 넘겼다.
- **남긴 것**: 같은 플랫폼 제약이 세 번 나오면 개별 가드로는 못 막는다 — 다음 모달은 또 가드 받을 위치 밖에서 생긴다. **누구나 읽을 수 있는 신호 하나**로 올리고, 새 모달을 넣을 때 「콜드스타트에 뜰 수 있나?」를 먼저 묻는 것을 팀 규칙으로 남겼다.

## 24. 가입 마지막 단계가 끊기고, 재시도는 막히던 문제 — 「실패」로 보이던 것의 대부분은 성공이었다

가입 마지막 단계(12문항 제출 → AI가 페르소나 생성)는 AI 응답을 기다리는 동기 요청이라 40~97초가 걸렸다. 이 한 단계에서 세 번에 걸쳐 문제가 드러났다.

### (1) 끊긴 요청을 실패로 보여 줬다
- **실측**(주말 3일, 서버 로그): 가입 요청 84건 중 **성공 25 · 클라이언트 끊김(499) 25 · 「이미 존재」(409) 29**. 기다리는 동안 백그라운드 전환·네트워크 변경으로 끊긴다.
- **원인**: 앱이 끊김을 에러로 띄웠다. 그런데 **서버는 계속 돌아서 대부분 성공**했다. 사용자가 다시 누르면 「이미 페르소나가 존재합니다」(409)를 또 에러로 띄웠고, 한 사용자는 7번 두드리다 요청 제한(429)까지 맞았다.
- **피해 규모를 다시 쟀다**: 같은 기간 가입자 57명 중 페르소나를 가진 48명은 **전원 완주**(재시도로). 영구 이탈 후보는 3명이었고 셋 다 설문 임시저장이 남아 있었다. 「30% 실패」가 아니라 「30%가 불쾌한 재시도를 겪고 3명 이탈」이 정확한 표현이었다.
- **해결**: 제출 실패(끊김·409·429·5xx)면 에러 대신 분석 중 화면을 유지하고 가입 상태 API를 폴링한다. 첫 조회는 **제출 후 20초**(AI 최소 소요 23초 실측 — 그 전엔 확정적으로 미생성), 이후 5초 간격, 제출 기준 120초까지. 기준을 실패 시각이 아니라 **제출 시각**으로 잡은 이유는 끊기는 시점이 3.8~65.9초로 제각각이라서다.
- **상태 판정의 함정**: 서버 상태는 `NONE → (생성 중) → CREATED → VALIDATED → COMPLETE`인데, 생성 중 상태는 트랜잭션 안에서만 존재해 **밖에서는 `NONE`으로 보인다.** `NONE`이 「미제출」과 「생성 중」을 둘 다 뜻한다. 서버에 상태를 하나 더 요청하는 대신, **앱은 자기가 방금 제출한 걸 안다** — 제출 시각을 로컬에 남겨 판정했다. 「완료」 판정도 `COMPLETE`가 아니라 `CREATED` 이상이어야 했다(생성과 완료 사이에 사용자 검증 단계가 있다).
- **같이 잡은 것**: 요청 인터셉터가 `/auth/signup` 접두사를 「공개 요청」으로 보고 토큰을 떼고 있었는데, 가입 완료 API 경로가 그 접두사에 걸렸다. 그래서 서버는 호출 주체를 몰랐고(AI 사용 로그의 사용자 칸 대부분이 비어 있음), 「토큰 없음 = 비인증」으로 분당 5회 제한을 걸어 429가 났다. **헤더만 붙여도 429가 사라졌다.**

### (2) 재시도가 409로 막혀 설문 화면에 갇혔다
- **증상**: 요청이 끊긴 사이 서버는 페르소나를 만들었는데, 사용자의 재제출 3번이 전부 409 「이미 사용 중인 이메일」 → 앱은 알림만 띄우고 제자리. 7일간 소셜 가입자 6명.
- **원인(서버 동료와 로그·코드로 확정)**: ① 서버가 「가입 도중 재로그인한 사람」의 로그인 응답에서 가입 경로 정보(`authProvider`)를 빼고 내려줬다. 앱은 그 값을 복사해 보관 → 가입 요청에서 키가 통째로 빠졌다. ② 서버 중복 판정이 그 빈 값과 `CREATED`를 「이미 가입 완료」로 오인했다. ③ 앱은 그 409를 「기다릴 필요 없는 에러」로 보고 알림만 띄웠다.
- **해결(앱)**: 가입 경로 값이 비어 있으면 **저장할 때가 아니라 보내는 순간** 마지막 로그인 수단으로 채운다 — 이미 빈 값이 저장된 폰도 다시 제출하면 살아난다. 409가 오면 가입 상태를 한 번 조회해 페르소나가 있으면 성공 경로로 보낸다(폴링하지 않는다 — 진짜 중복에 2분을 기다리게 하지 않으려고). 서버는 응답·판정을 같은 날 고쳤다.
- **검증**: 서버 동료가 테스트 계정에 「제출 직전 페르소나가 이미 생성된」 상태를 심어 운영 사례를 그대로 재현 → 수정 후 정상 가입(201) → 리포트까지 확인.

### (3) 결국 비동기로 바꿨다
- **결정**: 서버와 계약을 새로 잡았다 — 가입 요청에 `async: true`를 실으면 **즉시 202 + 「생성 중」**으로 답하고, 앱은 (1)에서 만든 폴링을 정상 경로로 쓴다. 옛 서버는 이 플래그를 무시하고 기존처럼 동기 201로 답하므로 **배포 순서와 무관하게 안전**하다.
- **실패 처리**: 생성이 실패하면 상태 API가 실패 플래그를 준다 → 「다시 시도」. 이때 설문 답이 메모리에 없으면(생성 중에 앱을 새로 켠 경우) 서버 임시저장으로 채우고, 그래도 빈 문항이 있으면 **빈 설문을 보내지 않고** 그 문항으로 데려간다. 이 과정에서 **마지막 문항은 임시저장이 안 되고 있던** 것도 발견했다(「다음 페이지로 넘어갈 때」만 저장했기 때문).
- **계측도 옮겼다**: 가입 완료 광고 이벤트는 「접수」가 아니라 **「생성 확인」 시점**에 보낸다. 202를 받은 순간 보내면 실패한 가입까지 완료로 잡힌다.
- **실기기 검증**(서버 동료와 합동): 폴링 중 실패 전환 → 다시 시도 → 백그라운드 25초 → 복귀 즉시 조회 → 리포트 / 재로그인 + 11문항만 저장된 상태 → 남은 문항 안내 → 리포트.

- **남긴 것**: 「실패율」을 보기 전에 **실패로 분류된 것이 정말 실패였는지**부터 쟀다. 끊긴 요청의 대부분은 성공이었고, 고칠 대상은 서버 처리가 아니라 앱의 해석이었다. 그리고 상태 하나가 두 의미(`NONE` = 미제출/생성 중)를 가질 때는 서버에 상태를 늘려 달라기 전에, **그 차이를 이미 아는 쪽(제출한 앱)** 이 판정하는 게 더 싸다.

## 25. 앱을 켤 때 토큰 갱신이 요청 수만큼 나가던 구조 — 동시에 받은 401을 하나로 묶기

- **증상**: 홈 기동 때 나가는 요청을 정리하다 보니, 액세스 토큰이 만료된 상태로 앱을 켜면 병렬로 나간 요청들이 **각자 401을 받고 각자 `/auth/refresh`를 호출**하고 있었다. 같은 화면이 두 번 마운트되는 경로(푸시로 홈 탭에 들어올 때), 아무도 쓰지 않는 30초 미읽음 폴링도 요청 수를 키우고 있었다.
- **왜 위험한가**: 갱신 응답이 새 리프레시 토큰을 돌려주는 방식(회전)이면, 먼저 끝난 갱신이 나머지가 들고 있던 리프레시 토큰을 무효로 만든다. 늦게 끝난 갱신은 「만료」로 판정되고, 앱은 그걸 「리프레시 토큰이 진짜 죽었다」로 보고 **로그아웃**시킨다. 사용자 입장에서는 이유 없이 로그인 화면으로 튕기는 버그가 된다.
- **해결**:
  - **갱신은 한 번만(single-flight)**: 진행 중인 갱신 Promise를 하나만 들고, 동시에 401을 받은 요청은 새로 갱신하지 않고 그것을 기다린다.
  - **이미 갱신됐으면 재시도만**: 401을 받은 요청이 보낼 때 붙인 토큰과 지금 저장된 토큰이 다르면, 다른 요청이 그사이 갱신을 끝낸 것이다 → 갱신 없이 새 토큰으로 재시도만 한다.
  - **갱신 중엔 요청을 잠깐 세운다**: 요청 인터셉터가 진행 중인 갱신을 기다렸다가 새 토큰을 붙인다. 낡은 토큰으로 나가 401을 또 받는 일을 없앤다.
  - 기동 경로도 같이 줄였다 — 탭 초기값을 첫 렌더에 반영해 홈이 두 번 그려지지 않게, 쓰지 않던 폴링은 제거, 배지 갱신은 탭 전환 때만.
- **유지한 원칙**: 갱신은 여전히 `401`에서만 발화하고 재시도는 한 번뿐이다([14번](#14-24시간마다-로그아웃되던-문제--원인이-우리-쪽이-아니었다)의 「403은 갱신하지 않는다」 그대로). 바꾼 것은 「누가 갱신하는가」뿐이다.
- **남긴 것**: 갱신 로직은 요청 하나 기준으로 짜면 맞아 보인다. **동시에 여러 요청이 같은 상태를 바꾸려 할 때**를 따로 물어야 드러난다.

## 26. 적어 둔 네이티브 설정이 한 번도 적용되지 않았다 — 읽히지 않는 파일, 틀린 옵션 이름

같은 계열의 문제가 한 달 간격으로 두 번 나왔다. 둘 다 **설정이 실행되지 않는 경로**에 있어서 틀려도 아무 일도 일어나지 않았다.

### (1) app.json에만 적어 둔 플러그인 4건이 어디에도 적용되지 않았다
- **증상**: 상태바 알림 아이콘을 흰색 실루엣으로 바꿨는데 기기에서는 계속 빨간 네모(앱 아이콘)가 나왔다. 다크모드 강제 해제 플러그인도 넣었는데 동작하지 않았다.
- **원인**: `app.config.js`가 정적 객체를 내보내면 Expo는 `app.json`을 **통째로 무시한다.** 그런데 플러그인 설정 4건(카카오 로그인 키, 알림 아이콘, 다크모드 강제 해제, 사진 저장 권한 문구)은 `app.json`에만 있었다. `expo config --type public`의 plugins 목록으로 확인했다.
- **가장 위험했던 것**: 카카오 로그인 플러그인. 그때 로그인이 되던 건 예전에 네이티브 폴더를 손으로 고쳐 둔 덕이었고, 네이티브 프로젝트를 한 번 다시 생성하면 라이브러리 기본 키가 들어가 안드로이드 카카오 로그인이 전부 막히는 구조였다([엔지니어링 결정 7](./engineering-decisions.md#7-네이티브-설정을-기억이-아니라-git과-빌드-가드로-지킨다)의 배경이 된 사고와 같은 경로).
- **해결**: 4건을 `app.config.js`로 옮기고, `app.json`은 지금 읽히지 않는다는 것과 어디에 넣어야 하는지를 주석으로 남겼다. 네이티브 빌드에만 영향이라 무선 업데이트가 아니라 다음 스토어 빌드부터 적용된다.

### (2) 새 빌드 머신에서 네이티브 프로젝트 생성이 실패 — 플러그인 옵션 이름 한 단어
- **증상**: 빌드 머신을 하나 더 들이면서 깨끗한 clone에서 Expo 네이티브 프로젝트 생성(`expo prebuild`)을 돌리자 `withAndroidStringsBaseMod: Cannot read properties of undefined (reading 'replace')`로 실패했다. 실패하면서 저장소에 추적되는 네이티브 파일 일부(서명 설정·알림 아이콘)까지 망가뜨렸다.
- **처음 판단**: 새 머신의 환경 차이(Node·SDK 버전)를 의심할 만했지만, 에러가 **문자열 리소스를 쓰는 단계**에서 `undefined`를 받았다는 점에서 설정 값 쪽을 먼저 봤다.
- **원인**: (1)에서 옮긴 카카오 로그인 플러그인이 `{ nativeAppKey }`로 키를 넘기고 있었는데, 플러그인은 `kakaoAppKey`를 읽는다. 키가 `undefined`로 들어가 문자열 치환에서 터졌다. 같은 이유로 매니페스트의 OAuth 스킴도 `kakaoundefined`가 될 수 있었다.
- **왜 옮긴 뒤에도 몰랐나**: 운영 빌드는 이미 있는 네이티브 폴더(올바른 키가 든 리소스·매니페스트를 git으로 추적)로 빌드하고, OTA는 JS만 내보낸다. 이 경로만 오래 써 와서 **플러그인이 실제로 도는 순간이 없었다.** 릴리즈 빌드에는 키가 기본값이면 실패시키는 검사도 있어 운영 영향은 없었다.
- **확인법**: 파일을 바꾸지 않는 `expo config --type introspect`로 플러그인이 만들 결과를 미리 본다. 수정 전엔 키가 `undefined`, 수정 후엔 문자열 리소스·OAuth 스킴·iOS 쪽 키까지 제대로 채워지는 것을 확인했다.
- **해결**: 옵션 이름 한 단어(`nativeAppKey` → `kakaoAppKey`). 새 머신 쪽에는 「생성 전 복구할 추적 파일 목록」과 「git에 없는 설정 파일을 넣을 위치」를 점검 목록으로 넘겼다.

- **남긴 것**: 설정이 **실행되지 않는 경로**에 있으면 틀려도 아무도 모른다. (1)은 「적었다」를 「적용됐다」로 믿었고, (2)는 「옮겼다」를 「동작한다」로 믿었다. 한 번도 안 돈 설정은 맞는지 알 수 없다고 보고, **돌리지 않고 결과를 미리 보는 도구**(`expo config`)로 실제로 만들어질 값을 먼저 확인한다.

## 27. 기기 알림을 끄면 마케팅 수신 거부도 못 하던 문제 — 배달 게이트와 동의 기록은 다른 층

- **증상**: 기기(OS) 알림 권한이 꺼져 있으면 알림 설정 화면의 토글이 전부 잠기고, 누르면 OS 설정으로 보냈다. 여기엔 **마케팅 수신 동의 토글도** 포함돼 있었다 → 기기 알림을 끈 사용자는 앱 안에서 광고성 수신 동의를 **철회할 방법이 없었다.**
- **원인**: 「OS 권한이 없으면 어떤 토글도 의미가 없다」는 판단을 모든 토글에 똑같이 적용했다. 서비스 알림 토글엔 맞는 말이다(어차피 배달이 안 된다). 하지만 마케팅 토글은 **배달 설정이 아니라 동의 기록**이라 성격이 다르다. 광고성 정보 수신 동의는 언제든 철회할 수 있어야 하고, 서버도 OS 권한과 무관하게 이 값을 저장한다.
- **해결**: 마케팅 토글에서만 잠금을 뺐다. 마스터·세부 토글은 그대로 OS 권한에 묶어 둔다. 바꾸면 서버가 남긴 처리 일시로 「동의/거부 처리되었습니다」를 안내하는 흐름은 그대로 돈다.
- **남긴 것**: [엔지니어링 결정 10](./engineering-decisions.md#10-알림-상태를-세-층으로-나누되-배달-가능-여부는-한-곳에만-둔다)에서 알림 상태를 OS 권한·수신 설정·동의 기록 세 층으로 나눴는데, 화면의 잠금 규칙은 그 구분을 따르지 않았다. **층을 나눴으면 UI 규칙도 층마다 따로** 정해야 한다.

## 28. 쇼츠 스와이프 재생 4초 → 1.85초 — 플레이어를 장마다 만들지 않고 하나를 재사용

- **증상**: 세로 쇼츠 피드에서 다음 장으로 넘기면 영상이 나오기까지 4~5초가 걸렸고, 10~16장에 1~2장꼴로 **멈춘 채 안 나오는 카드**가 있었다.
- **측정부터**: 실기기(보급형 안드로이드)·실 API로 20장을 넘기며 「스와이프 → 재생 시작」을 쟀다. 중앙값 **3.98초.** 동시에 살아 있는 플레이어 수를 바꿔 가며 보니 **멈춘 카드 수가 플레이어 수에 비례했다**(3개: 화면 밖 초기화에 14~102초, 멈춤 1~2장 / 1개: 37장 중 0장).
- **원인**: 세로 리스트(FlatList)가 장마다 임베드 플레이어(WebView)를 새로 만들었다. 비용 대부분이 영상이 아니라 **플레이어 초기화**였다.
- **해결**:
  - 리스트를 **3칸 페이저**로 바꾸고 플레이어는 **한 번만** 만든다. 스와이프하면 영상만 갈아 끼운다(`loadVideoById`). 20장을 넘기는 동안 플레이어 생성 1회, WebView 생성 1회.
  - 멈춘 카드 워치독: 활성 장이 유예 시간 안에 준비 신호를 못 내면 다시 만든다. 이 집계는 「영상 오류 신고」와 **다른 API**로 보낸다 — 신고는 3건이 쌓이면 영상이 영구 만료되는데, 기기 자원 문제를 신고로 보내면 멀쩡한 영상이 사라지기 때문이다.
- **재사용을 무너뜨릴 뻔한 것**: WebView `source` 객체가 영상 id에 반응하게 두면 영상을 바꿀 때마다 **페이지를 통째로 다시 로드**해 재사용이 무의미해진다. 실측에서 1.76초가 5.08초로 튀어 잡았다. `source`는 플레이어를 새로 만들 때만 바뀌게 고정했다.
- **결과**: 스와이프 → 재생 중앙값 **3.98초 → 1.85초**(두 번 재현: 1.85 / 2.03). 첫 진입은 그대로다 — 초기화 비용은 첫 장에서 한 번 낸다.
- **같이 잡은 것**: 갈아 끼운 영상엔 반복 재생이 안 걸려 종료 화면이 뜨는 것(종료 이벤트에서 다시 재생), 목록이 줄어드는 렌더에서 인덱스가 범위를 벗어나 크래시 나던 것(effect 보정은 한 프레임 늦어서 **렌더에서** 클램프).
- **남긴 것**: 「느리다」를 「영상이 무겁다」로 읽지 않고, 무엇이 몇 번 만들어지는지부터 셌다. 숫자가 플레이어 수에 비례한다는 걸 보고 나서야 고칠 대상이 정해졌다.

## 29. 실시간 대화가 「간헐적으로 비어 보이던」 문제 — 연결 실패·재연결 때 구독이 사라졌다

공개 대화방(실시간 소켓)과 1:1 대화방에서 같은 구조의 문제가 세 번 나왔다.

### (1) 첫 연결이 실패하면 메시지가 영영 안 왔다
- **증상**: 가끔 방에 들어가도 대화가 하나도 오지 않았다. 나갔다 들어오면 정상.
- **실측**: 연결 직후 끊겨 `connect()`가 실패로 끝났고, 화면이 건 구독 3개(대화·이벤트·오류 큐)는 전부 「연결 안 됨, 구독 불가」로 **버려졌다.** 25초 뒤 재연결은 성공했지만 구독은 0개였다. 소켓은 살아서 ping/pong만 돌았다.
- **원인**: 구독 헬퍼가 미연결일 때 아무것도 남기지 않고 돌아섰다. 재연결 복구는 「남아 있는 구독」만 다시 걸기 때문에 되살릴 게 없었다. 나갔다 들어오면 이미 연결된 상태라 구독이 바로 붙어서 「간헐적」으로 보였다.
- **해결**: 미연결이면 버리지 않고 **예약**해 두고, 연결되는 순간 복구 루틴이 건다. 복구 루틴은 재연결 때만이 아니라 **첫 연결 성공에서도** 돌게 옮겼다. 서버를 재기동해 소켓을 끊었다 붙여 구독 3건이 자동 복구되는 것을 확인했다.

### (2) 메시지 조회가 실패하면 「대화 없는 방」과 똑같아 보였다
- **원인**: 조회가 실패하면 목록 state는 건드리지 않고 로딩만 껐다. 서버가 「대화 없음」을 준 화면과 구분되지 않았다.
- **해결**: 응답이 배열이 아니면 실패로 보고 0.4초·0.8초 간격으로 두 번 더 받는다. 세 번 다 실패하면 로그를 남긴다. 화면에 돌아왔는데 메시지가 없으면 한 번 더 받는다 — 진짜 빈 방이면 결과가 같으니 실패로 비어 보이던 경우만 복구된다.

### (3) 1:1 대화방 상태 구독도 재연결 뒤 살아나지 않았다
- **증상**: 방을 열어 둔 사이 재연결이 일어나고 상대가 나가면, 입력창이 안 잠기고 보낸 말이 **조용히 실패**했다(iOS 담당 동료 제보).
- **원인**: (1)을 고칠 때 만든 예약·복구 경로를 이 구독은 타지 않았다. 별도 목록에 넣고 있어 복구 루틴이 보지 못했다.
- **해결**: 같은 헬퍼로 옮겼다. 해제는 「아직 내 핸들러일 때만」 하게 바꿨다 — 대화 목록과 대화방이 같은 주소를 번갈아 잡을 때, 앞 화면의 늦은 해제가 뒤 화면의 구독을 지우지 않게. 와이파이를 끊었다 켜서 재구독 로그 확인 → 상대 나가기 → 새로고침 없이 잠기는 것을 실기기로 봤다.

- **남긴 것**: 「간헐적」은 원인이 없다는 뜻이 아니라 **조건을 아직 못 찾았다**는 뜻이었다. 그리고 한 곳을 고친 뒤에도 같은 일을 하는 다른 경로가 헬퍼를 안 타면 그대로 남는다 — 구독은 전부 한 헬퍼를 지나게 했다.

## 30. 가입도 안 끝난 계정에 출석 보상이 지급됐다 — 로그아웃 뒤에도 홈 화면이 살아 있었다

- **증상**: 로그아웃하고 새 이메일로 가입을 시작했을 뿐인데, 본인인증도 끝나지 않은 계정에 **출석 체크가 나가 보상이 지급**됐다. 실기기 로그에서 로그인 확인 2초 뒤 출석 API가 200으로 찍혀 있었다.
- **처음 판단**: 출석은 홈에 들어올 때만 부르니 가입 도중엔 불릴 수 없다고 봤다(코드 주석에도 그렇게 적혀 있었다).
- **원인**: 출석 코드가 아니라 **로그아웃의 화면 정리**였다. 로그아웃이 `router.replace('/start')`로 맨 위 한 장만 갈아 끼워서, 홈 → 설정 → 로그아웃이면 설정만 시작 화면으로 바뀌고 **홈은 그 아래 살아 있었다.** 언마운트되지 않으니 effect도 붙어 있고, 다른 계정으로 로그인하는 순간 사용자 id가 바뀌며 홈의 출석 effect가 다시 돌았다. 로그아웃이 중복 방지 플래그까지 초기화해서 가드도 걸리지 않았다. 접속 이벤트 보상도 같은 구멍으로 나갔다.
- **해결**: 로그인 방향은 이미 같은 이유로 스택을 비우고 있었다. 로그아웃도 짝을 맞춰 **스택을 전부 비운 뒤** 시작 화면으로 보내는 함수 하나를 만들고, 로그아웃·탈퇴 4곳에 적용했다.
- **남긴 것**: 「이 화면에 들어올 때만 돈다」는 전제는 화면 이동에는 맞지만 **나간 줄 알았던 화면이 남아 있을 때**는 깨진다. 계정이 바뀌는 지점은 화면이 아니라 스택 단위로 정리해야 한다.

## 31. 연타 한 번에 채팅방이 여러 개 — 잠금은 「요청이 끝날 때」가 아니라 「돌아왔을 때」 푼다

- **증상**: 홈 「오늘의 인연」 카드의 질문 버튼을 빠르게 두 번 누르면 채팅방이 여러 개 열리고 **서로 다른 질문이 여러 개** 전송됐다(사용자 제보). 누르는 즉시 「보낸 질문」으로 표시돼 카드의 질문이 바뀌었기 때문이다.
- **원인**: 방 생성 → 질문 전송 → 화면 이동까지 1~3초가 걸리는데, 그사이 처리 중 잠금이 없었다. 여러 카드를 동시에 누르거나 카드 본체(프로필)를 같이 눌러도 화면이 쌓였다.
- **해결**:
  - 질문과 카드 본체 탭을 **잠금 하나로** 묶었다. state가 아니라 ref로 잡아 같은 프레임의 두 번째 탭도 막는다. 처리 중인 카드는 흐리게 보여 준다.
  - 잠금은 이동 직후가 아니라 **홈으로 돌아왔을 때(포커스)** 푼다. 이동 직후에 풀면 넘어가는 애니메이션 중에 탭이 또 통한다. 포커스가 안 돌아오는 예외에 대비해 3초 뒤에도 푼다.
  - 「보낸 질문」 기록은 **전송 성공 뒤로** 옮겼다. 방 생성이 실패해도 질문이 사라지던 것도 같이 고쳐졌다.
- **검증**: 첫 카드 질문·옆 카드 질문·카드 본체를 거의 동시에 6번 → 방 생성 1, 질문 1, 화면 1장, 뒤로 가면 바로 홈.

## 32. 동성 프로필을 열면 매칭 버튼이 한 프레임 보였다 사라졌다

- **증상**: 동성 프로필 열람을 켠 뒤, 동성 프로필에 들어가면 매칭 신청 버튼이 **한 프레임** 보였다가 사라졌다.
- **원인**: 프로필 상세는 응답이 오기 전까지 상대 성별을 몰라 기본값(이성)으로 그렸다.
- **해결**: 목록에는 이미 성별이 있으니 **진입할 때 같이 넘겨** 첫 렌더부터 맞게 그린다. 라운지 3곳(글쓴이·댓글 작성자·소개글 하단)과 실시간 대화방 3곳(이름·아바타·액션시트)에서 넘기게 했다.
- **남긴 것**: 「응답이 오면 고쳐진다」는 화면은 첫 프레임이 틀린다. 앞 화면이 이미 아는 값은 넘겨서 **첫 프레임을 맞게** 그린다.

## 33. 말풍선이 끝없이 떨었다 — 잰 값으로 다시 배치하는 되먹임

- **증상**: 소개글 상세의 장면 일러스트 위 말풍선이 멈추지 않고 미세하게 좌우로 떨었다.
- **원인**: 말풍선 위치를 소수점으로 주면 픽셀 정렬 때문에 잰 크기가 미세하게 달라지고, 그 값으로 위치를 다시 계산해 또 움직였다. x가 41 ↔ 42를 무한 왕복하는 **레이아웃 되먹임**이었다.
- **해결**: 위치를 정수로 못 박고, 새로 계산한 결과가 이전과 같으면 state를 갈지 않는다.
- **남긴 것**: `onLayout`으로 잰 값을 다시 레이아웃 입력으로 쓰면 수렴하는지부터 확인해야 한다. 「같으면 안 바꾼다」 한 줄이 루프를 끊는다.

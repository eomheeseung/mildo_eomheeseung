# 실운영 트러블슈팅

실서비스를 운영하며 진단·해결한 사례입니다. "왜 그런지"를 데이터로 규명한 과정에 초점을 뒀습니다.

## 1. 소셜 가입자가 설문 완료 직전에 막히던 버그

**증상** — 카카오로 가입한 유저가 12문항 페르소나 설문을 다 채우고 "완료"를 누르는 순간 "허용되지 않은 이메일 도메인" 오류. @kakao.com 가입자 15명 중 완주 0명.

**원인** — 이메일 도메인 화이트리스트 검증이 **v1(이메일 가입) 경로에만** 있고, 소셜 가입이 타는 `signupWithPersona` 경로의 화이트리스트에는 `kakao.com`·`daum.net`·`nate.com`·`hanmail.net`이 누락돼 있었음. 소셜 로그인은 통과하지만 마지막 가입 확정에서 막히는 구조.

**해결** — 화이트리스트를 통합하고 소셜 도메인을 추가. 프로덕션 로그와 DB로 "완주 0명"을 먼저 정량 확인한 뒤 수정 → 배포 후 send-code 200 검증.

## 2. NICE 본인인증 CI 도난 (1인 1계정)

**증상** — 재인증할 때마다 기존 계정의 CI/DI가 새 계정으로 옮겨가, 기존 계정이 본인인증을 잃음.

**원인** — 재인증 로직이 CI 중복 검사 없이 새 계정에 CI를 **덮어씀**.

**해결** — `users.ci` 유니크 제약 + "살아있는 계정이 이미 그 CI를 보유하면 가입 거부(U007)". 탈퇴 계정의 CI는 승계 허용. 운영 데이터로 기존 CI 보유 계정이 전부 distinct임을 확인해 유니크 인덱스가 깨끗이 생성되는지 사전 검증.

**왜 앱 검사만으로는 부족한가 (TOCTOU)** — 중복 가드를 넣어도 앱 로직은 `findByCi`로 **검사(check)한 뒤 저장(act)** 하는 구조라, 검사와 저장 사이에 같은 CI의 요청이 끼어들면 둘 다 "중복 없음"을 통과합니다(time-of-check-to-time-of-use). 이 틈은 애플리케이션 레벨에서 없앨 수 없으므로 역할을 나눴습니다 — **앱 가드는 정상 케이스의 UX·에러 메시지 담당, 경합의 최종 방어선은 DB 유니크 제약**. 경합을 뚫고 들어온 두 번째 쓰기는 DB가 거부하므로 검사의 시간차가 무해해집니다. 같은 원리로 9번의 이중 지급도 원장 유니크가 마지막에 막고 있었고, 이벤트 보상 지급은 아예 검사·행동을 `INSERT IGNORE` + UNIQUE(slot, user) 한 문장으로 원자화해 틈 자체를 없앴습니다.

## 3. push-consent 403 — 백엔드가 아니었다

**증상** — 알림 동의 API가 403.

**규명** — 처음엔 서버 로직을 의심했으나, 서버 로그에 해당 요청이 **0건**. Spring Security에서 토큰 누락은 401이 아니라 403으로 떨어짐 → **클라이언트가 Authorization 헤더를 안 실은 것**. 도메인 이전(dev.mildo.us → mildo.us) 중 origin-scoped localStorage의 토큰이 유실된 것이 원인. 백엔드는 정상이었음을 데이터로 입증하고, 프론트에 원인을 전달.

**교훈** — "500이 아닌 4xx는 클라이언트 계약 문제일 수 있다"를 로그 부재로 먼저 확인.

## 4. Claude 5 세대 API 대응

**증상** — 최신 모델(sonnet-5 등)로 바꾸자 ①`temperature is deprecated`(400) ②그 후 `No content to map`(빈 응답 파싱 실패).

**원인** — ①신세대 모델이 `temperature` 파라미터를 폐기. ②복잡한 프롬프트에서 응답 `content[0]`에 `thinking` 블록이 자동 삽입돼, 기존의 `content[0].text` 추출이 빈 문자열을 반환.

**해결** — ①지원 모델에만 `temperature`를 싣도록 분기. ②`type=text`인 **첫 블록**을 찾아 추출(구형 모델은 동작 변화 없음). 운영 서버에서 직접 API를 curl로 때려 `content_blocks=2, block0=thinking`을 확인한 뒤 수정.

[`docs/ad-spend.md`](./ad-spend.md#연동하며-겪은-삽질-기록) 참고 — API 버전 sunset(v21만 유효), MCC 헤더로 인한 권한 거부, 통화 micros 환산.

## 6. 앱이 24시간마다 로그아웃되던 문제 — 401을 안 주고 있었다

**증상** — 유저가 하루 주기로 로그아웃. 토큰 갱신이 있는데도 발화하지 않음.

**규명** — 진입점(`AuthenticationEntryPoint`)을 지정하지 않아 Spring Security 기본값(`Http403ForbiddenEntryPoint`)이 적용됐고, **토큰 없음·만료·무효가 전부 403**으로 나갔습니다. 앱 HTTP 인터셉터는 관례상 **401에서만** 토큰 갱신을 트리거하므로 갱신이 아예 시도되지 않았고, access 토큰 수명(24h)이 다하는 순간 그대로 로그아웃됐습니다.

운영 로그로 정량 확인(2026-07-25~27):

```
/auth/me       200 723건 / 403 24건 / 401 0건
/auth/refresh  모바일 UA 기준 호출 0건
403 수신자     전부 CFNetwork(iOS)·okhttp(AOS)
```

로그에 남아 있던 refresh 호출(7/20 59건, 7/22 75건)은 **전부 관리자 웹**이었습니다. 즉 앱은 refresh 토큰을 받고도 한 번도 쓰지 못한 상태였습니다.

**해결** — 미인증은 401(`JwtAuthenticationEntryPoint`), 인증됐으나 권한 부족은 403 유지(`JwtAccessDeniedHandler`)로 분리. 403을 남긴 이유는 **갱신해도 풀리지 않는 케이스**(정지·차단·구독 필요)라 재시도 대상이 아니기 때문입니다. Authorization 헤더 유무로 "만료/무효"와 "미첨부"도 구분해 메시지를 다르게 줍니다.

## 7. 탈퇴가 12회 연속 실패 — try/catch로는 격리가 안 된다

**증상** — 회원 탈퇴가 운영에서 전면 실패. 12회 연속 롤백.

**원인** — 부수 작업(`analytics_events` 파기)을 `try/catch`로 감싸 "실패해도 탈퇴는 진행"을 의도했는데 성립하지 않았습니다. **같은 트랜잭션에서 난 예외는 잡아도 rollback-only 마크가 남아**, 커밋 시점에 `UnexpectedRollbackException`으로 터집니다. 테이블 부재(1차)·FK 위반(2차)이 연달아 같은 방식으로 탈퇴를 깼습니다.

**해결** — 진짜 격리는 **호출 대상이 `REQUIRES_NEW`여야** 성립하므로 `AnalyticsEventPurger`를 별도 빈으로 분리했습니다.

다만 **파기 본체는 `REQUIRED`로 남겼습니다** — `chat_rooms`가 앞 단계에서 이미 잠겨 있어 `REQUIRES_NEW`로 떼면 자기 자신과 락 경합이 나 교착됩니다. "격리가 항상 옳다"가 아니라 **락 보유 상태를 보고 결정**해야 하는 지점이었습니다.

## 8. 이벤트 보상이 앱을 열지 않아도 지급되던 문제

**증상** — 「접속하면 베리 지급」 이벤트에서, 앱을 열지 않은 유저에게도 보상이 나감.

**규명** — 방문 추적 인터셉터가 인증 요청마다 지급 로직을 불러 **요청 하나만 지나가도 "접속"으로 판정**하고 있었습니다. 화면을 봤는지와 무관하므로, **푸시 도착 시 OS가 앱을 깨우며 보내는 백그라운드 요청만으로도** 보상이 나갔습니다.

```
8/1 16시 슬롯 — 캠페인 푸시 발송 2초 뒤 첫 지급
               지급 11건 전부 인터셉터 경로, 정상 경로(핑) 지급 0건
```

앱을 실제로 연 경우조차 인터셉터가 항상 핑보다 빨라 **정상 경로가 한 번도 발화하지 못했습니다.** 게다가 두 경로는 알림 방식이 달라(핑은 앱이 화면에 띄우므로 푸시 없음, 인터셉터는 「지급 완료」 푸시 발송) 쓰지 않기로 한 푸시가 계속 나갔습니다.

**해결** — 지급 경로를 `POST /v1/event/ping` 하나로 통일. 인터셉터 호출은 제거하고 **재연결 금지 경고 주석과 함께** 죽은 코드로 남겼습니다(다음 사람이 "왜 안 쓰지?" 하고 되살리는 것을 막기 위해).

## 9. 동시 지급 하나가 조용히 사라지던 문제 ★

**증상** — 앱을 켠 순간 이벤트 보상과 출석 보상이 함께 지급돼야 하는데, 한쪽이 안 들어옴. 에러 화면도 없음.

**규명** — nginx 액세스 로그 전수 집계로 실패 지점을 특정했습니다.

```
2026-08-02
  attendance/check-in   200 110건 / 409 2건
  event/ping            200 868건 / 409 1건
  → 409 3건이 전부 "앱 기동 시 두 요청이 같은 초에 나간" 경우
```

베리 잔액 테이블에 `@Version` 낙관적 락이 걸려 있는데, **적립 경로만 락 없이 읽고 있었습니다.** 두 트랜잭션이 같은 버전을 읽고 각자 잔액을 올리면 늦게 커밋하는 쪽이 충돌로 지고 409 + 트랜잭션 전체 롤백이 됩니다. **적립에는 재시도가 없어 그 지급이 그대로 사라졌습니다.**

실패 조건이 "동시에 썼다"가 아니라 **"읽은 뒤 남이 먼저 커밋했다"** 라는 점, 그리고 JPA 쓰기 지연이 읽기와 쓰기 사이를 벌려 그 창을 키운다는 점이 이 건의 핵심입니다. 트랜잭션 생애주기 단위의 분석은 [`engineering-decisions.md` §5](./engineering-decisions.md#무슨-일이-벌어지는가--트랜잭션-생애주기로-보기)에 정리했습니다.

실제 피해를 DB 타임스탬프로 역추적:

| 유저 | 진 요청 | 실제 지급 | 지연 |
|---|---|---|---|
| A | 출석 12:00:14 | 12:00:53 | 39초 (앱 재기동으로 우연히 복구) |
| B | 출석 12:29:48 | **15:20:32** | **2시간 51분** |
| C | 이벤트 핑 12:17:11 | 12:17:11 | 0초 (반복 호출이라 자동 복구) |

**핑은 주기 호출이라 스스로 복구되지만, 출석은 앱 콜드스타트에만 호출**되므로 유저가 앱을 다시 켤 때까지 안 들어옵니다.

**재현·검증** — 원인 가설을 확정하려고 계정 읽기 직후에 `Thread.sleep(3000)`을 임시로 넣어 충돌 창을 강제로 벌리고, 같은 유저에게 두 요청을 동시 발사했습니다.

```
락 없음(수정 전 재현)  ping 409 / check-in 200 → 이벤트 3베리 유실, 잔액 +2
비관적 락(수정 후)     둘 다 200, 커밋이 3초 간격으로 직렬화, 잔액 +5 정확
```

**해결** — 적립 경로도 비관적 락으로 전환. 선택 근거와 대안 비교는 [`engineering-decisions.md`](./engineering-decisions.md#5-잔액-동시-갱신--왜-비관적-락인가)에 정리했습니다.

**돈은 틀어지지 않았습니다.** 원장 유니크 제약이 이중 지급을 막고 있었고, 실패한 쪽은 롤백돼 "잘못 준 것"이 아니라 **"줘야 할 것이 안 들어간"** 상태였습니다.

## 10. 같은 `type` 값을 두 기능이 나눠 쓰다 생긴 오분류

**증상** — 관리자 환불 통계에 결제 환불이 아닌 건이 섞임. 결제를 한 번도 하지 않은 무료 회원이 **탈퇴 시 5년 보존 대상**으로 잡힐 수 있는 상태.

**원인** — 관리자 백오피스가 프로필 사진 보상을 회수할 때 원장에 `type='CLAWBACK'`으로 기록하는데, **그 값이 결제(충전) 환불과 같았습니다.** 백엔드는 `CLAWBACK`을 결제 환불 전용으로 해석하고 있어 사진 회수가 대금 거래로 오분류됐습니다.

전자상거래법상 결제기록 보존 의무 때문에 만든 규칙이라, **대금 거래가 없는 회원의 이름·연락처가 보존되는 것은 즉시 파기 원칙 위반**입니다.

**해결** — 회수 행에는 `ref_type='PHOTO_REVIEW'`가 함께 붙으므로 집계·판정에서 제외했습니다. **원장 행은 손대지 않았습니다** — 읽는 쪽만 고쳐서 과거 행까지 소급 정상화됩니다. 원장은 불변이어야 하고, 데이터를 고치면 감사 추적이 깨집니다.

> 근본적으로는 `type`에 값을 하나 더 만드는 게 맞지만, 그러면 백오피스(PHP)와 **동시 배포**가 강제됩니다. `ref_type` 제외만으로 목적이 달성되므로 이번엔 하지 않았습니다.

## 11. `ddl-auto`는 ENUM 컬럼을 늘려주지 않는다

**상황** — 커뮤니티 댓글을 붙이면서 신고 대상에 `COMMENT`를 추가해야 했습니다. 신고 테이블의 `reason`·`target_type`은 MySQL **네이티브 ENUM 컬럼**입니다.

**함정** — 자바 `enum`에 값을 추가하면 코드는 컴파일되고 로컬 `ddl-auto`도 조용히 지나가지만, **기존 ENUM 컬럼의 값 목록은 그대로**입니다. `ddl-auto`는 없는 컬럼을 만들 뿐 있는 컬럼의 타입 정의를 고치지 않습니다. 이 상태로 배포하면 앱은 멀쩡히 뜨고, **첫 댓글 신고가 들어오는 순간** INSERT가 실패합니다 — 배포 검증에서는 안 잡히고 실사용에서 터지는 부류입니다.

**처리** — 배포 전 점검에서 잡아 `ALTER ... MODIFY COLUMN`을 수동 반영했습니다. 이때 **새 값은 반드시 목록 맨 뒤에** 붙입니다 — 뒤에 추가하면 인플레이스로 끝나지만, 중간에 끼우거나 순서를 바꾸면 테이블 재작성이 필요하고 저장값 해석이 어긋날 여지가 생깁니다. 이후 "자바 enum에 값을 추가하면 해당 컬럼의 DB 타입을 확인한다"를 배포 체크리스트로 남겼습니다.

## 12. "알림 거부율 67%"는 측정 오류였다

**상황** — OS 알림 권한 상태를 수집하는 API를 넣고(계측 전용 — 발송 조건에는 쓰지 않음) 운영 데이터를 봤더니 **거부율이 67%**로 나왔습니다. 심각한 온보딩 문제로 보였습니다.

**규명** — 숫자를 발표하기 전에 수집 경로를 검증하다가, 앱이 Android에서 **권한을 한 번도 요청하지 않은 상태를 `DENIED`로 보고**하고 있는 것을 찾았습니다. Android 권한 API에는 iOS의 "미결정(not determined)"에 해당하는 상태가 없어, "물어봤는데 거부"와 "아직 안 물어봄"이 같은 값으로 뭉개진 것입니다(`canAskAgain`으로만 구분 가능). 즉 67%의 상당수는 거부한 유저가 아니라 **아직 요청조차 받지 않은** 유저였습니다.

**처리** — 상태 체계를 3값(`GRANTED / UNDETERMINED / DENIED`)으로 전환했습니다. 서버는 상태값을 화이트리스트로만 검증하고 있어 변경 없이 수용됐습니다. 이미 쌓인 행은 어느 쪽이었는지 **소급 재분류가 불가능**하므로 버리고, 대신 **상태 변경 이력 테이블**(직전 상태와 같으면 기록 생략, 플랫폼 구분)을 추가해 교정 이후의 실제 거부율과 "요청 → 허용" 전환율을 측정할 수 있게 했습니다.

이 건의 교훈은 9번과 반대 방향입니다 — 9번은 로그로 코드를 의심한 사례라면, 이 건은 **계측 자체를 의심**해야 했던 사례입니다. 지표가 이상하면 현상 이전에 수집 정의부터 검증합니다.

## 13. 자정을 넘기며 보상 지급 날짜가 밀리던 문제 ★

**상황** — 데일리 미션(글쓰기·프로필 조회 등)의 보상은 **행동이 커밋된 뒤에** 지급합니다. 글 저장이 롤백됐는데 베리만 나가는 일을 막으려고 `TransactionSynchronization`의 커밋 후 콜백에 지급을 걸어두었습니다. 여기까지는 의도대로였습니다.

**함정 — 날짜를 콜백 안에서 뽑고 있었습니다.**

```java
// 문제: 지급 시점(=커밋 이후)에 날짜를 계산
afterCommit(() -> grantSafely(userId, type, LocalDate.now(KST)));
```

멱등키가 `FEED_POST:{userId}:{날짜}` 형태라 **날짜가 키의 일부**입니다. 23:59:59에 쓴 글이 00:00:00에 커밋되면, 행동은 어제인데 키는 오늘 것으로 찍힙니다. 그 결과:

- **어제치 미션은 영구 미지급** — 어제 날짜 키로는 아무것도 발행되지 않았고, 어제 미션판을 다시 열 방법이 없습니다.
- **오늘 다시 해도 재지급 불가** — 오늘 키를 이미 점유했으므로 원장 유니크 `(type, ref_type, ref_id)`가 두 번째를 거부합니다.

이틀에 걸쳐 한 번만 지급되고, 백오피스 「미션 지급 현황」에서는 *어제 완료 인원 ≠ 어제 지급 건수*로만 흔적이 남습니다.

**두 번째 얼굴 — 트랜잭션이 둘일 때는 더 어긋납니다.** 프로필 조회 기록은 조회가 읽기 전용 트랜잭션이라 `REQUIRES_NEW`로 분리해 **먼저 커밋**됩니다. 즉 기록의 날짜(`view_date`)는 바깥 트랜잭션보다 이른 시각 기준입니다. 콜백에서 날짜를 다시 뽑으면 자정을 넘긴 순간 *오늘 조회 수 0*이 되어, 3명을 다 채우고도 지급을 놓칩니다. **같은 요청 안에서도 트랜잭션마다 시각 기준이 다르다**는 점을 놓친 것입니다.

**처리** — 날짜를 **행동 시점에 고정**해 콜백으로 캡처했습니다.

```java
LocalDate actedOn = LocalDate.now(KST);      // 행동 시점에 확정
afterCommit(() -> grantSafely(userId, type, actedOn));
```

이러면 어긋날 수 있는 창이 *커밋 지연 전체*에서 *`now()` 호출과 행 삽입 사이*로 줄어듭니다. 완전히 0은 아니지만 수십~수백 밀리초에서 마이크로초 단위가 됩니다.

**같이 나온 것** — 밸런스 게임 참여 판정도 `투표.created_at >= 오늘 00:00`이었는데 **상한이 없어서**, 자정 직전에 누른 어제 문항의 투표가 `00:00:00.x`로 찍히는 순간 *오늘 투표한 것*으로 잡혀 미션이 공짜로 완료됐습니다. 시각이 아니라 **문항의 노출 일자**로 판정하도록 바꿨습니다(문항은 하루 1개·날짜 유니크라 조인해도 1행).

## 14. 연속 출석이 60일에서 얼어붙는 구조 ★

**상황** — 연속 출석 도장판(7칸)과 3일차·7일차 보너스를 붙였습니다. "며칠째인가"는 저장된 값이 없어서, 오늘부터 하루씩 거슬러 올라가며 출석 로그가 **끊기는 지점**에서 멈추는 방식으로 셌습니다. 로그가 유일한 진실이라 값이 어긋날 수 없는 구조였습니다.

**함정 — 방어적으로 넣은 상한이 정답을 바꿔버립니다.** 몇 년 치가 쌓인 계정에서 전부 읽지 않도록 조회에 `LIMIT 60`을 걸어뒀는데, 루프가 멈추는 이유가 **두 가지인데 코드는 그걸 구분하지 않았습니다.**

```
① 빈 날을 만났다        → 진짜로 연속이 끝났다
② 받아온 60행을 다 썼다  → 그냥 자료가 떨어졌다
```

60일 연속 출석한 사람은 60행 안에 빈 날이 없어 ②로 멈추는데, 코드는 이를 ①로 읽고 **"연속 60일"**이라고 답합니다. 61일째도 60, 62일째도 60 — **연속 일수가 60에서 얼어붙습니다.** 도장판 칸은 `((연속-1) % 7) + 1`이라 4칸에 고정되고, 3일차·7일차에 다시 닿지 못해 **보너스가 영영 나가지 않습니다.** 예외도 로그도 없이 조용히 그렇게 됩니다.

**왜 놓치기 쉬운가** — 읽어야 할 행 수가 곧 **그 사람의 현재 연속 일수**입니다. "하루라도 빠지면 초기화"라는 규칙이 있으니 대부분은 몇 행이면 끝납니다. 하지만 **한 번도 안 끊긴 사람**은 멈출 지점 자체가 없어, 가장 우수한 유저에게서만 터집니다. 운영 데이터로는 최장 연속이 19일이라 당장은 안전했고, 기록 시작일을 기준으로 **60일 뒤에야** 처음 발생할 문제였습니다.

**처리** — 상한을 올리는 건 벽을 뒤로 미룰 뿐이라, 계산 방식 자체를 바꿨습니다(설계 근거는 engineering-decisions §13). 연속 일수와 마지막 출석일을 **상태로 저장**하고, 체크인 때 *마지막 출석일이 어제면 +1, 아니면 1로 리셋*합니다. 읽기가 1행으로 끝나 상한이라는 개념이 사라졌습니다.

## 15. 셔플을 넣었는데 매일 같은 사람이 나오던 문제

**상황** — 홈 추천·탐색 목록에서 "어제 본 사람이 오늘 또 나온다"는 문제가 반복됐습니다. 정렬에 날짜 시드 셔플을 넣어 두 번 고쳤는데, **두 번 다 처음엔 셔플이 돌지 않았습니다.**

**원인은 코드가 아니라 모수였습니다.** 캐러셀은 노출 칸이 10개인데 후보 풀이 6·11명이었습니다. **섞어도 결국 전원이 나옵니다.** 셔플 코드는 멀쩡했고 발동 조건이 안 맞았을 뿐입니다.

같은 함정이 테마 추천에도 있었습니다. 후보를 조건 부합도(등급)로 나눈 뒤 **같은 등급 안에서만** 섞는데, 등급 안 인원이 노출 수와 비슷하면 매일 같은 얼굴이 됩니다.

**그래서 코드 리뷰 대신 데이터를 셌습니다.**

```
등급 0 후보 수 (운영, 뷰어별)
  여성 뷰어가 보는 남성   214~215명
  남성 뷰어가 보는 여성    53~54명
  3명 미만인 뷰어  0명 / 6명 미만  0명 / 10명 미만  0명
```

노출이 3명이므로 캐러셀이 죽었던 조건에 해당하는 뷰어가 한 명도 없었습니다. **셔플이 도는 것은 코드가 아니라 이 숫자가 보증합니다.**

**부수적으로 더 큰 것을 발견했습니다.** 등급을 나누는 기준(4축 평균 유사도 70 이상)이 실제로는 아무것도 거르지 않고 있었습니다.

```
이성 쌍 11,610건의 유사도 분포
  90 이상  41%   80~89  55%   70~79  4%   70 미만  0.04%
```

**99.96%가 같은 등급**입니다. 축 값이 45~55에 몰려 있어(표준편차 9~11) 두 사람 차이가 평균 10~15고, `100 - 차이`를 4축 평균 내면 편차가 더 상쇄되기 때문입니다. 이 점수는 **한 사람을 설명하려고** 만든 값(프로필 게이지 4칸/3칸)인데 **두 사람을 변별하는 데** 그대로 쓴 것이 무리였습니다. 경계값만 올리면 증상은 가려지지만 변별력은 그대로라, 축을 교체하는 쪽으로 방향을 잡고 별건으로 분리했습니다.

**교훈** — "섞었다"는 구현 사실이지 동작 보증이 아닙니다. **모수 대비 노출 수**를 재기 전에는 셔플이 돈다고 말할 수 없습니다.

## 16. 백오피스 화면이 전부 비어 있던 것 — API는 정상이었다

**상황** — 관리자 대시보드·분석 화면의 수치가 전부 `-` 또는 `0`으로 나왔습니다. 활성 유저 0명, 탈퇴 0명, 성별 0/0. 시계열은 *"구간이 너무 넓어 시계열을 생성하지 않았습니다(day 버킷도 2000 포인트 초과)"* 를 띄웠습니다. 조회 구간은 **오늘 하루**였습니다.

**처음 진단이 틀렸습니다.** DB에는 데이터가 멀쩡했으므로 조회 조건이 실제 값과 안 맞는다고 봤습니다(`use_yn`을 숫자로 비교, `status`를 소문자로 비교 등). 그렇게 보고까지 했습니다.

**응답을 직접 열어보고 뒤집혔습니다.** API는 정상이었습니다. 시계열도 `bucket: "hour"`로 12포인트를 제대로 반환했고, 성별·연령·지역 분포까지 DB 실측과 완전히 일치했습니다. 브라우저 Network 탭의 요청 URL도 정상이었습니다. **요청도 맞고 응답도 맞는데 화면만 비어 있었습니다.**

**원인** — 모든 응답이 `{ success, message, data: {...} }` 봉투로 감싸여 나가는데, 화면이 `res.data.***`가 아니라 `res.***`로 읽고 있었습니다. 전부 `undefined`가 되고, 그것을 어디선 `?? 0`으로 어디선 `?? '-'`로 처리하면서 **한 화면에 두 종류 증상이 섞여** 보인 것입니다.

시계열 메시지도 서버가 보낸 게 아니었습니다. `series`가 `null`일 때 클라이언트가 띄우도록 규정한 문구인데, `undefined`를 `null`로 오인해 출력한 것입니다. **기간을 30분으로 좁혀도 같은 메시지가 나온 것**이 결정적 단서였습니다 — 기간과 무관한 문제라는 뜻이니까요.

**교훈 두 가지** — 첫째, **`-`와 `0`은 다른 신호**입니다. `-`는 값이 안 온 것이고 `0`은 계산 결과가 0인 것이라, 섞여 있으면 원인이 하나가 아니라고 봐야 합니다. 둘째, DB에 데이터가 있는데 화면이 비면 **API 응답을 직접 열어보는 것이 첫 단계**입니다. 저는 그걸 건너뛰고 쿼리부터 의심해 한 번 헛짚었습니다.

## 17. 운영 테이블이 통째로 사라진 사고 — DDL은 롤백되지 않는다 ★

**상황** — 신규 기능(밸런스 게임)의 문항 50건을 운영 DB에 넣고 검증까지 마쳤습니다. **약 1시간 뒤 확인해보니 테이블 자체가 없었습니다.** `balance_question`·`balance_vote` 두 개만 사라졌고, 같은 배포로 생성된 나머지 테이블 3개와 핵심 테이블은 멀쩡했습니다.

**추적** — `ddl-auto: update`는 테이블을 지우지 않습니다. 그래서 사람의 작업을 의심하고 백오피스 감사 로그를 봤습니다.

```
occurred_at   18:33:41
category      WRITE
target_type   balance_question
summary       밸런스 문항 묶음 등록 3건 (2026-08-21 ~ 2026-08-23)
path          GET /api/test
```

해당 시간대의 유일한 밸런스 관련 작업이었습니다.

**결정적 단서는 "성공했다"는 것이었습니다.** 시작일 `2026-08-21`은 이미 문항이 있던 날짜입니다. `publish_date`에 UNIQUE가 걸려 있으므로 **정상이라면 3건 모두 중복 에러로 실패했어야 합니다.** 그런데 `result = OK`로 기록됐습니다. 즉 **등록 직전에 테이블이 비워졌거나 삭제됐다**는 뜻입니다.

**그리고 DDL은 트랜잭션 롤백 대상이 아닙니다.** MySQL에서 `DROP`/`CREATE`는 암묵적 커밋을 일으킵니다. "초기화 후 등록" 코드가 `DROP` → `CREATE` → `INSERT` 순으로 돌다 INSERT 단계에서 실패하면, **INSERT만 롤백되고 DROP은 남습니다.** 관측된 상태(테이블 없음 + 등록 성공 기록)와 정확히 일치합니다.

**처리** — 원래 DDL 그대로 테이블을 재생성하고(컬럼·유니크·인덱스 동일하게 맞춰 `ddl-auto`가 나중에 변경하지 않도록) 문항 50건을 재삽입했습니다. 앱 출시 전이라 실사용자 투표가 0건이어서 유실은 없었습니다.

**남긴 조치와 교훈**

- **운영 DB에 닿는 코드에서 `DROP`·`TRUNCATE`·조건 없는 `DELETE`를 제거**하도록 요청했습니다. 개발 중 "테이블 초기화 후 테스트" 용도로 넣은 코드가 그대로 운영에 도달한 것으로 보입니다.
- **쓰기 동작이 `GET`으로 열려 있었습니다.** 주소창 입력이나 브라우저의 사전 로드만으로도 실행될 수 있습니다.
- 저희가 전달한 요청서에는 `DROP` 계열이 한 줄도 없었지만, *"이 테이블이 운영 DB에 아직 없습니다"* + DDL 제공이라는 조합이 **"없으니 만들고 시작하자"**로 읽힐 여지가 있었습니다. 이후 문서에 **현재 테이블이 존재하며 데이터가 들어 있다**는 상태를 명시하도록 고쳤습니다.
- 출시 후 같은 일이 나면 **유저 투표 기록이 복구 불가**입니다. 위험도는 시점에 따라 달라진다는 점을 문서에 남겼습니다.

---

공통적으로: **증상을 코드로 추측하기 전에 로그·DB·실제 API 응답으로 원인을 먼저 정량 확인**하는 것을 우선했습니다. 9번처럼 재현이 확률적인 경우에는 **실패 조건을 강제로 만들어 수정 전/후를 대조**했습니다.

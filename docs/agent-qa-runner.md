# 앱 QA를 에이전트에게 — 스크립트 E2E 대신 「화면을 보며 점검 목록을 도는」 방식

> 2026-10-15. 「서비스 개발을 AI 에이전트로 자동화하자」는 요구에서 프론트엔드 몫을 정리한 기록이다.
> 서버 쪽 파이프라인(이슈 → 구현 에이전트 → 검증 에이전트 → 사람 승인)은 be 브랜치
> [`docs/agent/agent-pipeline.md`](https://github.com/eomheeseung/mildo_eomheeseung/blob/be/docs/agent/agent-pipeline.md)에 있다.
> 이 문서는 그 흐름에서 **앱을 어떻게 검증할 것인가**를 다룬다.
> 결론부터 말하면 이렇다.
> - 스크립트형 E2E는 쓰지 않는다.
> - 에이전트가 실기기를 adb로 조작하며 점검 목록을 돈다.
> - 사람은 승인 한 곳에만 남긴다.

## 1. 왜 Maestro·Detox를 쓰지 않나

예전에 Maestro를 시도했지만 효과가 없었다. 이 앱의 조건에서는 정해진 순서로 누르는 스크립트가 버티지 못한다.

- **화면이 상황마다 다르다.** 앱을 열 때마다 뜨는 것이 상태와 날짜에 따라 달라진다.
  - 뜰 수 있는 것: 스플래시, OTA 업데이트 확인창, 권한 팝업, 출석·이벤트 모달, 조회 알림 모달
  - 스크립트는 한 단계만 어긋나도 멈춘다.
- **실제 버그는 「기기 상태」에서 난다.** 예를 들어 4번 사례는 이런 순서에서 나는 버그다.
  - 알림 탭으로 앱을 연다.
  - 백그라운드에 둔다.
  - OS가 프로세스를 정리한다.
  - 다음 알림을 탭한다.

  이런 시나리오는 스크립트로 만들기 어렵고, 만들어도 깨지기 쉽다.
- **배포가 잦다.** JS 변경은 OTA로 주 단위 여러 번 나간다. 문구와 레이아웃이 바뀔 때마다 셀렉터를 고치면 유지 비용이 이득보다 크다.

## 2. 대신 쓰는 방식 — adb + uiautomator 「글자로 찾아 탭」

추가 설치 없이 adb만으로 돈다.

| 도구 | 쓰는 곳 |
|---|---|
| `uiautomator dump` | 화면의 텍스트와 좌표를 XML로 받아 **글자로 요소를 찾아 탭**한다. 좌표를 박지 않아 레이아웃이 조금 바뀌어도 안 깨진다. 한글도 인식한다 |
| `screencap` | 매 단계 캡처한다. 예상 못 한 팝업은 **에이전트가 캡처를 보고 판단**해 닫고 진행한다(스크립트가 멈추는 지점) |
| `am kill` / `am start` / 딥링크 | 콜드·웜·「프로세스 정리 후」 진입을 명령 한 줄로 재현한다 |
| `run-as` + AsyncStorage(sqlite) | 기다려야 하는 상태를 즉시 만든다. 액세스 토큰 서명을 훼손해 만료를 재현하거나, 스누즈 시각을 하루 전으로 되돌린다 |
| dev 푸시 API(서버) | 알림 종류별로 테스트 계정에 실제 FCM을 보내고, 탭했을 때 어느 화면으로 가는지 확인한다 |
| 테스트 계정 초기화 API(서버) | 점검이 반복돼도 매번 같은 출발 상태를 만든다 |
| curl | 화면 대신 API 응답이 명세와 같은지 직접 대조한다. 화면보다 빠르고 원인 귀속이 정확하다 |

이 방식으로 홈 개편 때 체크리스트 47항목을 자동으로 통과시켰다. 함께 익힌 함정은 이렇다.

- **Git Bash의 경로 변환**: `/sdcard/...` 경로를 Git Bash가 Windows 경로로 바꾼다. 그러면 **예전 dump 파일을 받아 엉뚱한 화면을 분석**한다. `MSYS_NO_PATHCONV=1`이 필수다.
- **하단 탭바 좌표 탭**: 탭바가 떠 있는 좌표를 탭하면 탭이 바뀐다. 「카드 탭이 안 먹는다」는 오탐이 나서 러너에 탭바 가드를 넣었다.
- **TextInput 값 확인**: RN `TextInput`은 uiautomator에 빈 텍스트로 잡힌다. 입력값은 캡처로 확인한다.
- **화면 캡처 저장**: PowerShell로 리다이렉트하면 바이너리가 깨진다. `adb exec-out screencap -p > x.png`로 받는다.
- **내 테스트부터 의심하기**: 코드 버그라고 말하기 전에 **내 테스트부터 의심**한다. 이렇게 오진한 적이 있다.
  - 셸이 URL의 `&`를 잘라 「파라미터가 안 먹는다」고 했다.
  - 로딩 전에 캡처해 「탭이 안 열린다」고 했다.
  - 다른 요청의 에러 로그를 엉뚱한 API 탓으로 돌렸다.

## 3. 4단 구조

```
1단 정적 검사 (자동, 몇 분)    tsc · 출시 설정 검사 · 시크릿 스캔
        │
2단 API 점검 (자동)            변경된 API 응답을 명세와 curl 대조
        │
3단 실기기 점검 (에이전트)     점검 목록대로 실기기 조작 → 항목별 통과/실패 + 캡처 + 실패 원인
        │
4단 사람                       화면 느낌·문구 확인, 출시 승인, 스토어·실결제
```

- **1단**의 출시 설정 검사는 예전 사고(로컬 서버 주소가 운영 앱에 박힘, [troubleshooting #1](./troubleshooting.md))에서 나온 빌드 가드다.
- **3단 점검 목록**은 저장소에 고정한다. 에이전트는 매번 조금씩 다르게 움직이니 「지난번과 같은 걸 다 봤다」는 보장을 목록이 대신한다.
  - 기본 영역: 로그인과 자동 로그인, 홈 탭, 알림 종류별 이동(콜드·웜·프로세스 정리 후), 뒤로가기, 대화방 송수신, 재화 결제 진입, 로그아웃
  - **버그를 고치면 그 재현 시나리오를 목록에 남긴다.**
- **4단**에서 사람이 보는 것은 PR에 붙은 캡처다. 승인 시간을 1분 안으로 줄이는 것이 목표다.

## 4. 실제로 잡은 사례 — 옛 알림이 다시 열리는 버그

에이전트 실기기 점검이 왜 필요한지 보여 주는 사례다.

- **증상**: 알림 A로 앱을 연 뒤 시간이 지나면, 아이콘으로 열어도 알림 B를 눌러도 **A의 대화방이 열렸다.**
- **재현 조건**: 처음 알림 탭으로 시작한 작업(task)이 최근 앱 목록에 남아 있어야 한다. 그 상태에서 **프로세스만** OS에 정리돼야 한다.
  - 백그라운드 복귀(프로세스 살아 있음)에서는 정상이다.
  - 강제 종료나 스와이프로 앱을 지우면 작업이 사라지니 정상이다.
  - 메모리가 적은 보급형 기기에서 일상적으로 생길 수 있는 조건이다.
  - `am kill`로 프로세스만 죽여 그 상태를 그대로 만들었다.
- **원인**: Activity가 `singleTask`다. 안드로이드는 남은 작업을 되살릴 때 **그 작업을 처음 연 인텐트(A)** 로 Activity를 다시 만든다.
  - 알림 라이브러리는 `onCreate`에서 그 인텐트를 읽어 「마지막 알림 응답」으로 A를 다시 돌려준다.
  - 앱에는 「이 알림은 이미 처리했다」는 기록이 프로세스 경계를 넘어 남지 않았다.
- **해결(JS, OTA 가능)**: 알림마다 고유한 메시지 id를 저장소에 최근 30개 기록하고, 이미 처리한 id는 건너뛴다.
  - 콜드 스타트 경로와 실행 중 리스너, 두 곳 모두 같은 함수를 거친다.
  - 실기기에서 네 시나리오를 확인했다.
    - 아이콘으로 열기: 홈
    - 새 작업 상태에서 콜드 탭: 해당 방
    - 웜 탭: 해당 방
    - 옛 작업 상태에서 탭: 옛 방이 아니라 홈
- **남은 것**: 옛 작업 상태에서 새로 누른 B는 홈에 머문다.
  - B는 `onNewIntent`로 따로 오는데, 그 순간 JS가 아직 떠 있지 않아 흘려진다(코드 독해 기반 추정, 결과는 실측).
  - 네이티브 `onNewIntent` 처리가 필요해서 다음 스토어 빌드로 넘겼다. 「엉뚱한 방」이 「홈에 머묾」으로 바뀌어 오해를 부르는 상태는 없앴다.
- **남긴 것**: 이 시나리오를 3단 점검 목록의 고정 항목으로 넣었다.

## 5. 사람 vs 에이전트 — 속도 트레이드오프

「이럴 바엔 사람이 하는 게 빠르지 않나?」는 맞는 질문이다.

| 기준 | 사람 | 에이전트 |
|---|---|---|
| 한 동작 시간 | 2~3초 | 10~30초(캡처 → 판단 → 탭) |
| 짧은 확인(「이 화면 맞아?」) | **빠름** | 느림 |
| 그동안 사람 손 | 묶임 | **비어 있음** |
| 만들기 어려운 상태(프로세스 정리, 토큰 만료, 특정 방 번호 푸시) | 수십 분 또는 불가 | **명령 한 줄** |
| 실패했을 때 | 「이상해요」에서 끝나고 재현부터 다시 | **로그·코드까지 보고 원인과 함께 보고** |
| 40항목을 배포마다 반복 | 지쳐서 빠뜨림 | 목록대로 |

그래서 역할을 나눴다.

- **사람**: 화면 느낌, 문구, 짧은 확인, 출시 승인
- **에이전트**: 상태를 만들어야 하는 재현, 알림 종류별 이동, 출시 전 반복 점검, 버그 재현과 원인 분석

자동화 장치를 크게 키우지는 않는다. 점검 목록 문서 하나와 이미 써 본 도구면 충분하다. 그 이상은 말 그대로 속도 손해가 커진다.

## 6. 8단계 출시 파이프라인과 우리 상황 판정

| 단계 | 내용 | 판정 |
|---|---|---|
| ① 명세 | 이슈에 화면·동작·예외, 서버 완료 시 실제 응답 예시 | 바로 가능 |
| ② 구현 | 에이전트가 이슈를 읽고 PR | 바로 가능 |
| ③ CI 검사 | tsc · 출시 설정 · 시크릿 | **tsc 잔존 오류 정리 후**(7절) |
| ④ 실기기 점검 | 3단. 폰이 꽂힌 기계에서만 돌아서 클라우드 CI가 아닌 **self-hosted 러너** | 러너·목록 정비 중 |
| ⑤ 테스트 빌드 | 네이티브 변경이 있을 때만 | 필요 시 |
| ⑥ 사람 승인 | PR의 캡처를 보고 승인 = 출시 버튼 | 사람 |
| ⑦ OTA 발행 | 승인 후 자동 | 마지막에 붙임 |
| ⑧ 감시 | 크래시 수집 → 이상 시 알림, 이전 OTA로 롤백 | **가장 먼저 필요**(지금 없음) |

정한 원칙은 이렇다.

- **자동 출시에서 빼는 것**: 결제, 알림 라우팅, 네이티브 변경은 사람이 실기기로 확인한 뒤에만 낸다.
- **`expo prebuild` 금지**: 어떤 자동화에도 넣지 않는다. iOS는 네이티브 폴더를 손으로 관리해서, 한 번 돌면 광고 귀속 설정·권한 문구·카카오 설정이 사라진다.
- **OTA 채널 유지**: 채널은 하나다. 채널을 새로 파면 기존 사용자가 업데이트를 못 받는다.
- **iOS 머지 후 grep 검사**: v2 → iOS 브랜치 머지 뒤에는 iOS 전용 경로를 grep으로 확인한다. 확인할 것은 New Architecture 설정, 결제 분기, 스플래시 플러그인이다. 「충돌 안 났다 ≠ 안전」이다.

## 7. tsc 잔존 오류 정리 계획

CI에 타입 검사를 걸면 지금은 매번 빨간불이다. 잔존 오류는 127건이고, 성격이 몇 묶음으로 갈린다.

- **API 클라이언트 공통 응답 타입 불일치(20여 건)**: 에러 응답 생성기가 돌려주는 모양과 각 메서드의 선언 반환 타입이 어긋난다. 같은 패턴이라 공통 타입 하나로 한 번에 정리된다.
- **중복 메서드 정의**: 어느 쪽이 실제로 쓰이는지 실기기에서 확인한 뒤 하나만 남긴다. 동작이 바뀔 수 있는 유일한 묶음이다.
- **라우트 문자열 타입, 모듈 선언 누락**: 기계적으로 정리한다.

정리 뒤에는 「새 오류 0건」을 CI 통과 조건으로 건다. 에이전트가 낸 틀린 코드를 실행 전에 걸러내는 검증 장치로 쓰기 위해서다(서버 문서 1절과 같은 판단).

## 8. 플랫폼별 가능·준비·불가

**Android**

- 바로 가능
  - 구현, tsc
  - API 대조
  - 실기기 점검 목록
  - 로컬 AAB 빌드와 서명 확인
  - OTA 발행 명령(승인 후)
- 준비하면 가능
  - CI 검사: tsc 정리
  - 크래시 수집: SDK 추가와 스토어 빌드 1회
  - OTA 자동 발행: 워크플로와 승인 단계
  - 알림 전 종류 자동 점검: 서버 dev 푸시와 초기화 API(완료)
  - Play 업로드 자동화: 서비스 계정
- 불가(사람)
  - 심사 대응
  - 실결제 검증
  - 디자인 판단
  - 출시 결정

**iOS**

- Mac 러너에서 가능
  - 로컬 빌드, 시뮬레이터 실행·캡처·딥링크
  - TestFlight 업로드: API 키 + 클라우드 관리 배포 서명
  - OTA 발행
- 준비하면 가능
  - 실기기와 시뮬레이터 탭 조작: WebDriverAgent
  - 실기기 원격 푸시 라우팅 확인
- 사람
  - 샌드박스 결제: 시스템 인증 시트가 뜬다.
  - ATT 팝업: 최초 1회만 뜬다.
  - 심사

iOS가 사람 몫이 큰 이유는 시뮬레이터로 볼 수 없는 것이 많아서다.

- 원격 푸시는 로컬 알림으로 재현되지 않는다(페이로드 직렬화 경로가 다르다).
- 모달 겹침 프리징은 iOS에서만 난다([troubleshooting #23](./troubleshooting.md)).

**한 대에서 두 플랫폼을 돌릴 때의 조건**

- **체크아웃 분리**: Android용과 iOS용을 `git worktree` 두 개로 나눈다. 같은 설정 파일이라도 New Architecture 값이 두 플랫폼에서 반대이고, 네이티브 의존성이 그 값으로 생성된다.
- **Metro 포트 분리**: 두 플랫폼의 번들러가 같은 포트를 쓰지 않게 나눈다.
- **실기기 순차 실행**: Android 실기기 점검과 iOS 실기기 점검을 동시에 돌리지 않는다.
- **툴체인 고정**: 점검용과 출시용 Xcode가 다르면 「확인한 바이너리 ≠ 출시하는 바이너리」가 된다. 실제로 최신 Xcode에서만 RN 서드파티(fmt)의 `consteval` 컴파일 오류가 났다. 대응은 이렇게 했다.
  - 서드파티를 패치하지 않았다.
  - 출시 실적이 있는 버전으로 툴체인을 고정했다.
  - 패치는 네이티브 변경이라 OTA로 못 나가고, 버전 고정은 되돌릴 수 있다.

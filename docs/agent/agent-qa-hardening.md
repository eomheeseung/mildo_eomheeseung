## 1. 버그 — 「이미 그 상태」는 실패가 아니다

이미 숨긴 회원의 프로필을 다른 경로(저장 목록·피드·알림)로 열면 「괜찮아요(숨기기)」 버튼이 그대로 보였다. 누르면 서버는
`409 / H002 이미 숨긴 사용자입니다` 를 돌려주고, 앱은 그 메시지를 토스트로 띄운 채 화면에 머물렀다. 다시 눌러도 같다.
운영에서 하루 1~4건씩 쌓이던 오류였다.

이미 숨긴 상태가 되는 길은 둘이었다. 저장(북마크)과 숨김이 서로를 지우지 않고, 홈 카드의 「싫어요」가 같은 숨김 테이블에 조용히 기록한다.

고치는 방향은 **서버를 바꾸지 않는 것**으로 정했다. 409 → 200 으로 바꾸면 이미 배포된 앱 버전들이 받는 응답 의미가 달라진다.
대신 앱이 `H002` 를 「사용자가 원한 상태가 이미 되어 있다」로 읽고 성공과 똑같이 처리한다(토스트 + 이전 화면). 같은 화면의
북마크 버튼이 `B002(이미 북마크)` 를 이미 이렇게 처리하고 있어서, 새 규칙이 아니라 **기존 규칙을 숨김에도 맞춘 것**이다.
클라이언트 쪽에서 요청을 멱등하게 다루는 셈이다 — 같은 의도를 두 번 보내도 결과 화면은 같다.

```ts
const res = await apiClient.hideUser(userId);
// H002 = 이미 숨김 → 사용자가 원한 상태가 이미 됨. 북마크의 B002 처리와 같다
if (res.success || res.code === 'H002') showToast(`${name}님이 숨겨졌어요!`, 2000, () => router.back(), 'hide');
```

## 3. 멈춘 곳과 고친 것

### ① 횟수 한도 — 다 보고도 판정을 못 썼다

검증 에이전트 한 회차는 도구 호출 60번으로 제한한다. 첫 AOS QA 는 핵심(이미 숨긴 상대 → 성공 토스트 → 뒤로, DB 숨김 행 1건)을
다 확인한 뒤, 회귀 확인 대상을 찾다가 한도에 걸렸다. 같은 호출을 두 번씩 보낸 것도 여러 번이었다.

문제는 구조에 있었다. 스크립트는 에이전트 출력의 **마지막 「## 판정」 블록만** 이슈 댓글로 올리고 라벨을 바꾼다. 한도에 걸리면
그 블록이 없으니, 실제로는 통과한 점검이 「막힘」으로 기록됐다.

지시문에 「핵심 먼저, 판정 먼저」를 쓰는 것만으로는 보장이 안 된다. 그래서 스크립트가 보장하게 했다 — 한도로 끊기면 **같은 대화를
6턴만 이어서**, 더 조작하지 말고 지금까지 확인한 것으로 판정 블록만 쓰게 한다. 대화를 이어 가니 읽은 것·본 것이 그대로 남아 있다.

```bash
if [ "$RC" -ne 0 ] && grep -q "Reached max turns" "$OUT"; then
  case "$ROLE" in qa|qa-fe|qa-ios)          # 개발 역할은 하지 않는다 — 반쪽 작업을 「완료」로 쓸 수 있어서
    MAX_TURNS=6 run_claude "횟수 한도에 걸렸다. 도구를 쓰지 말고, 이 대화에서 실제로 확인한 것만으로 「## 판정:」을 써라.
본 것처럼 쓰지 말고 못 본 항목은 「못 봄 — 횟수 한도」로." resume
    grep -qE '^## (판정|결과):' "$OUT" || RC=1 ;;   # 그래도 없으면 예전처럼 막힘
  esac
fi
```

지시문에는 운영 규칙을 더했다. 핵심을 먼저 끝내고, 회귀는 남은 횟수 안에서, 대상 찾기가 두 번 실패하면 회귀를 그만두고 「회귀 못 봄 — 이유」로
적는다. 한도를 늘리는 건 하지 않았다. 헛도는 시간을 늘릴 뿐이다.

### ② 시뮬레이터 자판 — 키를 누르는 방식은 자판 배열을 탄다

iOS 시뮬레이터 앱은 한국어 기기로 맞춰 둔다. 입력 도구(`idb ui text`)는 글자를 **하드웨어 키 코드**로 바꿔 누르는데, 기기 자판이
두벌식이라 `dev@…` 가 `ㅇㄷㅍ@…` 로 들어갔다. 허용되지 않은 도메인이 떠서 로그인조차 못 했다. 검증 에이전트는 규칙대로
「확인 못 했으니 막힘」으로 판정하고, 필요한 도구 세 가지를 제안했다.

자판을 영문으로 고정하면 이번엔 한글을 못 넣는다. 그런데 AI 대화 같은 화면은 한글로 시험해야 의미가 있다. 그래서 글자에 따라 길을 나눴다.

- 숫자·기호만이면 키 입력 — 인증번호 칸처럼 키 이벤트가 필요한 곳. 숫자는 두벌식에서도 그대로다.
- 글자가 섞이면 **시뮬레이터 클립보드에 넣고 Cmd+V** — 자판 배열과 무관하게 영문·한글이 그대로 들어간다.

```bash
if printf '%s' "$TXT" | LC_ALL=C grep -q '^[0-9[:punct:] ]*$'; then
  idb ui text --udid "$U" "$TXT"                                   # 키 입력
else
  printf '%s' "$TXT" | xcrun simctl pbcopy "$U" && idb ui key --udid "$U" --command 25   # Cmd+V
fi
```

실제 앱 로그인 칸에서 영문 이메일·한글 문장·숫자를 넣고, 화면의 접근성 트리에서 값을 다시 읽어 확인했다.

### ③ 머지된 브랜치 — AOS 와 iOS 는 다른 열차다

이 앱은 AOS 출시 브랜치(v2)와 iOS 출시 브랜치(v2-ios)를 따로 운영한다. iOS 에만 있는 코드가 있어서다. iOS 검증은
「v2-ios + 이 이슈의 브랜치」를 검증 기계 안에서만 합쳐서 띄우는데, AOS 통과 직후 사람이 v2 PR 을 머지했고 뒷정리가 브랜치를 지웠다.
준비 단계가 브랜치를 못 받아 멈췄다.

흐름에도 같은 가정이 박혀 있었다. PM 지시문의 「PR 이 다 머지된 이슈에는 QA 를 내지 않는다」가 v2 머지만 보고도 적용될 수 있었다.
하지만 v2 에 들어갔다고 iOS 에서 확인된 건 아니다. 두 가지를 고쳤다.

- 준비 도구: 브랜치가 없으면 GitHub 가 PR 마다 보존하는 `pull/N/head` 로 원본 커밋을 받아 합친다.
- PM 규칙: 머지 뒤 금지는 「AOS·BE 검증 다시 돌리기」에만. iOS 출시 PR 이 머지되기 전이면 iOS 검증 카드는 낸다.

### ④ 같은 코드를 두 번 — 커밋이 아니라 트리로 비교한다

iOS 담당 에이전트가 v2 를 v2-ios 에 합친 정식 PR 을 만들자 iOS 검증이 자동으로 처음부터 돌았다. 20분 전 ③을 고친 다음 회차에서 통과한 것과
**같은 코드**인데도. 검증 에이전트는 매 회차 새 대화라 앞 회차를 모르고, 지시문은 회귀까지 다 하라고 한다. 결국 ①과 같은 한도에 걸렸다.

같은지 판단은 추측으로 하면 안 된다. 「함께 들어간 커밋이 하나뿐」이라는 설명도 근거가 약하다. 두 코드는 만들어진 경로가 다르다 —
하나는 「v2-ios + 이슈 커밋」을 검증 기계가 합친 것, 하나는 「v2-ios + v2 머지 커밋」을 iOS 담당이 합친 것이라 **커밋 해시는 다르다**.
그래서 내용 주소인 **git 트리 해시**를 쓴다. 파일 내용이 한 글자라도 다르면 다르고, 같으면 경로와 무관하게 같다.

- iOS 를 띄울 때마다 `HEAD^{tree}` 를 남긴다.
- iOS 를 **실제로 보고** 통과하면 그 트리를 이슈별로 기록한다(재사용 통과는 다시 기록하지 않는다).
- iOS 출시 PR 의 트리가 기록과 같으면 에이전트를 부르지 않고 통과로 처리한다. 앱은 그 PR 코드로 띄워 첫 화면까지 뜨는 것은 확인한다.

### ⑤ 머지했는데 「막힘」 — 정리 주기

PM 이 「사람 판단 필요」를 쓴 지 48초 뒤에 사람이 머지했다. 이슈를 닫고 라벨을 정리하는 뒷정리는 10분 주기라, 그 사이 카드에는
「막힘」이 남아 있었다. 사람 입장에서는 「머지했는데 왜 막혔다고 하느냐」가 된다. 주기를 2분으로 줄였다. launchd 는 이전 실행이
끝나기 전에 다음을 띄우지 않으니 겹칠 걱정은 없다.

### ⑥ DevTools 창이 앞으로 — 원인은 화면 아래 경고 줄

검증 중 맥 화면에 React Native DevTools 창이 계속 앞으로 떴다. Metro 를 켜는 것만으로는 이 창이 뜨지 않는다. 열리는 길을 코드에서
좁혔다 — Metro 터미널의 `j` 키(검증용 Metro 는 입력을 받지 않으니 제외), 앱 개발자 메뉴, 앱이 직접 부르는 디버거 열기. Metro 로그에서
**북마크 해제 요청 바로 뒤**에 앱의 디버거 열기 요청 흔적이 있었고, 검증 캡처 하단에는 개발 모드 경고 줄
「Open debugger to view warnings.」가 있었다. 탭 바 근처를 누르다 이 줄이 눌린 것이다.

앱 코드에서 경고를 끄는 건 개발 빌드 동작을 바꾸는 일이라 하지 않았다. 대신 검증 도구가 iOS 를 켤 때·끌 때·누를 때마다 디버거 탭을
찾아 닫고 시뮬레이터를 앞으로 올린다. 지시문에는 「경고 줄은 누르지 말고, 가리면 ✕ 로 닫는다」를 넣었다.

## 4. PM 이 맞게 판단한 부분

①에서 AOS QA 가 「막힘」으로 끝나자 PM 에이전트가 1차로 받았다. 고칠 거리가 있어서가 아니라 **횟수 한도**라는 것을 정확히 짚었고,
처음부터 다시 돌리는 대신 「핵심 시나리오 다섯 단계만, 회귀는 FE 가 이미 봤으니 빼고, 단계를 늘리지 말 것」이라는 작업 카드 한 장을
검증 담당에게 바로 보냈다. 그 회차는 5분 만에 통과했다.

이 「작업 카드」는 이날 아침 도입한 방식이다. 예전에는 이슈의 단계 라벨 하나가 상태의 전부라 재작업도 통째로 단계를 되돌렸다.
카드는 **누가·무엇만** 하는지를 따로 들고, 같은 이슈에 여러 담당이 동시에 붙을 수 있다. 실제 이슈로 한 바퀴 돈 것은 이번이 처음이었다.

검증 에이전트도 규칙을 지켰다. ②에서 로그인을 못 하자 화면을 일부라도 본 것을 근거로 통과를 주지 않고 「확인 못 함」으로 막혔다.
이날 아침 바꾼 판정 규칙(핵심 미확인 = 막힘)이 그대로 작동한 것이다. 시뮬레이터에 허용되지 않은 계정이 로그인돼 있는 것도 알아채고
로그아웃한 뒤 시험 계정으로 다시 들어가려 했다.

## 5. 시험 데이터는 앱으로 되돌린다

검증은 스테이징 DB 에 숨김·북마크 행을 만든다. 끝나면 **앱 화면에서** 「숨김 해제」와 북마크 해제를 눌러 0건으로 되돌리고, 읽기 전용 조회로
확인한다. 앱의 정상 API 를 타니 DB 를 직접 고치지 않는다. 에이전트가 DB 를 직접 바꿔야 할 때는 대상 행을 먼저 조회해 보여 주고
사람이 승인해야 실행되는 별도 경로를 탄다.

## 6. 남은 것

- **대화 이어 쓰기.** 검증 에이전트는 회차마다 새 대화라 ①·④처럼 앞 회차를 모른다. 대화를 하나로 계속 쓰면 다른 이슈의 맥락이 섞이고
  길어지면 앞부분이 흐려진다. 그래서 **이슈 × 역할** 단위로 대화를 이어 쓰고, 이슈가 닫히거나 기준 브랜치가 바뀌면 새로 여는 쪽을
  다음 단계로 잡았다. 트리 비교와 판정 보장을 먼저 한 바퀴 돌려 본 뒤에 바꾼다.
- **사진이 안 뜨는 카드.** 같은 날 스테이징 홈에서 일부 시험 계정 사진이 빈칸으로 보였다. 사진 주소가 없는 파일을 가리켰고, 홈의 그 줄은
  주소가 **비어 있을 때만** 기본 이미지를 쓰고 불러오기 실패는 빈칸으로 둔다. 데이터는 정리했고, 불러오기 실패에도 기본 이미지로
  바꾸는 앱 수정은 다음 작업으로 남아 있다.

돌아보면 이날 에이전트가 틀린 판단을 한 곳은 거의 없다. 멈춘 곳은 전부 **에이전트가 서 있는 바닥** — 자판 배열, 지워진 브랜치,
마지막 블록만 읽는 파서, 10분짜리 주기 — 이었다. 검증 단계를 믿을 수 있게 만드는 건 더 긴 지시문이 아니라, 지시문이 지켜지지 않아도
결과가 맞게 나오는 결정적인 장치다.

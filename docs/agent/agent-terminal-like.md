# 「터미널 클로드처럼」 — 에이전트에게 기억·시간·판단을 돌려준 개편

2026-10-27 ~ 11-05. 파이프라인이 한 바퀴씩 돌기 시작하자 사람(대표)의 요구가 바뀌었다. 「PC 터미널에서 쓰는 클로드랑 거의 똑같이
쓰고 싶다」. 그때까지 에이전트는 **일감마다 새로 태어나서, 횟수로 잘리고, 스크립트가 정한 다음 단계로 떠밀리는** 일꾼이었다.
이 문서는 그 셋을 바꾼 기록이다. 원칙은 앞 문서([`agent-qa-hardening.md`](./agent-qa-hardening.md))의 「보장은 스크립트가 한다」를
뒤집은 게 아니라 경계를 그은 것이다 — **스크립트는 객관적 조건만 보장하고, 일의 종류를 보는 판단은 에이전트에게 둔다.**

파이프라인 구조는 [`agent-pipeline.md`](./agent-pipeline.md), 사무실 화면은 [`agent-office.md`](./agent-office.md) 에 있다.

## 1. 무엇이 「터미널 클로드」와 달랐나

| | 터미널에서 쓰는 클로드 | 개편 전 에이전트 |
|---|---|---|
| 기억 | 대화가 이어진다. 「이거 기억해」가 바로 먹는다 | 일감마다 새 대화. 규칙을 바꾸려면 지시문 파일을 고쳐 git 커밋·푸시 |
| 한도 | 사람이 보다가 멈춘다 | 턴 60 — 앱 QA 가 정답 직전에 잘렸다 |
| 판단 | 일을 보고 도구를 고른다 | 「FE 완료면 무조건 앱 QA」 — HTML 만 고친 일에 에뮬레이터를 켰다 |
| 막힐 때 | 사람에게 물어보되, 할 수 있는 건 한다 | 스테이징 DB 한 줄을 바꾸는 데도 사람 승인을 기다렸다 |

## 2. 에이전트 집 — 대화를 이어 쓰고, 길어지면 스스로 기억을 정리한다

역할 지시문과 기억을 git 저장소 밖, 맥의 **에이전트 집** 폴더로 옮겼다. 지시문·기억을 고치는 데 커밋이 필요 없고, 바꿀 때마다
이전 판이 기록 폴더에 남는다.

- **자리마다 대화 하나를 이어 쓴다.** 역할(BE·BE QA·FE·앱 QA·PM…)마다 대화를 하나 두고, 일감이 바뀌어도 `--resume` 으로 이어 간다.
  QA·PM 이 앞 일감에서 무엇을 봤는지 기억한 채 다음 일을 시작하게 되었다 — 바꾼 다음 날 QA 한 건이 2분 반 만에 통과했다.
- **길어지면 스스로 정리한다.** 대화 기록이 40MB 를 넘으면, 그 대화에게 「지금까지 배운 것의 완성본」을 정해진 표식 사이에 쓰게 하고,
  그걸 저장한 뒤 새 대화를 연다. 새 대화는 그 기억을 첫 프롬프트로 읽는다. 오래된 대화의 앞부분이 흐려지는 문제를,
  요약을 사람이 아니라 **당사자에게** 시키는 것으로 풀었다.
- **기억 묶음은 여섯 개.** 공통 · 서버 개발 · 서버 점검 · 앱 개발 · 앱 점검 · PM. 처음엔 역할 수만큼 나눴다가 「헷갈린다」는 피드백에
  사람이 부르는 이름 기준으로 다시 묶었다. iOS 반영 담당은 앱 개발 기억을 같이 읽는다.
- **「기억시키기」는 일을 끊지 않는다.** 사무실 화면에서 묶음을 골라 한 줄을 남기면, 돌고 있는 일은 그대로 두고 다음 일감부터 읽힌다.
- **계정이 바뀌면 새 대화.** 사용량 한도에 걸려 다른 계정으로 넘어가면 이전 대화를 이어 쓸 수 없으므로, 기억만 들고 새로 연다.
  한도 문구를 못 알아봐 「결과 JSON 없음」으로 멈춘 일이 한 번 있었고, 종료 코드가 0 이어도 마지막 줄의 한도 문구를 보고 다음 계정으로
  넘기게 고쳤다.

## 3. 한도는 횟수가 아니라 시간

턴 수 한도는 일의 크기를 모른다. 앱 QA 는 화면 하나를 확인하는 데도 누르기·캡처·읽기로 턴을 많이 쓰고, 60 턴에서 판정 직전에 잘렸다.
사람이 실제로 신경 쓰는 건 「얼마나 오래 붙잡고 있나」였다.

| 역할 | 시간 한도 | 실측 최대 |
|---|---|---|
| 앱 개발 · 앱 QA | 25분 | 23분 |
| 서버 개발 · 서버 QA | 10분 | 5분 |
| PM | 5분 | 2분 |

턴은 300(PM 100)으로 올려 **폭주를 막는 마지막 안전장치**로만 남겼다. 사람은 사무실 화면의 「멈추기」로 언제든 끊을 수 있고, 멈추면
그 이슈에 줄 서 있던 작업 카드도 같이 취소된다.

## 4. 스크립트가 판단을 덮지 않게

문서만 고친 이슈에서 PM 은 「앱 QA 대상이 아니다」라고 맞게 판단했다. 그런데 단계 스크립트가 「FE 완료 라벨이면 앱 QA」로 넘겨,
QA 가 에뮬레이터를 켜고 볼 화면이 없어 막혔다. 에이전트는 맞았고, **스크립트가 그 판단을 덮었다.**

고친 기준은 이렇다.

- 스크립트가 다음 단계로 **자동으로 넘기는 건 객관적 조건일 때만** — 커밋이 있다, PR 이 있다, 앱 코드가 바뀌었다.
- 그 밖은 PM 이 정한다. 「무엇을 검증해야 하나」는 일의 내용을 읽어야 답할 수 있는 질문이다.
- **비싼 준비는 조건을 확인한 뒤에.** 에뮬레이터·시뮬레이터 기동은 몇 분과 메모리를 먹는다(맥 한 대에서 둘을 같이 켜면 메모리가 모자란다).
  볼 화면이 있는지 먼저 확인한다.

## 5. 승인제를 거둔 곳 — 스테이징 DB 는 바로 실행하고 보고한다

시험 상태를 만들려면 가끔 스테이징 DB 한두 줄을 바꿔야 한다. 처음 설계는 보수적이었다 — 에이전트가 요청을 내면 대상 행을 먼저 조회해
보여 주고, 사람이 PIN 으로 승인해야 실행. 다시 세어 같을 때만, 한 트랜잭션으로.

일주일 써 보니 **승인 대기가 일을 막는 가장 흔한 이유**가 됐다. 사람의 결론은 「그냥 하고 보고만 잘해라」였다.

- 요청 = 그 자리에서 한 트랜잭션으로 실행하고, 이슈에 「무엇을 왜 바꿨는지」 보고 댓글을 남긴다.
- 그래도 남긴 선: **스키마 변경과 운영 DB 는 불가.** 초기화로 지워지지 않아 시험 계정을 영구히 막아 버리는 테이블(신고 기록) 쓰기도 거절한다.
- 승인 흐름(PIN·재카운트)은 코드에 그대로 두고 스위치 하나로 되돌릴 수 있게 했다.
- **DB 보다 앱이 먼저.** 상대 계정이 해야 하는 동작(신청·수락·나가기)은 그 계정의 토큰으로 **실제 앱 API** 를 부르는 도구로 만든다.
  시험 전용 API 는 만들지 않는다 — 운영 코드에 들어가는 순간 공격면이 되기 때문이다. 모든 에이전트가 「앱 사용 설명서」를 읽고 시작한다.

같은 시기에 찾은 것 하나 — QA 시작 시 테스트 계정 초기화가 인증 토큰 없이 불려 **처음부터 한 번도 돌지 않았다**(401). 실패가 조용했던
이유는 초기화 결과를 아무도 확인하지 않았기 때문이다. 시험 계정으로 로그인한 토큰을 받아 부르도록 고쳤다.

## 6. 큰 기능은 기능 브랜치로

버그·작은 개선은 지금처럼 `feature/v2` 로, 홈 개편 같은 큰 신규 기능은 **앱 저장소만** `feature/v2-<이름>` 에 모은다.

- 서버는 브랜치를 나누지 않는다. 스테이징 서버가 v2 로 돌고, 새 API 는 **추가만** 하니 먼저 들어가도 기존 앱이 깨지지 않는다.
- 이슈 본문 첫 줄 `기준 브랜치: feature/v2-…` 를 보고 앱 담당이 그 브랜치에서 시작하고 PR 도 그쪽으로 낸다. PM 이 오더를 정리할 때 적는다.
- 기능 브랜치 PR 은 머지돼도 iOS 출시 브랜치 검증을 띄우지 않는다. 끝날 때 한 번 v2 로 합치고, 그때 기존 iOS 검증 흐름을 탄다.
- v2 를 기능 브랜치로 끌어오는 도구(`sync`)는 충돌이 나면 멈추고 파일 목록만 알린다. 충돌을 에이전트가 푸는 것은 아직 하지 않는다.

## 7. PM 의 자율 점검 — 일을 스스로 찾는다

PM 에이전트는 오더를 기다리기만 하지 않고 주기적으로 정해진 영역 하나를 둘러보고 **일을 찾아 이슈로 올린다.**
앞 문서의 버그도 이렇게 찾은 것이다.

- 찾은 일은 바로 시작하지 않고 「발견 대기」로 둔다. 사람이 사무실 카드에서 「맡기기」를 누르면 팀이 시작한다(설정으로 바로 시작도 가능).
- 한 번에 두 건까지만 올린다. 둘러본 범위는 결과에 남겨, 같은 곳을 반복해서 보지 않는다.
- 고칠 방법이 정해지지 않았거나 질문이 있으면 「착수 보류」로 질문을 남긴다.

## 8. 사람 쪽 마찰 두 가지 — 상태가 사실보다 늦거나, 버튼이 일을 되돌려보내거나

에이전트 쪽이 매끄러워지자 **사람이 보는 화면과 버튼**에서 마찰이 드러났다.

### 머지했는데 「승인 대기」

사람이 iOS PR 을 머지하고 사무실 화면을 몇 번 새로고침해도 카드는 「승인 대기」였다. 화면은 캐시 없이 GitHub 라벨을 그대로 보여 주고,
라벨을 정리하고 이슈를 닫는 건 **2분마다 도는 뒷정리**다(앞 문서에서 10분 → 2분으로 줄인 그 주기). 실제로 머지 후 1분 36초 뒤에 닫혔다.
그 사이 화면은 틀린 게 아니라 **늦은 것**이었지만, 사람에게는 「머지가 안 먹었다」로 읽힌다.

주기를 더 줄이면 GitHub 호출이 늘 뿐 간격은 남는다. 대신 화면이 아는 사실로 판단하게 했다 — 「승인 대기」인데 열린 PR 도 남은 iOS
결정도 없고 머지된 PR 이 있으면, 뒷정리를 기다리지 않고 **「머지됨 · 정리 중」**으로 보여 주고 「사장님 할 일」에서 뺀다.
상태의 원본(라벨)은 그대로 두고 **표시만 사실에 맞췄다.**

같이 칩 색도 정리했다. 「승인 대기」가 서버 QA 와 같은 초록, iOS 가 서버 개발과 비슷한 파랑이라 색으로 구분이 안 됐다.
**같은 역할끼리만 같은 색**으로 묶었다 — PM 보라 · 서버 개발 파랑 · 서버 QA 초록 · 앱 개발 분홍 · 앱 QA 주황 · iOS 청록 ·
사람 차례 먹색 · 머지 짙은 청록 · 위험 빨강.

### 「맡기기」를 눌렀더니 「다시 맡기기로 넘기라」

PM 이 찾은 일의 제목에는 `[FE]` 라고 써 놓고, 결과 JSON 의 범위 칸은 비워 둔 경우가 있었다. 이슈를 만드는 스크립트는 범위 칸만 봐서
범위 라벨을 붙이지 않았고, 질문도 없는데 「범위를 정할 수 없음」 댓글을 자동으로 달았다. 사람이 「맡기기」를 누르면, 다음 담당을 정하는
단계가 **AI 없이 범위 라벨만 보는 스크립트**라 막힐 것이 뻔했으므로, 사무실 서버가 미리 409 로 거절하고 「다시 맡기기로 PM 에게 범위를
정하게 하라」고 안내했다. 사람 입장에서는 맡겼는데 일을 돌려받은 셈이다.

- 이슈를 만들 때 범위 칸이 비면 **PM 이 제목에 적은 `[FE]`·`[BE]`·`[BE·FE]` 로 채운다.** 같은 에이전트가 쓴 두 칸이 어긋난 것이니,
  사람에게 묻기 전에 그 에이전트가 이미 남긴 정보부터 쓴다.
- 「맡기기」는 거절하지 않는다. 범위 라벨이 없으면 제목으로 붙이고 시작하고, 제목에도 없으면 **PM 에게 범위를 정하게 넘긴다.**
  버튼의 의미(「이 일을 하라」)를 시스템 사정으로 바꾸지 않는다.
- 범위는 있는데 질문 없이 보류된 경우의 자동 문구도 「바로 시작할 일인지 PM 이 확신하지 못함」으로 실제 사유에 맞췄다.

두 건 모두 고친 쪽은 에이전트가 아니라 **사람이 보는 표시와 누르는 버튼**이었다. 에이전트가 맞게 일해도, 사람이 화면을 믿지 못하거나
버튼이 일을 되돌려보내면 사람은 다시 직접 확인하러 간다 — 자동화가 아낀 시간이 그 자리에서 새어 나간다.

## 9. 남은 것

- **기능 브랜치 동기화 충돌**은 아직 사람이 푼다. PM 이 `sync` 를 직접 돌리고 충돌을 앱 담당에게 카드로 넘기는 것이 다음 단계다.
- **한 이슈에서 앱 PR 이 두 번 나오는 경우**(후속 수정) iOS 검증 시작 버튼 판정이 어긋난다. 판정을 「이슈당 마지막 앱 PR」 기준으로 바꿔야 한다.
- 사무실 화면의 표시 규칙(`stageText`)과 서버의 넘김 이력 판정(`holder_of`)이 같은 규칙을 두 언어로 들고 있다. 이번 「정리 중」은 화면에만
  넣었다. 규칙이 더 늘면 서버 한 곳에서 계산해 내려 주는 쪽으로 합친다.
